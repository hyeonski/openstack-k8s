# ADR-0017: S1 복구 목적지 compute의 용량을 늘린다

- 상태: 채택됨 — 2026-10-02 S1 복구 실험 구성
- 결정일: 2026-10-02
- 관계: ADR-0016의 compute01 사양만 대체한다. 호스트 수, VM flavor, worker 증감 범위와 기존 검증 기록은 유지한다.

## 배경

S1 자동 진단과 다른 compute로의 Pod 재배치는 동작했으나, 4 vCPU 목적지에서는
회복 p95가 기준선의 1.2배를 간헐적으로 초과했다. 60초 구간 3회 연속 안정화를
최대 8회 관측하는 정책에서도 연속 성공은 최대 2회였고 `needs_review`로 끝났다.
요청 성공과 평균 개선만으로 복구 완료를 선언하지 않는다.

compute01에는 workload control plane과 복구 목적지 worker가 함께 있다. 호스트의
평균 CPU 사용률만으로 요청 지연의 여유를 보장할 수 없으므로, 목적지 용량을
늘린 별도 실험 구성을 채택한다. 임계값은 실패 결과를 통과시키기 위해 완화하지 않는다.

## 결정

- compute01을 `n2-standard-8`(8 vCPU·32 GiB)로 변경한다. compute02는
  `n2-standard-4`(4 vCPU·16 GiB), controller는 `e2-standard-4`로 유지한다.
- GCP 호스트 3대, workload control plane 1대, worker 1~3대와 CP/worker의
  2 vCPU·2 GiB·20 GB flavor, quota·초과 할당 정책·10시간 자동 종료 제한을 유지한다.
- S1 측정은 서비스·경쟁 VM을 compute02에, 요청 control plane·목적지 worker를
  compute01에 배치한다. 생성 직후 두 worker가 같은 compute에 있으면
  `graduation-s1-spread`가 이번 준비에서 생성한 일반 Pod·연결 볼륨 없는 worker만 이동한다.
- 자동 대응의 회복 기준은 기준선 p95의 1.2배 이내, 요청 실패 없음, 60초 구간
  3회 연속 통과 및 전체 부하 마지막 60초 재확인이다. 관측 상한은 8개 구간이다.
- 기반 사양은 IaC에 반영하고 실제 클라우드와의 차이를 확인한다. 재기동 후
  Cinder loop/VG와 CSI가 자동으로 복원되는지도 확인한다.

## 결과 해석과 전환 조건

실측 수치와 정리 상태는 [통합 검증 기록](../graduation/recovery-validation-2026-10-02.md)에
남긴다. 4 vCPU 구성의 실패를 새 기준으로 재분류하지 않는다. 용량 변경과 함께
호스트 재기동·worker 재생성이 있었으므로 CPU 증설만의 인과 효과를 분리한 실험은 아니다.
S2·S3의 최종 실행은 증설 전 구성에서 수행했으며 S1의 증설 후 실행과 구분한다.

compute01의 실행 비용은 증가한다. 사용하지 않을 때 세 호스트를 모두 종료하며,
원래 사양으로 되돌릴 때에는 같은 복구 기준을 새 실행으로 검증하고 IaC와 이 결정을
함께 갱신한다. 새 사양에서 worker 1→3 자동 증감 전체를 재검증했다고 주장하지 않는다.
과거 4 vCPU 구성의 CA·S4 검증 결과는 해당 당시 조건의 기록으로 유지한다.
