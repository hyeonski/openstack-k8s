# Monolith 운영 리허설 플랫폼 기획서

- 작성일: 2026-09-09
- 상태: 제품 기획 초안 — 구현 전 검토 대상
- 대상: 외부 고객이 소스 코드를 제출하는 SaaS
- 실행 기반: 현재 저장소가 구축하는 GCP·OpenStack·Kubernetes 환경
- 관련 문서: [PRD](./prd.md), [현재 저장소 설명](../../README.md)

## 1. 제품 정의

사용자가 소스 코드와 예상 트래픽을 제출하면, 고객 서비스의 운영 비용을 먼저 간략히 추정하고, 격리된 실험으로 성능·용량·확장·복구 특성을 확인해 운영 구성과 개선 우선순위를 제시한다.

부하 테스트 경험이 없는 개발자도 무엇을 테스트할지 직접 설계하지 않고 첫 결과를 얻을 수 있어야 한다. 관측값, 실험에서 검증한 판단, 추정과 가정을 구분하고, 근거가 부족하면 판단을 보류한다.

## 2. 합의된 방향과 결정 보류 범위

### 2.1 합의된 방향

| 항목 | 방향 |
|---|---|
| 사용자 | 외부 고객의 백엔드 개발자와 운영 담당자 |
| 제공 형태 | 소스 코드를 직접 제출받는 SaaS |
| 필수 분석 입력 | 프로젝트 소스 코드와 개발 중 계획한 예상 트래픽, 두 가지 |
| 초기 아키텍처 범위 | Monolith 우선, MSA 제외 |
| 비용의 의미 | 고객이 제출한 서비스 또는 제안된 구성으로 운영할 때 부담할 비용 |
| 결과 순서 | 운영 비용 초안 → 실험 결과 → 구성별 성능·운영 비용 비교 |
| 실행 기반 | 현재 레포의 구축 결과 위에 제품 기능 추가 |
| 자동화 원칙 | 가능한 조건은 자동 분석하고, 부족한 정보는 가정 또는 미확인으로 표시 |
| 진행 범위 | 제품 기획과 PRD 작성. 애플리케이션 구현은 별도 단계 |

### 2.2 현재 선택하지 않는 항목

새 제품의 언어·프레임워크·데이터 저장 기술·부하 생성 도구·작업 실행 도구를 선택하지 않는다. 최초 고객 코드 지원 언어와 프레임워크, 지원 DB 제품도 기술 검토 단계에서 결정한다. 앞선 논의의 특정 언어·프레임워크·DB 조합은 채택한 결정이 아니다.

이는 실행 기반을 미정으로 둔다는 뜻이 아니다. GCP·OpenStack·Kubernetes라는 기존 기반은 고정이며, 새 기술 선택은 그 위에서 요구사항을 충족하는 방법에 한정한다.

월 비용 산정을 위한 최초 고객 배포 프로파일, 기본 평가 수치, 테스트 시간과 자원 상한, 보존 기간도 이 문서에서 임의의 확정값으로 만들지 않는다. 베타 전 각각 명시적이고 버전이 있는 운영 정책으로 정한다. 사용자에게 추가 필수 입력을 요구하는 방식으로 결정을 넘기지 않는다.

## 3. 문제와 제품 가설

### 3.1 사용자가 겪는 문제

- 예상 트래픽에 어떤 테스트가 필요한지 모른다.
- 응답시간과 자원 사용량을 측정해도 운영 결정을 내릴 기준이 부족하다.
- 트래픽 급증 시 자동 확장이 늦어질 수 있다는 점을 확인하기 어렵다.
- 서버 증설이 효과적인지, DB나 다른 공유 자원이 병목인지 구분하기 어렵다.
- 과도한 자원 할당과 장애 대비 여유를 구분하기 어렵다.
- 운영 비용과 성능을 같은 조건에서 비교하기 어렵다.
- 테스트 데이터와 시나리오의 부족을 서비스 전체의 안정성으로 오인할 수 있다.

### 3.2 검증할 제품 가설

1. 두 가지 입력만으로 지원 범위에 속하는 프로젝트의 유효한 첫 실험을 만들 수 있다.
2. 상황별 판정과 다음 행동이 원시 지표만 제공하는 것보다 이해하기 쉽다.
3. 구성 비교와 추천 재실험이 실제 운영 설정 결정에 도움을 준다.
4. 고객이 다음 배포나 트래픽 계획 변경 시 서비스를 다시 사용한다.

사업성은 확정하지 않는다. 외부 베타에서 자동 온보딩 성공률, 수작업 개입, 결과 활용과 반복 사용을 검증한다.

## 4. 사용자와 대표 사용 상황

| 사용자 | 상황 | 필요한 결정 |
|---|---|---|
| 출시를 준비하는 개발자 | 예상 사용자 수는 있지만 성능 기준이 없음 | 예상 트래픽에서의 성능과 초기 구성 선택 |
| 작은 팀의 운영 담당자 | 이벤트로 트래픽 급증 예상 | 사전 여유와 확장 설정 준비 |
| 운영 비용을 줄이려는 개발자 | 현재 자원 할당이 과한지 의문 | 더 작은 구성의 성능·비용·복구 조건 비교 |
| 기능을 변경한 개발자 | 성능이 나빠졌는지 확인 필요 | 같은 조건의 이전 결과와 비교 |

첫 베타는 외부 고객을 제한적으로 수용한다. 동시에 많은 고객을 실행하는 기능보다 유효한 실험과 결과 해석을 우선한다. 초기에는 한 번에 한 실험을 실행하는 방안을 기본 운영안으로 둔다.

## 5. 최소 입력과 자동 분석

### 5.1 입력 경험

프로젝트 ZIP 업로드와 자연어 트래픽 설명을 첫 입력 방식으로 제안한다. 별도 테스트 스크립트, 인프라 설정, SLO 수치, 클라우드 계정 정보를 필수로 요구하지 않는다. 계정 인증과 이용 동의는 분석 입력과 별도의 서비스 이용 절차다.

| 트래픽 설명 | 처리 원칙 |
|---|---|
| 평소 20 RPS, 이벤트 때 5분간 200 RPS | 명시된 도착률과 지속 시간을 보존 |
| 동시 사용자 500명 | 행동 빈도·대기 시간·요청 수를 가정하고 출처 표시 |
| 하루 방문자 1만 명, 저녁에 집중 | 방문당 요청 수와 집중 시간에 대한 시나리오 범위 생성 |
| 트래픽이 많아질 것 같다 | 탐색 테스트 수행, 예상 트래픽 충족 판정 보류 |

사용자 수, 동시 세션 수, 시나리오 실행 횟수, HTTP 요청 수를 같은 단위로 취급하지 않는다. 사용자 설명을 변환한 산식과 가정은 결과에서 확인할 수 있어야 한다.

### 5.2 플랫폼이 준비할 내용

- 지원 범위 판정과 빌드·실행 방법 파악
- API, 데이터 구조, 인증, 외부 의존성 탐색
- 테스트 데이터와 정상 응답 조건 준비
- 대표 API 또는 사용자 흐름과 호출 비율 선택
- 런북 선택과 제한된 비교 구성 생성
- 초기 비용 산정용 구성과 가정 작성

코드에서 직접 확인한 사실, 사용자 입력, 플랫폼 가정, 미확인을 구분한다. 임의의 프로젝트를 모두 자동 실행할 수 있다고 약속하지 않는다. 지원 범위는 구현 단계에서 정하고 사전에 안내한다.

### 5.3 실패와 불확실성 처리

필수 인증이나 데이터 준비를 재현할 수 없으면 해당 기능을 제외하거나 실행을 보류한다. 외부 의존성을 대체 응답으로 처리했다면 실제 외부 서비스 성능은 미검증이다. 선택한 API만 테스트한 경우 전체 서비스에 대한 통과 판정을 하지 않는다.

자동 분석으로 만든 가정은 추가 확인을 매번 요구하지 않고 공개한다. 사용자는 선택적으로 수정해 새 실행을 만들 수 있다. 가정이 바뀌면 과거 실행의 조건과 결과를 덮어쓰지 않는다.

## 6. 사용자 여정과 화면

| 단계 | 사용자 경험 | 제공 결과 |
|---|---|---|
| 제출 | 코드와 트래픽을 입력하고 시작 | 접수, 코드 버전 식별 |
| 분석 | 진행 상황과 지원 여부 확인 | 감지한 구성, 테스트 범위, 가정 |
| 비용 초안 | 테스트 완료를 기다리지 않고 비용 확인 | 고객 월 운영 비용 초안, 포함·미산정 항목 |
| 실험 | 현재 단계와 중단 가능 여부 확인 | 실험 중간 상태, 실패·제한 이유 |
| 결과 | 핵심 판단부터 상세 근거 확인 | 9개 결과 영역과 검증 상태 |
| 보정·재실행 | 가정이나 예상 트래픽을 선택적으로 수정 | 변경된 조건의 새 결과 |
| 비교 | 이전 실행 또는 추천 후보 비교 | 성능·비용 변화와 비교 가능 여부 |

화면은 새 분석, 진행 상황, 결과, 분석 이력 네 영역으로 구성한다. 기술 로그는 상세 보기로 두고 기본 화면에는 사용자에게 의미 있는 상태와 다음 행동을 표시한다.

## 7. 사용자에게 제공할 결과

| ID | 결과 | 사용자가 알 수 있는 내용 | 주요 조건과 한계 |
|---|---|---|---|
| O-01 | 예상 운영 비용 | 고객 서비스의 기본 월 비용, 변동 비용, 구성별 비용 | 가격표·배포 프로파일·가정 표시 |
| O-02 | 목표 트래픽 대응 | 실제 처리량, 기능별 지연·오류·정상 처리율 | 적용한 목표 또는 플랫폼 기준 표시 |
| O-03 | 검증된 용량과 여유 | 최고 통과 부하, 첫 기준 초과 구간, 목표 대비 여유 | 상한까지 통과해도 최대 용량 발견으로 표현하지 않음 |
| O-04 | 병목과 원인 후보 | 자원·DB·공유 구간의 포화 징후, 추가 조사 대상 | 관측과 원인 가설 구분 |
| O-05 | 자원 설정 후보 | CPU·메모리·실행 개수 등의 비교 결과 | 실험한 후보만 검증된 추천으로 표시 |
| O-06 | 확장 정책과 지연 | 감지·준비 시간, 확장 중 오류, 축소 결과 | 사양 변경·애플리케이션 증감·노드 증감 분리 |
| O-07 | 지속 실행과 복구 | 누적·악화 징후, 재시작·축소·복구 중 영향 | 실험 시간과 정의한 기능 범위에 한정 |
| O-08 | 구성 적정성과 비용 대안 | 최소·여유·복구 요구 후보의 성능과 비용 | 저사용률만으로 과설계 단정 금지 |
| O-09 | 개선 우선순위 | 권장 변경, 근거, 비용 변화, 재검증과 관측 방법 | 예상 효과와 검증된 효과 구분 |

첫 화면은 목표 대응 판정, 월 운영 비용, 우선 문제, 검증된 추천, 중요한 가정과 미검증 범위를 보여준다. 9개 영역을 제공하되 실행하지 않은 항목은 미검증으로 표시한다.

## 8. 런북 구성

런북은 사용자 상황에 대응하는 재현 가능한 실험 절차다. 목적, 선행 조건, 대상 기능, 입력 조건, 데이터 준비, 단계, 측정값, 유효성 조건, 판정 기준, 중단 조건, 결과 보존, 정리 범위를 포함한다.

| ID | 런북 | 목적 | 적용 조건 | 주 결과 |
|---|---|---|---|---|
| R-01 | 기본 동작 | 테스트 데이터와 요청이 실제로 유효한지 확인 | 실행 가능한 프로젝트 | O-02의 선행 근거 |
| R-02 | 워밍업·기준 측정 | 초기화와 정상 상태 구분 | R-01 통과 | O-02, O-04 |
| R-03 | 예상 부하 유지 | 목표 트래픽에서 품질 유지 확인 | 해석 가능한 트래픽과 평가 기준 | O-02 |
| R-04 | 단계적 부하 증가 | 품질 저하 구간 탐색 | 유효한 기준 측정 | O-03, O-04 |
| R-05 | 사양·실행 개수 비교 | 제한된 구성 후보의 효과 비교 | 같은 데이터·조건 재현 가능 | O-05, O-08 |
| R-06 | 급증·확장 | 늘어난 수요에 제때 대응하는지 확인 | 복수 실행 및 확장 가능 | O-06 |
| R-07 | 부하 감소·축소 | 요청 처리 중 안전하게 줄어드는지 확인 | 확장 또는 복수 실행 완료 | O-06, O-07 |
| R-08 | 지속 실행 | 시간에 따른 성능·자원 변화 확인 | 실행 시간 예산 확보 | O-07 |
| R-09 | 재시작·복구 | 정의된 중단으로부터 회복 확인 | 재현·복구 가능한 테스트 상태 | O-07 |

코드·데이터·호출 비율·워밍업 조건을 고정하고 비교한다. 사양과 실행 개수, DB 조건을 동시에 바꿔 원인을 구분할 수 없게 만들지 않는다. 비교 후보와 반복 실행은 시간·자원 상한 안에서 제한한다.

## 9. 평가와 추천 원칙

### 9.1 수치의 의미

- 관측값: p90·p95·p99, 처리량, 오류율, 자원 사용량 등 실제 측정
- 목표값: 평가에서 사용할 지연·오류 등의 허용 조건
- 확장 기준값: 자원을 추가하거나 줄이는 정책
- 경보 기준값: 운영자가 상황을 확인할 조건
- 자원 제한값: 실행에 허용할 자원의 경계

이들을 하나의 적정 threshold로 묶지 않는다. 사용자가 목표를 지정하지 않아도 버전이 있는 플랫폼 평가 프로파일로 첫 실험을 진행할 수 있으나, 이를 고객 사업에 필요한 목표라고 표현하지 않는다. 적절한 프로파일을 적용할 수 없는 경우에는 탐색 결과만 제공한다.

### 9.2 신뢰 가능한 판단

목표 부하와 실제 도달 부하, 누락·미실행 요청, 기능별 정상 응답과 실패를 기록한다. 표본 수, 측정 시간, 반복 변동, 부하 생성기와 기반 환경의 포화를 확인한다. percentile을 실행별·인스턴스별 단순 평균해 종합값으로 만들지 않는다.

원인 추천은 관측 사실 → 원인 가설 → 비교 실험 → 검증된 효과 순서로 발전시킨다. 근거가 없는 코드 위치나 DB 쿼리를 문제로 확정하지 않는다. 측정이 부족하면 추천을 보류하는 것이 정상 동작이다.

### 9.3 오버 엔지니어링 판단 범위

작은 후보가 동일한 성능·확장·복구 요구를 충족하는지 비교한다. 후보 사이의 비용과 효과를 보여주며, 자원 사용률이 낮다는 이유만으로 불필요한 구성이라고 단정하지 않는다. 실험 결과만으로 아키텍처 전체의 적정성, Kubernetes 필요 여부, MSA 전환 필요성을 결정하지 않는다.

## 10. 고객 운영 비용 산정

### 10.1 산정 대상

고객의 서비스 운영 비용을 산정한다. 플랫폼의 실험 수행 비용과 SaaS 이용료는 O-01과 O-08에 포함하지 않는다.

코드에 배포 구성이 있으면 지원하는 범위에서 그 구성을 해석한다. 없으면 명시적인 고객 배포 프로파일을 사용해 제안된 구성의 비용을 산정한다. 기존 GCP·OpenStack·Kubernetes 실험 기반 전체를 고객에게 필요한 구성으로 간주하지 않는다.

### 10.2 비용 구성

- 컴퓨팅: 사양별 개수와 가동 시간
- DB: 배포 형태, 사양, 저장 공간
- 저장·백업: 할당 용량, 사용량, 보존 조건
- 네트워크: 외부 전송량과 단가 적용 구간
- 부가 인프라: 실제 고객 구성에 필요한 로드밸런서·공인 주소 등

월 비용은 구성 요소의 가동·할당 비용과 사용량 기반 비용의 합으로 계산한다. 가격표 식별자, 지역, 통화, 기준일, 월 가동 시간, 할인·세금 처리, 포함·제외 항목을 보존한다.

초기에는 측정 전 가정으로 비용 초안을 만들고, 응답 크기 등 측정 가능한 정보가 확보되면 산정 근거를 보완한다. 값이 없으면 미산정으로 표시하며 0원과 구분한다. 피크 지속 시간이 없으면 임의의 평균을 사실처럼 제시하지 않고 비용 시나리오나 범위를 사용한다.

### 10.3 성능과 비용의 연결 한계

같은 조건에서 검증한 자원 후보에 고객 배포 가격을 대응시킨다. 중첩 가상화의 측정값과 다른 운영 환경의 처리량이 동일하다고 가정하지 않는다. 가격 대응이 가능해도 성능 대응을 검증하지 못했으면 운영 환경 성능은 미검증으로 표시한다.

구성 절감 비교는 같은 가격 기준과 포함 범위로 계산한다. 기반 호스트와 그 내부 VM 비용을 중복 합산하지 않고, 논리적 자원 감소를 실제 청구액 감소로 자동 환산하지 않는다.

## 11. 기존 레포 위에서의 제품 확장

현재 구축 기반은 GCP 호스트, OpenStack, Kubernetes 노드 이미지, management cluster, CAPI/CAPO, workload cluster와 Autoscaler 검증 흐름이다. 제품은 이 결과 위에서 실행한다. 대체 인프라로의 이관이나 별도 플랫폼 재구축은 본 기획에 포함하지 않는다.

새로 필요한 제품 책임은 코드 접수·실행 준비, 트래픽 해석, 런북 실행, 애플리케이션·DB 관측, 비용 산정, 결과 판정, 실행 이력과 사용자 화면이다. 배치 위치와 구현 도구는 추후 설계하되, 제출 코드가 기존 관리 권한과 기반 서비스에 접근하지 못하는 경계를 유지한다.

현재 worker 증설 검증은 제품의 HTTP 성능·자동 축소 검증과 동일하지 않다. compute 호스트의 용량은 유한하고, 내부 worker를 추가해도 기반 GCP 용량이 자동으로 늘지 않는다. 실험 환경의 용량 한계를 고객 코드의 한계와 구분해야 한다.

기존 ADR은 현재 기반에 계속 적용된다.

- [ADR-0013](../adr/0013-use-gcp-as-the-only-runtime.md): GCP 단일 실행 환경
- [ADR-0014](../adr/0014-run-management-capi-on-controller.md): controller의 management 환경
- [ADR-0015](../adr/0015-require-layered-gcp-verification.md): 계층별 검증과 실패 증거 보존

고객별 실행 상태, 이름, 경로, 대상 소유 범위의 분리는 제품 실행에 추가한다. 제품 실험 자원의 수명주기를 정할 때 기존 persistent foundation을 정리 대상으로 삼지 않는다. 실패 증거를 수집한 뒤 고객 실험 자원을 기한에 따라 정리하는 정책은 기존 무기한 보존과 구분하며, 충돌하는 기반 정책을 변경할 경우 별도 ADR에서 다룬다.

## 12. MVP 범위와 확장 순서

| 단계 | 제공 범위 | 완료 조건 |
|---|---|---|
| A. 실험 기반 검증 | 현재 레포 위에서 기준 Monolith 실행과 계층별 관측 | 의도한 애플리케이션·DB 병목과 실험 환경 포화 구분 |
| B. 핵심 MVP | 두 입력, 자동 준비, 비용 초안, R-01~R-05, 결과·비교·다음 행동 | 지원 프로젝트에서 추가 필수 입력 없이 유효한 첫 결과 |
| C. 확장·안정성 | 조건부 R-06~R-09, O-06·O-07 상세 검증 | 확장 중 품질, 축소·복구, 지속 실행 결과 제공 |
| D. 외부 베타 확대 | 외부 프로젝트 적용, 온보딩·반복 사용 개선 | 신뢰도·자동화·사용자 이해도 평가 후 수용 범위 확대 |

고객 접근 분리, 제출 코드의 관리 권한 접근 차단, 실행 상한·중단·자료 정리는 외부 코드를 수용하기 전에 검증한다. D 단계까지 미루는 선택 기능이 아니다.

핵심 MVP 보고서에는 9개 결과 영역을 유지하되 아직 수행하지 않은 확장·복구 항목은 미검증으로 표시한다. 기능을 구현했다는 이유만으로 모든 프로젝트에 검증 완료 결과를 보장하지 않는다.

## 13. 성공 지표와 제품 검증

| 지표 | 정의 |
|---|---|
| 지원 프로젝트 자동 완료율 | 지원 판정된 제출 중 추가 필수 입력·수작업 없이 유효한 핵심 결과를 얻은 비율 |
| 전체 제출 지원 비율 | 유효한 업로드 중 지원 판정을 받은 비율 |
| 수작업 개입 | 실행당 운영자 개입 횟수와 시간 |
| 첫 비용·결과 대기 시간 | 제출 후 비용 초안, 유효한 실험 결과까지 각각 걸린 시간. 대기와 실행 구분 |
| 판정 신뢰도 | 의도한 병목·실패 사례의 판정 정확성과 무효 실험의 판정 보류 여부 |
| 추천 재검증 | 목표·비용·부작용을 포함한 추천의 재실험 결과 |
| 이해·활용 | 사용자가 결과에서 다음 행동을 선택할 수 있는지 |
| 반복 사용 | 다음 배포 또는 트래픽 계획 변경 시 다시 실행하는지 |

베타 표본 없이 수치 목표를 임의 확정하지 않는다. 출시 정확성 조건은 [PRD의 수용 기준](./prd.md#10-출시-수용-기준)에 명시하고, 사용성과 사업 지표의 목표값은 베타 기준선 확보 후 정한다.
