# PRD — Monolith 운영 리허설 플랫폼

- 작성일: 2026-09-09
- 상태: 제품 요구사항 초안 — 구현 전 검토 대상
- 기획 근거: [플랫폼 기획서](./plan.md)
- 고정 실행 기반: 현재 저장소가 구축하는 GCP·OpenStack·Kubernetes 환경
- 기술 선택: 신규 제품 기술 스택과 최초 고객 코드 지원 스택은 보류

## 1. Problem Statement — 문제 정의

백엔드 개발자는 예상 트래픽을 감당할 수 있는지, 어떤 지연시간과 자원 설정을 기준으로 평가해야 하는지, 현재 구성이 과하거나 부족한지 판단하기 어렵다. 부하 테스트 도구를 실행해도 적절한 시나리오·데이터·기준이 없으면 결과를 실제 운영 결정으로 연결하기 어렵다.

사용자가 알고 싶은 비용은 자신이 제공한 서비스 또는 제안된 구성의 운영 비용이다. 실험 플랫폼의 내부 실행 비용과 구분해야 한다. 또한 사용자는 테스트 전문가가 아니므로 소스 코드와 개발 중 계획한 예상 트래픽 외의 설정을 첫 결과의 필수 입력으로 요구하지 않는다.

## 2. Solution — 해결 방향

외부 고객이 코드와 예상 트래픽을 제출하면 플랫폼이 실행 범위를 분석하고 고객 월 운영 비용 초안을 먼저 제공한다. 이어서 현재 레포의 구축 환경 위에서 조건이 통제된 실험을 수행하고, 성능·용량·병목·자원 설정·확장·복구·비용 대안·개선 우선순위를 제시한다.

Monolith를 우선 지원한다. 자동으로 준비할 수 없는 흐름은 미검증 또는 지원 제한으로 표시한다. 사용자 입력, 코드에서 확인한 사실, 플랫폼 가정, 미확인을 구분한다. 신규 제품 기술 스택, 지원 언어와 DB 제품, 구현 도구는 본 PRD에서 선택하지 않는다.

### 2.1 우선순위

| 우선순위 | 의미 |
|---|---|
| P0 | 핵심 MVP 및 최초 외부 코드 수용 전에 필요한 요구사항 |
| P1 | 확장·축소·지속 실행·복구에 대한 후속 실험 요구사항 |

### 2.2 용어

| 용어 | 정의 |
|---|---|
| 고객 서비스 | 사용자가 제출한 Monolith와 그 실행 의존성 |
| 실행 기반 | 현재 레포가 구축하는 GCP·OpenStack·Kubernetes 환경 |
| 고객 배포 프로파일 | 고객 서비스 운영 비용을 계산할 대상 구성과 가격 조건 |
| 분석 실행 | 코드 버전, 트래픽, 가정, 평가 프로파일을 고정한 하나의 작업 |
| 사용자 흐름 | 인증·데이터·호출 순서·정상 응답 조건을 포함한 기능 수행 절차 |
| 런북 | 목적·조건·실행·관측·판정·중단·정리를 가진 실험 절차 |
| 평가 프로파일 | 적용 대상과 기준값·측정 창·판정 규칙이 명시된 버전별 정책 |
| 검증된 추천 | 조건을 고정한 재실험으로 효과와 제약을 확인한 구성 또는 변경 |
| 미검증 | 해당 기능 또는 조건을 실제 실험하지 않은 상태 |
| 판정 보류 | 실험의 유효성이나 근거가 부족해 결론을 내리지 않는 상태 |

## 3. User Stories — 사용자 이야기

1. 출시를 준비하는 개발자로서, 코드와 예상 트래픽만 제출해 테스트 준비 지식 없이 첫 결과를 얻고 싶다.
2. 개발자로서, 자연어로 예상 사용량을 설명해 RPS를 몰라도 분석을 시작하고 싶다.
3. 개발자로서, 내 프로젝트가 지원되는지와 제한 사유를 알아 불필요한 대기를 줄이고 싶다.
4. 개발자로서, 감지한 API와 의존성을 확인해 플랫폼이 실제로 무엇을 이해했는지 알고 싶다.
5. 개발자로서, 내가 입력한 조건과 플랫폼 가정을 구분해 결과의 의미를 이해하고 싶다.
6. 개발자로서, 가정을 선택적으로 수정하고 새 실행을 만들어 내 계획과 더 가까운 결과를 얻고 싶다.
7. 예산을 계획하는 사용자로서, 테스트가 끝나기 전에 고객 서비스의 월 운영 비용 초안을 보고 싶다.
8. 사용자로서, 비용의 포함·제외·미산정 항목과 가격 기준을 확인해 추정액을 오해하지 않고 싶다.
9. 개발자로서, 테스트한 기능과 제외한 기능을 알아 일부 결과를 전체 서비스에 확대 해석하지 않고 싶다.
10. 개발자로서, 정상적인 데이터와 요청으로 테스트했는지 확인해 무의미한 성능 결과를 피하고 싶다.
11. 개발자로서, 예상 트래픽에서 실제 처리량·지연·오류를 확인해 목표 대응 여부를 판단하고 싶다.
12. 개발자로서, 주요 기능별 결과를 확인해 전체 평균에 가려진 문제를 찾고 싶다.
13. 운영 담당자로서, 최고 통과 부하와 첫 기준 초과 구간을 알아 용량 여유를 판단하고 싶다.
14. 운영 담당자로서, 실험 환경이 먼저 포화되었는지 알아 고객 서비스의 한계와 구분하고 싶다.
15. 개발자로서, 병목 관측과 원인 가설을 구분해 우선 조사할 대상을 정하고 싶다.
16. 개발자로서, 제한된 사양·실행 개수 후보를 같은 조건에서 비교해 자원을 결정하고 싶다.
17. 사용자로서, 추천 구성의 월 운영 비용 변화를 확인해 성능과 지출을 함께 판단하고 싶다.
18. 운영 담당자로서, 자동 확장 완료까지의 지연과 오류를 알아 사전 여유를 준비하고 싶다.
19. 운영 담당자로서, 축소 중 요청 실패와 반복 증감을 확인해 확장 정책을 조정하고 싶다.
20. 개발자로서, 지속 실행의 자원 누적과 성능 악화 징후를 알고 싶다.
21. 운영 담당자로서, 재시작과 중단 이후의 복구 시간 및 실패 요청을 확인하고 싶다.
22. 개발자로서, 명시적으로 검증 가능한 업무 조건이 있다면 중복 처리·정합성 결과를 함께 알고 싶다.
23. 사용자로서, 최소 구성과 여유·복구 요구를 충족하는 후보를 비교해 적정 구성을 선택하고 싶다.
24. 사용자로서, 추천마다 근거와 다음 재검증 방법을 받아 실제 작업으로 연결하고 싶다.
25. 사용자로서, 실행 진행 상황과 중단 버튼을 통해 작업을 통제하고 싶다.
26. 사용자로서, 실패하거나 중단해도 확보된 결과와 이유를 확인하고 싶다.
27. 사용자로서, 이전 결과와 비교할 때 어떤 조건이 달라졌는지 알고 싶다.
28. 사용자로서, 제출 코드와 결과에 다른 고객이 접근할 수 없고 보존·삭제 방식을 확인하고 싶다.
29. 플랫폼 운영자로서, 실행별 소유 자원과 상태를 확인해 중복 실행과 잘못된 정리를 방지하고 싶다.
30. 플랫폼 운영자로서, 자동 완료율과 수작업 개입을 측정해 실제로 지원 가능한 범위를 개선하고 싶다.

## 4. 기능 요구사항

### 4.1 입력과 실행 준비

| ID | 우선순위 | 요구사항 | 수용 기준 |
|---|---|---|---|
| FR-01 | P0 | 소스와 예상 트래픽 접수 | 유효한 제출에 실행 ID와 코드 식별값을 부여한다. 분석에 필요한 추가 필수 폼 없이 접수한다. |
| FR-02 | P0 | 지원 범위 판정 | 지원·부분 지원·지원 불가와 이유를 표시한다. 지원 스택은 실제 구현된 지원 정책에 따라 판정하며 무조건 실행하지 않는다. |
| FR-03 | P0 | 코드 분석 | 실행 방법·API·DB·인증·의존성·기존 자원 설정의 확인 결과와 출처를 기록한다. 미확인을 사실로 처리하지 않는다. |
| FR-04 | P0 | 트래픽 해석 | 명시된 단위와 지속 시간을 보존한다. 사용자 수를 요청량으로 변환하면 행동 빈도·호출 수 등 가정과 변환 근거를 기록한다. |
| FR-05 | P0 | 가정 관리 | 추가 입력 없이 기본 분석을 진행할 수 있다. 가정 수정은 새 실행으로 남기며 원래 실행 결과를 덮어쓰지 않는다. |
| FR-06 | P0 | 시나리오·데이터 준비 | API 호출 순서, 데이터 규모, 호출 비율, 정상 응답 조건을 고정한다. 준비 실패 기능과 대체한 외부 의존성을 결과에 표시한다. |
| FR-07 | P0 | 기본 동작 검증 | 정상 요청·데이터 처리가 확인되기 전에 큰 부하 실험을 진행하지 않는다. 상태 코드와 가능한 기능 검증을 함께 확인한다. |

| FR-25 | P1 | 지속 실행·복구 | 관측한 시간 내의 자원 누적·성능 변화, 재시작 이후 회복·실패를 기록한다. 검증 가능한 업무 조건이 없으면 데이터 정합성 검사를 완료로 표시하지 않는다. |

### 4.4 작업 제어와 고객 데이터

| ID | 우선순위 | 요구사항 | 수용 기준 |
|---|---|---|---|

| FR-28 | P0 | 실행 소유·재개 | 실행별 대상과 상태를 식별한다. 재시도 시 실제 자원 상태를 대조해 중복 생성·중복 실험을 방지한다. |

## 5. 결과 계약과 판정 상태

### 5.1 결과의 공통 필드

모든 판단은 실행 ID, 코드 식별값, 런북과 평가 프로파일 버전, 대상 기능, 데이터·트래픽 조건, 측정 환경, 측정 시간·표본 수, 근거 자료, 중요한 가정, 미검증 범위를 연결해야 한다.

비용 결과는 고객 배포 프로파일과 가격표 버전을 추가로 연결한다. 추천 결과는 기준 구성, 변경 내용, 비교 실행, 효과와 비용 변화, 적용 제약, 재검증 방법을 연결한다.

### 5.2 판정과 작업 상태 구분

| 판정 | 의미 |
|---|---|
| 기준 충족 | 유효한 실험에서 적용한 기준 충족 |
| 기준 미충족 | 유효한 실험에서 적용 기준 초과 |
| 탐색 결과 | 사업 목표 또는 적합한 평가 기준이 없어 측정·곡선 중심 제공 |
| 부분 검증 | 일부 기능·조건만 실험함 |
| 판정 보류 | 실험 유효성 또는 근거 부족 |
| 미검증 | 해당 실험을 수행하지 않음 |

작업 완료·실패·취소·시간 초과는 위 판정과 별개의 실행 상태다. 시스템 오류로 작업이 실패했다고 고객 서비스가 기준 미충족인 것은 아니다. 전체 보고서는 기능별 상태를 종합하며 미검증 항목을 통과로 승격하지 않는다.

### 5.3 지표 해석

- p90·p95·p99는 응답 지연 분포이며 적정 목표 자체가 아니다.
- 관측값, 목표값, 확장 기준, 경보 기준, 자원 제한을 구분한다.
- 요청 성공과 업무상 정상 처리의 범위를 명시한다.
- 자원 사용률에는 분모와 측정 구간을 표시한다.
- 표본 부족·반복 변동·부하 누락의 유효성 규칙은 버전별 정책으로 관리한다.
- 인스턴스 또는 반복 실행의 percentile을 단순 평균하지 않는다.
- 단기 실험을 월간 가용성이나 운영 환경 전체의 보장으로 표현하지 않는다.

## 6. 핵심 사용자 흐름

1. 사용자가 프로젝트 소스와 자연어 트래픽을 제출한다.
2. 플랫폼이 코드 버전과 실행을 식별하고 지원 범위를 판정한다.
3. 코드·트래픽에서 확인한 정보와 가정으로 실험 계획 및 비용용 구성을 작성한다.
4. 고객 월 운영 비용 초안 또는 산정 제한 사유를 먼저 제공한다.
5. 격리된 고객 서비스 실행과 데이터 준비를 완료하고 기본 동작을 확인한다.
6. 조건을 충족하는 핵심 런북을 실행하고 유효한 측정 자료를 수집한다.
7. 제한된 구성 후보를 비교하고 추천 후보를 재검증한다.
8. 성능·비용·가정·미검증 범위와 다음 행동을 제공한다.
9. 결과를 보존하고 실험 소유 자원의 정리 상태를 확인한다.
10. 사용자는 조건을 선택적으로 보정하거나 같은 조건의 새 실행을 요청한다.

P1 런북은 구현 및 프로젝트 선행 조건을 만족할 때 삽입한다. 추가 입력이 없으면 가능한 범위에서 실행하고, 재현 불가능한 조건을 임의의 성공으로 대체하지 않는다.

## 7. Implementation Decisions — 제품 책임과 고정 경계

이 절은 기술 구현안이 아니라 향후 설계가 보존해야 할 책임 경계다. 신규 언어·프레임워크·저장 기술·실험 도구·메시징·AI 공급자는 결정하지 않는다.

### 7.1 고정 기반

- 플랫폼은 현재 저장소의 GCP·OpenStack·Kubernetes 구축 결과 위에서 운영한다.
- 기존 인프라를 대체하는 신규 플랫폼 구축이나 이관은 요구하지 않는다.
- 현재 계층별 검증, 관리 경로, persistent foundation 보호 원칙을 보존한다.
- 실제 성능 실험·자동 축소·고객 실행 분리는 기존 증설 검증과 별도의 제품 요구사항이다.
- 기반 변경이 기존 ADR과 충돌하면 별도 설계와 ADR에서 변경 관계를 기록한다.

### 7.2 논리적 책임과 입출력

| 책임 | 입력 | 출력·보장 |
|---|---|---|
| 접수·분석 | 소스, 트래픽 설명 | 지원 여부, 코드·구성 사실, 가정 |
| 계획 | 분석 결과, 운영 정책 | 시나리오·데이터 조건·런북·비교 후보·상한 |
| 실행 | 고정된 계획과 실행 소유 범위 | 실행 상태, 대상 식별, 단계별 자료 |
| 관측·유효성 | 측정 자료와 환경 상태 | 유효·무효 근거, 누락·표본·포화 정보 |
| 평가·추천 | 유효한 측정과 평가 기준 | 판정, 원인 가설, 검증된 후보, 다음 행동 |
| 비용 산정 | 고객 구성, 사용량 가정, 가격표 | 초안·보완 견적, 항목별 근거와 미산정 |
| 결과·이력 | 실행·판정·비용 | 근거를 추적할 수 있는 보고서와 비교 |
| 수명주기 | 실행 소유 자원, 보존 정책 | 취소·재개·정리·삭제 상태 |

각 책임은 도구 교체와 무관하게 동일 조건에서 검증 가능해야 한다. 배포 단위의 개수나 MSA 분리는 이 표로 결정하지 않는다.

### 7.3 정보 계약

프로젝트, 코드 버전, 분석 실행, 가정 집합, 시나리오, 런북 버전, 배포 구성, 관측 자료, 판정, 추천, 가격표, 견적, 자료 보존·정리 상태를 식별한다. 실험 조건과 결과의 연결은 변경 불가능한 실행 기록으로 남기고, 수정은 새 기록으로 관리한다. 물리 스키마와 API 형식은 추후 설계한다.

### 7.4 비용과 실행 환경의 분리

실행 기반이 고정되어 있다는 사실은 고객에게 같은 운영 구성을 권장한다는 뜻이 아니다. 고객 비용용 배포 프로파일은 별도로 선택·버전 관리한다. 비용 추정을 위해 고객 클라우드 인증을 첫 입력에 추가하지 않는다. 운영 환경별 성능 보정이 없으면 자원·가격 대응과 실제 처리 용량의 동등성을 분리해 설명한다.

## 9. Testing Decisions — 검증 계획

테스트는 내부 함수 구조가 아니라 외부에서 확인 가능한 결과와 권한·수명주기 경계를 검증한다. 실제 외부 코드 수용 전까지 현재 기반 위에서 대표 프로젝트와 의도된 실패 사례를 사용한다.

| 검증 영역 | 대표 사례 | 기대 결과 | 관련 요구사항 |
|---|---|---|---|
| 접수·지원 | 유효 소스, 잘못된 파일, 지원 불가 의존성 | 정확한 지원 판정과 이유, 미실행 자원을 실행한 것으로 표시하지 않음 | FR-01~03 |
| 트래픽·가정 | RPS, 동시 사용자, 방문자 수, 불명확한 설명 | 명시값 보존, 변환 근거 공개, 부족한 목표는 탐색으로 분류 | FR-04~05 |
| 시나리오 | 인증 실패, 데이터 미준비, 외부 의존성 대체 | 무효 요청으로 성능 통과 판정하지 않음 | FR-06~07 |
| 비용 | 구성 존재·부재, 누락된 전송량, 가격표 변경 | 산정 근거 보존, 미산정과 0 구분, 같은 조건 비교 | FR-08~12 |
| 기본 성능 | 정상 처리, 지연 증가, 오류 증가 | 적용 기준에 맞는 기능별 판정 | FR-13~16 |
| 실험 유효성 | 생성기 포화, 기반 포화, 표본 부족, 큰 변동 | 용량 부족을 고객 서비스 문제로 확정하지 않고 보류 | FR-17 |
| 병목 | 의도된 CPU 병목, DB 대기, 관측 지표 부재 | 관측·가설 분리, 지표 부재 시 인과 확정 금지 | FR-18 |
| 후보·추천 | 효과 있는 변경, 개선 없는 변경, 조건 불일치 | 같은 조건에서만 검증된 추천, 무효 비교 제외 | FR-19~20 |
| 보고서 | 일부 런북 미실행, 실패·취소된 작업 | 9개 결과 영역의 상태와 근거 보존 | FR-21~22 |
| 확장·복구 | 늦은 확장, 축소 중 오류, 재시작, 지속 부하 | 확장 여부와 품질 충족을 별도 판정 | FR-23~25 |
| 작업 제어 | 취소, 시간 초과, 실행기 재시작, 정리 실패 | 중복 실행 방지, 부분 결과 보존, 정리 실패 노출 | FR-26~29 |
| 접근·보존 | 고객 간 조회, 관리 자격 접근, 자료 삭제 요청 | 접근 거부와 삭제 범위·상태 확인 | FR-30~31 |

현재 레포의 plan 범위 검사, 출력 비밀 값 제거, 실행 경로와 inventory 테스트는 기반 검증의 선례다. 이 테스트들의 통과를 제품 성능·고객 격리·결과 신뢰도 검증으로 대체하지 않는다. 기반 실행 경로를 변경하면 기존 정적 검사와 ADR의 계층별 검증도 적용한다.

## 10. 출시 수용 기준

핵심 MVP의 외부 베타 수용에는 다음 조건이 모두 필요하다.

- [ ] 지원 범위와 지원 불가 사유가 사용자에게 공개되어 있다.
- [ ] 지원 프로젝트가 코드와 트래픽만으로 접수부터 유효한 핵심 결과까지 진행한다.
- [ ] 전체 성능 실험 완료 전에 고객 운영 비용 초안 또는 산정 제한 사유를 제공한다.
- [ ] 비용에 가격 근거·가정·포함 범위·미산정 항목이 표시된다.
- [ ] 사용자 수를 요청량으로 변환할 때 가정과 단위를 보존한다.
- [ ] 정상 동작을 검증하지 못한 기능을 전체 서비스 통과 근거로 사용하지 않는다.
- [ ] 기본 부하·단계 증가·구성 비교의 측정 조건과 원본 근거를 보존한다.
- [ ] 생성기·기반 포화 등 무효 실험을 통과로 판정하지 않는다.
- [ ] 검증된 추천에는 비교와 반복 실행의 근거가 있다.
- [ ] 9개 결과 영역에 실제 검증 상태를 표시하며 미실행 확장·복구를 통과로 표시하지 않는다.
- [ ] 고객 간 데이터 접근과 제출 코드의 관리 권한 접근을 차단한다.
- [ ] 취소·시간 초과·실행 재시도·정리 실패를 검증했다.
- [ ] 소스·자료 보존 기간과 실행 상한이 설정되어 있고 사용자에게 안내된다.
- [ ] 실행 자원 정리가 기존 persistent foundation을 대상으로 하지 않는다.
- [ ] 제품의 대표 흐름이 현재 레포의 구축 결과 위에서 실행되는 것을 확인했다.
- [ ] 적용한 기본 평가 기준이 고객의 사업 목표나 운영 보장으로 표현되지 않는다.

P1 출시에는 R-06~R-09의 조건부 실행, 결과 판정과 실패·중단 경로 검증을 추가한다. 체크리스트는 향후 검증할 항목이며 현재 완료했다는 의미가 아니다.

## 11. 제품 성과 측정

| 지표 | 측정 기준 |
|---|---|
| 전체 제출 지원 비율 | 유효한 제출 중 지원 판정된 비율 |
| 지원 프로젝트 자동 완료율 | 지원 판정된 제출 중 수작업·추가 필수 입력 없이 유효한 핵심 결과를 얻은 비율 |
| 수작업 개입 | 실행당 운영자의 개입 횟수·시간 |
| 결과 도달 시간 | 비용 초안과 핵심 결과까지 각각 측정, 큐 대기·준비·실험 시간 분리 |
| 판정 신뢰도 | 의도된 정상·병목·실패·무효 실험의 기대 판정과 비교 |
| 추천 검증 결과 | 재실험의 개선·미개선·부작용·불확실성을 모두 집계 |
| 결과 활용과 재사용 | 사용자 다음 행동 선택, 다음 코드 버전·트래픽 변경 시 재실행 |

구체적인 사업 목표값과 일정은 베타 근거 없이 확정하지 않는다. 수용 기준과 사업 지표를 구분해, 반복 사용이 적다는 이유로 판정 정확성을 낮추지 않는다.

## 12. Out of Scope — 제외 범위

- 신규 제품 기술 스택과 최초 고객 코드 지원 언어·DB 제품 선택
- 현재 레포의 실행 기반 교체 또는 다른 인프라로 이관
- MSA, 무제한 외부 의존성, 모든 프로젝트의 자동 실행
- 보안 취약점 분석과 모의 해킹 제품 기능
- 고객 운영 환경 직접 변경·배포·부하 테스트
- AI의 자율적인 운영 변경과 자동 코드 수정
- 사업상 SLO 자동 확정, 운영 가용성·처리량·정확한 청구액 보장
- 여러 클라우드 동시 최적화, 복잡한 과금·마켓플레이스·플러그인 시스템
- 핵심 MVP 단계의 미구현 P1 런북에 대한 검증 완료 주장

## 13. Further Notes — 후속 결정과 변경 관리

| 후속 결정 | 시점 | 결정 원칙 |
|---|---|---|
| 신규 제품 기술 스택 | 기술 설계 단계 | 현재 레포의 기반 위에서 제품 요구사항 충족 |
| 최초 고객 코드·DB 지원 범위 | 자동 실행 검증 전 | 적은 범위에서 빌드·데이터·시나리오 재현 가능 |
| 고객 비용용 배포 프로파일 | 비용 기능 검증 전 | 실험 기반과 구분, 가격·가정 설명 가능 |
| 평가 기준과 표본·변동 정책 | 기준 실험 검증 전 | 적용 대상 명시, 오판 방지, 버전 관리 |
| 런북 시간·비교 후보·부하 상한 | 외부 실행 전 | 기반 용량과 실험 신뢰도 안에서 제한 |
| 보존·삭제 기간 | 외부 코드 접수 전 | 고객 안내, 재현·증거와 자원 수명주기 구분 |
| 기존 ADR 변경 필요 여부 | 기반 정책 변경 전 | 현재 결정 유지 또는 새 ADR로 대체 관계 명시 |
| 상용 요금과 사업 목표 | 베타 결과 확보 후 | 고객 가치·자동화 수준·지속 사용 근거 |

사용자가 합의한 필수 입력 두 가지와 기존 레포 기반 고정은 후속 설계에서 임의로 변경하지 않는다. 이 문서와 기획서의 방향이 달라지면 제품 의도는 기획서에서, 구현 수용 조건은 PRD에서 함께 수정한다. 문서 작성은 기술 스택 선택이나 구현 착수의 승인으로 해석하지 않는다.
