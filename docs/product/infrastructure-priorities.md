# OpenStack–Kubernetes 기반 작업 우선순위

- 작성일: 2026-09-23
- 목적: 고객 코드의 성능·비용·장애 시나리오를 구체화하고 실행하기 위해 필요한 기반 작업을 함께 검토한다.
- 기준: 앞서 논의한 1~14번 작업과 우선순위를 유지하고, 1·2번 구현 후 상태를 반영했다.
- 상태 근거: 현재 저장소 `ae4c641`, 2026-09-11 실환경 검증 및 2026-09-13 코드·실행 증거 재검토. 이 문서 작성 시 실환경을 다시 기동하거나 검증하지 않았다.
- 관련 문서: [기획서](plan.md), [PRD](prd.md), [자동 증감 검증 결과](../worker-autoscaling-validation.md), [ADR-0016](../adr/0016-separate-observation-and-enable-worker-scale-in.md), [기존 후속 항목](infrastructure-follow-ups.md)

## 읽는 기준

여기서 1·2·3순위는 **인프라 구현 순서**다. PRD의 제품 요구사항 P0/P1과는 별개다. 2·3순위라도 해당 실험이나 외부 고객 코드 수용의 선행 조건이면 먼저 완료해야 한다. 모든 항목이 끝나야 시나리오 작성을 시작할 수 있다는 뜻은 아니다.

`완료`는 명시한 범위에서 구현과 검증을 마친 상태, `부분 완료`는 일부 기반만 구현·확인된 상태, `미착수`는 이 목록의 완료 기준에 맞춘 작업이 남은 상태다. `조건부` 항목은 지원할 실험 범위를 정한 뒤 착수 여부를 결정한다. 기존 도구나 스크립트가 있다는 사실만으로 전체 항목을 완료 처리하지 않는다.

## 고정된 인프라 범위

| 구분 | 범위 |
|---|---|
| GCP OpenStack controller 호스트 | 1대 고정. OpenStack 관리 서비스와 management Kubernetes(kind), CAPI/CAPO, CA 실행 |
| GCP OpenStack compute 호스트 | 2대 고정. 현재 각각 4 vCPU·16 GiB |
| workload Kubernetes control plane | Nova VM 1대 고정 |
| workload Kubernetes worker | **Nova VM 최소 1대~최대 3대**, CA min=1/max=3 |
| workload Kubernetes용 Nova VM 총합 | **2~4대**. control plane과 worker 모두 compute 호스트 자원 사용 |

worker 증감의 단위는 OpenStack Nova VM이다. GCP compute 호스트 자동 증감은 범위에 포함하지 않는다. 현재 control plane·worker flavor는 각각 2 vCPU·2 GiB·20 GB다. worker 3대는 기능 검증을 통과한 상한이며, 실제 고객 부하를 감당할 성능 여유까지 검증한 값은 아니다.

## 1순위 — 바로 진행할 핵심 기반 작업

| 번호 | 작업 | 현재 상태 | 필요한 작업과 이유 | 완료 기준 |
|---|---|---|---|---|
| 1 | **환경 준비와 상태 검사 분리** | **완료** | `prepare`에서 의도한 설정 적용, `status/verify`에서 조회, `probe`에서 임시 Pod를 통한 통신 검사로 분리했다. 상태 확인이 실험 조건을 바꾸거나 장애를 숨기지 않도록 한다. | 조회 시 관리 대상 설정 변경·시험 Pod 생성 없음. 준비 중·불일치·조회 불가·시간 초과 구분. 별도 API·노드별 CNI/DNS 검사 가능 |
| 2 | **자동 증감 범위 확대·scale-in 추가** | **완료** | worker 1~3대 범위와 자동 축소 정책을 적용했다. 부하 감소 후 자원을 회수하고 다음 실행에서 다시 확장할 수 있도록 한다. | 자동 `1→2→3→2→1→2→1` 통과. 삭제 대상 Machine·Node·Nova VM·포트 회수와 control plane·공유 자원 보존 확인 |
| 3 | **수동·자동 제어 충돌 방지** | **부분 완료** | 수동 증감 시 CA 중지·원래 replica 수 복원, 같은 운영 클라이언트에서 수동 증감·자동 시험·정리 간 파일 잠금은 구현됐다. 고정 구성/자동 증감 모드, 향후 복구 작업과의 제어권, 실행기 중단 후 실제 상태 대조·복원을 정리해야 한다. | 지원하는 제어 경로들이 중복 변경하지 않음. 중단·재시도 후 제어 상태 복원. 여러 운영 클라이언트를 지원한다면 클라이언트 간 충돌도 방지 |
| 4 | **상시 모니터링·로그 수집** | **부분 완료 — [GCP 배포·정상 수집 실측](../../observability/live-validation-2026-09-24.md), 증감·장애 수용 시험 남음** | compute·Nova VM·Node·Pod·CA/CAPI 지표와 로그를 실행 ID·시간·자원 식별자로 연결한다. 고객 앱의 한계와 기반 인프라 포화를 구분하고 장애 전후를 추적하는 데 필요하다. | 정상·증감·실패 구간의 지표와 로그 조회 가능. CPU·메모리·디스크·네트워크 압박 및 자료 누락을 식별하고 보존 범위 명시 |
| 5 | **실행 자원 수명주기 관리** | **부분 완료** | 실행별 결과 디렉터리, 시험 자원 소유 label·UID, 단계별 제한 시간, 증거 보존 후 정리는 구현됐다. 전체 실행 상태, 취소, 재시도·재개, 전체 시간/자원 상한, 보존·정리 정책을 연결해야 한다. | 중간 실패·취소·재시작 후 실제 자원을 대조하여 중복 실행 방지. 소유 자원만 정리하고 정리 실패를 별도 기록. 다음 실행 준비 가능 |

1·2번의 완료에는 고객 HTTP 요청 연속성, 실제 CPU 사용량에 따른 성능 평가, worker 장애 자동 복구가 포함되지 않는다. PDB·배치 제약·local storage 등으로 축소가 막히는 사례와 수동 작업 중단·실패는 실환경에 의도적으로 주입하지 않았으며, 검증 범위는 [검증 문서](../worker-autoscaling-validation.md)를 따른다.

## 2순위 — 고객 Pod 테스트를 시작하기 전에 준비할 작업

| 번호 | 작업 | 현재 상태 | 필요한 작업과 이유 | 완료 기준·필요한 시점 |
|---|---|---|---|---|
| 6 | **기반 용량·VM 배치 확인** | **부분 완료** | worker 3대의 실제 배치와 자원 할당은 확인했다. 실제 부하에서 compute별 CPU·메모리·디스크·네트워크 압박 및 부하 생성기와의 자원 경쟁을 측정해야 한다. 필요 시 근거를 바탕으로 compute 사양 조정을 검토한다. | 고객 성능 판정 전, 기반 포화로 실험이 무효가 되는 조건과 시험 가능한 범위 확인. VM 생성 성공만으로 성능 여유를 주장하지 않음 |
| 7 | **고객 실행 자원 제한·격리** | **미착수** | CPU·메모리·임시 저장소 상한, namespace·권한·네트워크 정책, 관리 영역 접근 차단을 설계·검증한다. 고객 코드의 과소비나 오작동이 플랫폼과 다른 실행으로 번지지 않도록 한다. | **외부 코드 수용 전 필수.** 자원 상한 초과와 관리 자격 증명·서비스·다른 고객 자원 접근이 제한되는지 검증. namespace 분리만으로 완료 처리하지 않음 |
| 8 | **worker 복구 기반** | **미착수** | worker 상태 감지, kubelet 복구·Machine 교체 중 적용할 경로, 복구 재시도 상한과 CA 충돌 방지를 준비한다. 구체적인 장애별 복구 조건은 시나리오에서 정한다. | worker 장애 시험 전, 감지→복구 또는 교체→Ready·통신 회복 경로와 실패 시 중단·증거 보존 확인. 복구 도구 채택은 별도 결정 |
| 9 | **고객 앱 통신 경로** | **미착수** | Service와 실험용 Ingress 경로를 준비하고 앱 직접 요청과 Ingress 경유 요청을 구분한다. 앱·네트워크·진입 계층 중 어디서 실패하는지 판단할 기반이다. | HTTP·Ingress 시험 전, 부하 생성 위치와 접근 경로 확정. 양쪽 경로의 정상 응답·오류·지연 관측 및 실험 자원 정리 가능 |
| 10 | **Pod 증감·종료 기반** | **미착수** | HPA용 메트릭, requests/limits, 건강 검사, 종료 유예·SIGTERM 처리, PDB 적용 구조를 준비한다. Pod 증감과 worker 증감의 효과를 구분한다. | 앱 확장·축소 시험 전, Pod 증감 및 종료 동작 관측 가능. 요청 처리 중 축소 영향과 축소 차단 사유를 측정할 수 있음 |

## 3순위 — 실험 지원 범위에 맞춰 추가할 작업

| 번호 | 작업 | 현재 상태 | 필요한 작업과 이유 | 완료 기준·착수 조건 |
|---|---|---|---|---|
| 11 | **DB·테스트 데이터 초기화** | **조건부·미착수** | 같은 데이터를 반복 준비하고 실행 후 제거·복원하는 절차를 만든다. 실행마다 데이터 조건이 달라져 비교가 왜곡되는 것을 방지한다. | DB를 사용하는 고객 코드 실험 전에 필요. 초기 데이터 식별, 준비 성공 확인, 재실행 시 동일 기준 복원 |
| 12 | **지속 저장소·볼륨 복구** | **조건부·미착수** | worker 교체 후에도 데이터 보존이 필요한 경우 저장소와 재연결·복구 경로를 준비한다. Cinder/CSI 등은 요구사항에 따라 검토하며 현재 채택 결정은 아니다. | 데이터 보존을 요구하는 장애 실험 전에 필요. 교체 후 데이터 접근·보존 확인과 복구 실패 증거 확보 |
| 13 | **자원 구성 프로파일** | **미착수** | CPU·메모리·실행 개수·worker 사양 후보를 식별하고 동일 조건으로 적용·복원한다. 구성별 성능과 고객 운영 비용을 비교할 기반이다. | 구성 비교 실험 전, 프로파일 버전과 적용 결과·차이·복원 기록 확보. 고객 비용용 배포 프로파일과 실험 기반 비용 구분 |
| 14 | **장시간 운영 정책** | **부분 완료 — 호스트 자동 STOP만 있음** | 현재 10시간 자동 STOP을 고려해 신규 단계 착수 제한, 실행 시간 상한, 증거 반출·정리 시간을 배분한다. 실행 도중 기반 종료로 결과와 자원이 방치되는 것을 방지한다. | 장시간 시험 전, 남은 운영 시간에 따른 시작·중단 판단과 증거 보존·정리 가능. STOP 전 완료하지 못한 정리의 상태와 재개 방법 기록 |

## 다음 논의의 기준

1. 1·2번은 완료 상태로 유지하고, **3번의 제어권·중단 복원 범위와 5번의 실행 상태·재개 범위**를 함께 정한다. 현재 파일 잠금과 소유 자원 정리를 출발점으로 삼는다.
2. 4번에서 수집할 최소 지표·로그를 정하고, 이를 이용해 6번의 실제 용량과 실험 유효성을 확인한다.
3. 첫 고객 Pod 실험의 범위를 정해 7·9·10번의 선행 조건을 준비한다. worker 장애를 시험한다면 8번, DB·데이터 보존을 시험한다면 11·12번을 먼저 준비한다.

이 순서는 논의를 위한 기준이며 구현 도구나 수치 정책을 확정하지 않는다. 전체 HA, 대규모 저장소, 다중 고객 동시 실행은 필요성이 확인될 때 범위를 정한다. 이후 논의에서 범위나 순서를 바꾸더라도 작업 번호는 유지해 결정과 진행 상태를 추적한다.
