- 관련 문서: [기획서](plan.md), [PRD](prd.md), [자동 증감 검증 결과](../worker-autoscaling-validation.md), [ADR-0016](../adr/0016-separate-observation-and-enable-worker-scale-in.md), [기존 후속 항목](infrastructure-follow-ups.md)

## 읽는 기준

여기서 1·2·3순위는 **인프라 구현 순서**다. PRD의 제품 요구사항 P0/P1과는 별개다. 2·3순위라도 해당 실험이나 외부 고객 코드 수용의 선행 조건이면 먼저 완료해야 한다. 모든 항목이 끝나야 시나리오 작성을 시작할 수 있다는 뜻은 아니다.

`완료`는 명시한 범위에서 구현과 검증을 마친 상태, `부분 완료`는 일부 기반만 구현·확인된 상태, `미착수`는 이 목록의 완료 기준에 맞춘 작업이 남은 상태다. `조건부` 항목은 지원할 실험 범위를 정한 뒤 착수 여부를 결정한다. 기존 도구나 스크립트가 있다는 사실만으로 전체 항목을 완료 처리하지 않는다.

## 고정된 인프라 범위

| 구분 | 범위 |
|---|---|
| GCP OpenStack controller 호스트 | 1대 고정. OpenStack 관리 서비스와 management Kubernetes(kind), CAPI/CAPO, CA 실행 |
| GCP OpenStack compute 호스트 | 2대 고정. 현재 각각 4 vCPU·16 GiB |
| workload Kubernetes control plane | Nova VM 1대 고정 |
| workload Kubernetes worker | **Nova VM 최소 1대~최대 3대**, CA min=1/max=3 |
| workload Kubernetes용 Nova VM 총합 | **2~4대**. control plane과 worker 모두 compute 호스트 자원 사용 |

worker 증감의 단위는 OpenStack Nova VM이다. GCP compute 호스트 자동 증감은 범위에 포함하지 않는다. 현재 control plane·worker flavor는 각각 2 vCPU·2 GiB·20 GB다. worker 3대는 기능 검증을 통과한 상한이며, 실제 고객 부하를 감당할 성능 여유까지 검증한 값은 아니다.

## 1순위 — 바로 진행할 핵심 기반 작업

| 번호 | 작업 | 현재 상태 | 필요한 작업과 이유 | 완료 기준 |
|---|---|---|---|---|
| 1 | **환경 준비와 상태 검사 분리** | **완료** | `prepare`에서 의도한 설정 적용, `status/verify`에서 조회, `probe`에서 임시 Pod를 통한 통신 검사로 분리했다. 상태 확인이 실험 조건을 바꾸거나 장애를 숨기지 않도록 한다. | 조회 시 관리 대상 설정 변경·시험 Pod 생성 없음. 준비 중·불일치·조회 불가·시간 초과 구분. 별도 API·노드별 CNI/DNS 검사 가능 |
| 2 | **자동 증감 범위 확대·scale-in 추가** | **완료** | worker 1~3대 범위와 자동 축소 정책을 적용했다. 부하 감소 후 자원을 회수하고 다음 실행에서 다시 확장할 수 있도록 한다. | 자동 `1→2→3→2→1→2→1` 통과. 삭제 대상 Machine·Node·Nova VM·포트 회수와 control plane·공유 자원 보존 확인 |
| 3 | **수동·자동 제어 충돌 방지** | **완료 — 단일 운영 클라이언트의 지원 경로** | 수동 실패 시 CA 중지·journal 유지, 수렴 확인 후 복구, auto/fixed 모드, 같은 운영 클라이언트의 파일 잠금을 검증했다. 하위 변경 명령도 잠금 수명에 포함하며 실제 create 중 SIGKILL·재개를 확인했다. 향후 worker 장애 복구 경로의 제어권과 다중 클라이언트 지원은 별도다. | 지원하는 제어 경로들이 중복 변경하지 않음. 중단·재시도 후 제어 상태 복원. 여러 운영 클라이언트를 지원한다면 클라이언트 간 충돌도 방지 |
| 4 | **상시 모니터링·로그 수집** | **완료 — GCP 지표·로그·UID 추적의 내부 시험 범위** | 호스트·Nova VM·Node·Pod 및 CA/CAPI의 Pod 상태·Events·로그를 수집한다. 최종 구성의 정상 30분, 전체 증감, Pod 반복 실패·삭제 후 추적, 개별 수집기·gateway 중단과 복귀를 검증했다. 대상별 공백과 전송 손실을 별도로 판정하고 보존 범위를 명시했다. [종합 검증](../foundation-priority1-final-validation-2026-09-24.md) | 정상·증감·실패 구간의 지표와 로그 조회 가능. CPU·메모리·디스크·네트워크 압박 및 자료 누락을 식별하고 보존 범위 명시 |
| 5 | **실행 자원 수명주기 관리** | **완료 — 단일 운영 클라이언트의 자동 증감 시험 범위** | 내구 실행 상태, 취소, SIGKILL 후 실제 자원 대조, 소유 자원 정리 후 전체 재측정, 전체 시간·자원 상한과 보존 정책을 연결했다. 실환경에서 시간 초과·취소·정리 중단·강제 종료 후 재개를 확인했다. [최초 검증](../run-lifecycle-validation-2026-09-24.md) 이후 변경 명령 격리 수정과 [종합 검증](../foundation-priority1-final-validation-2026-09-24.md)의 전체 재개 시험을 추가했다. 고객 코드·분산 실행 관리는 별도다. | 중간 실패·취소·재시작 후 실제 자원을 대조하여 중복 실행 방지. 소유 자원만 정리하고 정리 실패를 별도 기록. 다음 실행 준비 가능 |

4번의 완료는 현재 GCP 기반 신호 수집·조회 계약에 한정한다. CAPI/CA 내부 reconcile 메트릭과 Grafana 대시보드, 장애 자동 탐지·복구 모듈의 구현 완료를 뜻하지 않는다.

1·2번의 완료에는 고객 HTTP 요청 연속성, 실제 CPU 사용량에 따른 성능 평가, worker 장애 자동 복구가 포함되지 않는다. PDB·배치 제약·local storage 등으로 축소가 막히는 시나리오는 별도 검증이 필요하다. 수동 실패·명시적 복구·fixed/auto 전환과 실행 중단 검증은 [최신 기록](../foundation-priority1-final-validation-2026-09-24.md), 기존 자동 증감 범위는 [검증 문서](../worker-autoscaling-validation.md)를 따른다.

## 다음 논의의 기준

1. 1~5번은 표에 명시한 단일 클라이언트·GCP 내부 시험 범위에서 완료 상태로 유지한다. 향후 worker 복구 제어권은 8번과 함께 정하고, 고객 실행·다중 클라이언트로 확장할 때 제어 및 수명주기 범위를 다시 검토한다.
2. 4번에서 검증한 지표·로그를 이용해 6번의 실제 용량과 실험 유효성을 확인한다. 고객 부하에서의 성능 여유와 수집 비용·부하는 추가 측정한다.
3. 첫 고객 Pod 실험의 범위를 정해 7·9·10번의 선행 조건을 준비한다. worker 장애를 시험한다면 8번, DB·데이터 보존을 시험한다면 11·12번을 먼저 준비한다.

이 순서는 논의를 위한 기준이며 구현 도구나 수치 정책을 확정하지 않는다. 전체 HA, 대규모 저장소, 다중 고객 동시 실행은 필요성이 확인될 때 범위를 정한다. 이후 논의에서 범위나 순서를 바꾸더라도 작업 번호는 유지해 결정과 진행 상태를 추적한다.
