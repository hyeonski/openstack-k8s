## 1. 전제와 우선순위

### 1.1 최종보고서 양식의 제약

- 전체 30쪽 내외: 서론 6, 관련연구 7, 제안 작품 7, 구현 및 결과분석 7, 결론 및 소감 2, 참고문헌 1쪽.
  관련연구에는 국문 3편 이상, 영문 3편 이상이 필요하다.
- 결과분석은 7쪽이다. 모든 분석을 본문에 넣을 수 없으므로 RQ별 핵심 표·그림만 본문에 두고, 나머지는 부록에 둔다.
- 배점의 상세설계(30)는 "계획에 명시된 바대로 결과물과 일치하는가"를 본다.
  신청서의 수동·자동 비교 약속에 대응하는 H1의 가치가 크다.
- 그림은 직접 그리고, 표는 위·그림은 아래에 캡션을 단다. 원천코드는 부록에 포함한다.

### 1.2 우선순위

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | 최종보고서 작성 | 제출물 자체. A단계 결과만으로도 결과분석 장을 구성할 수 있다 |
| 2 | H1 S1 사람 런북 3회 | 신청서·중간보고서가 약속한 수동·자동 비교. 상세설계 배점과 직결 |
| 3 | A2 같은 worker 재시작 4회 | RQ2(다른 compute로 옮긴 것이 효과의 원인)의 핵심 대조군 |
| 4 | V1·V2 음성 조건 각 3회 | RQ4 특이도. 예비 실행에서 조건이 성립하지 않을 위험이 있다 |
| 5 | S3 기본 동작 관측 1회 | RQ1 S3 공백. 문서 근거로 대체할 수 있다 |
| 제외 | V3~V5, A3 replay, RQ6 민감도 | 3절 |

S1 자동 4회는 A2와 H1의 공통 비교군으로 함께 쓴다. B단계와 H1을 하나의 새 캠페인으로 묶어 환경 기동과 정리를 줄인다.

## 2. C단계 — H1 S1 사람 런북 세부

[두 축 계획](two-axis-evaluation-plan-2026-10-24.md) 3·4절의 계약을 따른다. 아래는 이 일정에 맞춰 확정한 값이다.

### 2.1 확정 사항

| 항목 | 값 |
|---|---|
| 운영자 | 작품 개발자 본인 1명 |
| 본시험 횟수 | 수동 3회. 비교군은 같은 캠페인의 S1 자동 4회 |
| 연습 | 본시험 전 1회. 결과는 별도 기록하고 본시험에 합산하지 않음 |
| 장애 조건 | 기존 S1 자동과 같음(4 vCPU 경쟁 VM, 5 RPS, 요청당 100,000 round, 1,080초) |
| 증상 통보 | 공통 요청 관측에서 60초 창 p95가 기준선의 1.5배를 넘으면 실행기가 터미널 알림과 `symptom_notice_at`을 기록. 원인·목적지는 알리지 않음 |
| 허용 도구 | `kubectl`, `openstack` CLI, 호스트 지표 조회 스크립트(`scripts/host-stat.sh`), 공통 변경 도구 |
| 공통 변경 도구 | 운영자가 지정한 노드로 `nodeSelector`를 바꾸는 단일 명령. uid·resourceVersion 조건과 cooldown 기록은 자동과 같다. 목적지를 고르지는 않는다 |
| 운영자 기록 | 판단 확정, 완료 선언 시각을 기록하는 명령. 터미널 세션 전체를 시각과 함께 녹화해 조회·명령 수를 사후 집계 |
| 회복 판정 | 자동과 같음(배치 후 30초, 60초 창 3회 연속 안정). 운영자의 완료 선언과 별도로 판정 |
| 시간 제한 | 증상 통보 후 15분 안에 변경 명령이 없으면 `timeout`. 분모에 남김 |
| 순서 | 자동·A2·수동을 교대. 수동은 연속 배치하지 않음 |

### 2.2 측정 지표

| 지표 | 정의 |
|---|---|
| 증상 → 판단 | `symptom_notice_at` → 운영자 `decision_at` |
| 판단 → 변경 | `decision_at` → 공통 변경 도구 실행 |
| 변경 → 배치 준비 | 변경 → 새 Pod Ready |
| 배치 → 안정화 | 새 Pod Ready → 회복 판정 충족 |
| 총시간 | 증상 통보 → 회복 판정 충족 |
| 운영자 작업 | 녹화에서 센 조회 명령 수, 변경 명령 수, 정정 횟수 |
| 결과 | 정상 완료, 잘못된 목적지, 시간 초과, 측정 불완전 |

자동군의 대응 시각은 증상 통보와 같은 규칙으로 계산한 시각부터 잰다. 자동은 같은 시각에 진단을 이미 진행 중이므로,
비교는 "증상 확인 → 조치 시작"과 "총시간"을 중심으로 한다.

### 2.3 해석 경계

- 운영자가 시나리오와 정답을 알고 있다. 결과는 일반 운영자의 소요 시간이 아니라 **하한**으로 해석한다.
- 3:4 비교의 Mann–Whitney 최소 양측 p는 2/35≈0.057이다. 0.05에 도달할 수 없으므로 검정 대신 회차별 값과 구간별 분해를 제시한다.
- 고정 확인 구간(30초 + 180초)이 양쪽에 같이 들어가므로, 차이는 증상 → 변경 구간에 나타난다고 예상한다.

### 2.4 구현

| 작업 | 위치 |
|---|---|
| `manual` 모드: 진단을 하지 않고 증상 통보 후 운영자의 변경을 기다림 | `evaluation/graduation_evaluation_case.py`의 `EvaluationS1` |
| 공통 변경 도구와 운영자 기록 명령 | 같은 파일의 하위 명령과 `evaluation/commands.mk` 대상 |
| 독립 검증: 변경 1회, 목적지가 다른 compute인지, 회복 판정 재계산 | `evaluation/graduation_evaluation_verify.py` |
| 녹화 집계: 명령 수 계산 | 분석 스크립트 |

## 3. S3 기본 동작 관측과 범위 밖 항목

### 3.1 S3 기본 동작 관측 (순위 5, 시간이 남을 때만)

| 항목 | 내용 |
|---|---|
| 목적 | 펜싱 없이 Kubernetes 기본 동작만 둘 때 기존 DB가 계속 실행되는 동안 무슨 일이 일어나는지 관측(RQ1) |
| 방법 | 같은 장애를 주입하고, 펜싱·out-of-service를 하지 않은 채 10분 관측. controller-manager의 강제 분리 설정은 기본값으로 둔다 |
| 기록 | DB Pod 상태(Terminating 고착 여부), VolumeAttachment, Cinder 연결, 6분 강제 분리 발생 여부, 대체 Pod 기동 여부, 기존 컨테이너 생존 |
| 안전 | 시험 소유 DB만 사용한다. 강제 분리 후 이중 실행이 생기면 그 사실을 결과로 기록하고, 데이터 무결성은 주장하지 않는다. 정리는 기존 S3 cleanup을 따른다 |
| 생략 시 | 정의서 [R6]·[R8]과 3절 신호 표(VM ACTIVE·컨테이너 실행 중 10/10)로 논증하고, 미관측을 한계로 적는다 |

### 3.2 범위 밖으로 둘 항목

| 항목 | 결정 | 보고서 처리 |
