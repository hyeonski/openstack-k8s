# 평가 B단계 실행 계획 — S1 음성 조건과 같은 worker 재시작 대조군

> 2026-10-25: 범위·우선순위·일정은 [완전 평가 계획](complete-evaluation-plan-2026-10-25.md)이 대체한다. 이 문서의 조건 설계는 해당 실험 수행 시 참조한다.

작성일: 2026-10-25.
기준 구현: `74bd116`.
상태: 실행 계획. 평가 변형·검증 코드는 아직 구현하지 않았으며, 새 실환경 실행도 없다.
상위 설계: [평가 설계](evaluation-design-2026-10-25.md) 4.2절(A2)·4.4절(V1·V2), [두 축 계획](two-axis-evaluation-plan-2026-10-24.md) 6절.

## 1. 목적

| ID | 질문 | 연구 질문 | 현재 공백 |
|---|---|---|---|
| V1 | 원천 호스트의 CPU는 경합 수준이지만 서비스는 정상일 때 조치하지 않는가? | RQ4 특이도, RQ2(호스트 신호만으로 판단하지 않음) | 실환경 n=0 |
| V2 | 서비스는 느리지만 호스트 경합 근거가 없을 때 경합으로 단정하지 않는가? | RQ4 특이도, RQ2(서비스 신호만으로 판단하지 않음) | 실환경 n=0 |
| A2 | 같은 worker에서 재시작만 하면 회복되지 않는가? | RQ2(다른 compute로 옮기는 것이 효과의 원인) | 재배치 효과에 재시작·배치 변화가 섞여 있음 |

S1의 고유 기여는 서비스 영향과 호스트 경합을 **함께** 확인하는 판단이다. V1·V2는 둘 중 하나만 있을 때의 판단을 검증한다.
A2는 "다른 compute로 옮겨서 회복됐다"와 "Pod를 다시 띄워서 회복됐다"를 분리한다.

## 2. 고정 원칙

- 복구 정책·임계값(`graduation_s1_auto.py`의 `POLICY`, `diagnose`, `candidate_reasons`, `stable_window`)은 바꾸지 않는다.
  변형은 장애 조건을 만드는 시험 도구와 조치 단계의 대조군에만 둔다.
- 새 profile·새 freeze로 별도 캠페인을 만든다. 기존 캠페인 `graduation-evaluation-20261023T070441Z-30fdde87`의 원본·집계는 수정하지 않는다.
- 각 조건의 성립 여부를 원본으로 먼저 판정한다. 조건이 성립하지 않은 실행은 `condition_not_established`로 남기고,
  기대 판단의 분모에서는 제외한다. 실행 기록과 분모에서 지우지는 않는다.
- 예비 실행은 본시험과 별도로 기록하고, 본시험 결과에 합산하지 않는다.
  예비 실행으로 바꿀 수 있는 것은 조건을 만드는 시험 파라미터뿐이다. 정책 임계값은 바꾸지 않는다.
- 기대와 다른 결과(예: V2에서 재배치 발생)는 오조치로 기록하고 보고한다. 결과에 맞춰 정책이나 판정을 고치지 않는다.

## 3. 조건 설계

### 3.1 V1 — 호스트 CPU 경합, 서비스 정상

| 항목 | 내용 |
|---|---|
| 조건 생성 | 기존과 같은 4 vCPU 경쟁 VM을 원천 compute에 둔다. 서비스 요청을 가볍게 하여(요청당 연산 `rounds` 10,000, 앱 허용 최솟값) 호스트 경합이 서비스 지연으로 이어지지 않게 한다 |
| 성립 판정 | 진단 창에서 원천 호스트 CPU ≥70%이고 CPU PSI ≥ max(2%, 기준선×2). 동시에 p95 ≤ 기준선×1.5이고 실패가 기준선보다 늘지 않음 |
| 기대 판단 | 진단 미확정. 최대 6개 창 뒤 `deferred`(`sustained_service_and_host_evidence_missing`). 창별 사유에 `service_impact_not_confirmed`. 조치 0, Deployment 불변 |
| 위험과 대안 | 가벼운 요청에서도 CPU 경합이 지연을 1.5배 넘게 늘릴 수 있다. 예비 실행으로 먼저 확인한다. 성립하지 않으면 경쟁 VM의 부하 프로세스를 4→3개로 줄여 한 번 더 예비 실행한다. 그래도 성립하지 않으면 "이 테스트베드에서는 서비스에 무해한 CPU 경합을 재현하지 못했다"로 보고한다 |

### 3.2 V2 — 서비스 지연, 호스트 경합 없음

| 항목 | 내용 |
|---|---|
| 조건 생성 | 경쟁 VM 대신 같은 worker에 CPU 부하 Pod(시험 소유, `nodeName` 고정, 자원 제한 없음)를 띄운다. 같은 worker 안의 Pod 간 경쟁은 정의서 3.2절이 S1과 구분하라고 한 경우다 |
| 예상 신호 | worker VM(2 vCPU)이 포화되어 서비스 지연은 늘지만, 원천 호스트(4 vCPU) 사용률은 약 50% 수준으로 예상된다 |
| 성립 판정 | 진단 창에서 p95 > 기준선×1.5(또는 실패 증가). 원천 호스트 CPU <70% 또는 PSI가 기준 미만 |
| 기대 판단 | 진단 미확정, `deferred`. 창별 사유에 `host_contention_not_confirmed`. 조치 0, Deployment 불변 |
| 위험 | 호스트 CPU가 70%와 PSI 기준을 함께 넘으면 모듈이 재배치할 수 있다. 이는 조건 불성립이 아니라 실제로 관측된 판단이다. 오조치로 기록하고 원인(PSI 상승 경로)을 분석한다 |

### 3.3 A2 — 같은 worker 재시작 대조군

| 항목 | 내용 |
|---|---|
| 조건 | 기존 S1 자동과 같은 경쟁 VM·요청(`rounds` 100,000)과 같은 진단 |
| 대조 조치 | 진단 확정 후 다른 compute로 옮기는 대신, `nodeSelector`를 원천 worker로 고정한 채 rollout restart를 한 번 실행한다. 같은 JSON patch 조건(uid·resourceVersion)과 maxSurge 1·maxUnavailable 0을 유지한다 |
| 성립 판정 | 새 Pod UID가 원천 worker·원천 compute에 있음. 재시작 후에도 경쟁 VM이 ACTIVE이고 원천 호스트 경합이 지속됨 |
| 측정 | 자동과 같은 회복 판정(30초 대기, 60초 창 3회 연속 안정)과 마지막 60초 p95·기준선 비율 |
| 기대 결과 | 회복 판정 미충족(`recovery-needs-review`). 마지막 60초 p95가 무조치와 비슷한 수준 |
| 함께 실행 | 같은 캠페인에서 S1 자동을 교대로 실행한다. 같은 환경에서 재배치 효과가 재현되는지 확인하고, 두 조치를 직접 비교한다 |

## 4. 실행 규모와 순서

| 묶음 | 내용 | 횟수 | 1회 소요(기존 실측) |
|---|---|---:|---|
| 예비 | V1 1회, V2 1회 (본시험 제외) | 2 | 약 25~33분 |
| 본시험 V | V1 3회, V2 3회 | 6 | 약 25~33분 (진단 미확정으로 회복 관측 없음) |
| 본시험 A | A2와 S1 자동 교대 | 4 + 4 | 약 32분 |
| H1 (같은 캠페인) | S1 사람 런북. 비교군은 위 S1 자동 4회 | 연습 1 + 3 | 약 33분 |
| 합계 | | 20 | 약 10~11시간 + 환경 기동·정리 |

2026-10-25: A2·자동 각 4회로 확정했다. 마감 일정에 맞춰 H1을 같은 캠페인에 넣었다.
세션 구성과 축소 규칙은 [최종 평가 잔여 계획](final-plan-2026-10-25.md) 4·5절을 따른다.

- A2·자동을 각 4회로 정한 이유: 4:4 독립 비교의 Mann–Whitney 정확검정 최소 양측 p는 2/70≈0.029다.
  3:3이면 최소 p가 0.1이라 완전히 분리돼도 0.05에 도달할 수 없다.
- V1·V2 각 3회는 실환경에서 판단이 의도대로 동작했다는 존재 증명과 반복성 확인용이다. 3/3의 95% 하한은 29.2%다.
  거절 신뢰도를 추정하는 규모가 아니라고 보고서에 명시한다.
- 호스트 실행 제한(약 10시간)과 2시간 여유 규칙 때문에 두 세션으로 나눈다.
  - 세션 1: 예비 2회 → 결과 검토 후 파라미터 고정 → V1·V2 본시험 6회
  - 세션 2: H1 연습 1회는 세션 1 끝에 한다. A2·자동·수동 교대 11회(A2 먼저 시작, 회차마다 순서 교대, 수동은 연속 배치하지 않음)
- 예비 결과를 보고 조건 파라미터를 바꾸면 본시험 freeze 전에 이 문서에 기록한다.

## 6. 판정과 보고

| 판정 | 의미 |
|---|---|
| `expected_deferral` | V1·V2에서 조건이 성립했고 기대한 사유로 조치하지 않음 |
| `false_action` | V1·V2에서 조건이 성립했는데 재배치가 일어남 |
| `condition_not_established` | 조건이 성립하지 않음. 기대 판단의 분모에서 제외 |
| `control_measured` | A2에서 조건이 성립했고 회복 여부와 지연이 측정됨(회복 성공 여부와 무관) |
| `measurement_incomplete` | 요청·지표 누락 등으로 판정 불가 |

- 보고 형식: [A단계 분석](analysis-2026-10-25.md) 4절의 결정 행렬에 행을 추가하고, A2 대 자동은 4.3절과 같은 방식으로 제시한다.
- A2에서 회복이 일어나면 그대로 보고한다. 이 경우 S1 효과의 일부는 재시작으로 설명되며, RQ2 주장의 범위를 줄인다.
