작성 기준: 2026-10-29. 근거는 저장소의 코드·문서와 보고서 양식(hwpx)이다. 수치는 [평가 결과 통합 분석](../../evaluation-results-analysis-2026-10-29.md)과 [본평가 최종 결과](../../fresh-evaluation-final-results-2026-10-29.md)에서 가져왔다.

**읽는 법**
- 각 절은 **문단 단위**로 나눴다.
- `[문단 n]` 뒤의 인용문은 그 문단의 **주제문 초안**이다. 본문에 그대로 쓰거나 다듬어 쓴다.
- 들여 쓴 항목은 그 문단에 들어갈 내용과 근거다.
- 표는 실제 값으로 채웠고, 그림은 구성 요소를 적었다.

## 요약 (국문, 0.5~1쪽, 한 문단)

서론과 결론을 다 쓴 뒤 마지막에 작성한다. 문장 순서와 초안은 다음과 같다.

1. **문제**
   > OpenStack VM 위에서 Kubernetes를 운영하는 환경에서는 서비스 장애의 원인과 조치 수단이 서로 다른 관리 계층에 나뉘어 있어, 한 계층의 정보만으로는 적절한 대응을 결정하기 어렵다.
2. **목표**
   > 본 작품은 두 계층의 자원 관계를 연결하여 대표적인 장애 네 가지에 자동으로 대응하는 모듈의 프로토타입을 설계·구현하고, 그 효과를 비교 실험으로 검증하였다.
3. **구현**
   > Google Cloud 호스트 3대 위에 중첩 가상화로 OpenStack 2025.2와 Kubernetes 1.35.7을 코드로 구축하고, Cluster API와 Cluster Autoscaler를 연동하였다.
4. **방법**
   > 대응 모듈은 자원 관계 확인, 조치 조건 판단, 대상 조치, 결과 확인의 네 단계로 동작하며, 외부 측정 원자료로 결과를 독립 판정하는 평가 도구를 함께 구현하였다.
5. **평가 규모:** 11개 비교 조건에서 총 33회 실험하였다.
6. **결과 (4문장)**
   - 호스트 CPU 경합: 다른 compute 호스트로 재배치하자 조치 후 SLO 위반율이 0.08~0.14%로 낮아졌다. 무조치는 2.44~2.63%, 동일 노드 재시작은 2.24~3.54%였다.
   - 공유 송신 경로 혼잡: 작업 분리와 Neutron QoS를 함께 적용하자 4회 모두 조치 후 위반율이 0%였다. 작업 분리 단독은 2.63~3.02%였고, 대가로 업로드 처리량이 약 66% 줄었다.
   - 노드 통신 단절: fencing을 확인한 뒤 복구하자 3회 모두 데이터베이스가 회복되고, 커밋된 1,000건이 보존되었다.
   - worker 노드 VM 정지: 서비스가 약 73~81초 중단된 뒤 회복되었고, MachineHealthCheck가 정지 요청 후 283~298초에 노드 용량을 3회 모두 복원하였다.
7. **의의와 한계**
   > 조건당 2~4회의 사례 연구로서, 계층 간 정보 연결이 필요한 장애 유형과 안전한 조치 순서를 실측으로 보였다.

## 1. 서론 (5~6쪽)

### 1.1 제안 배경 및 필요성 (약 2쪽, 7문단)

**[문단 1] 운영 환경의 배경**
> 사설 클라우드에서는 OpenStack이 제공하는 VM 위에 Kubernetes 클러스터를 구성하여 컨테이너 서비스를 운영하는 방식이 널리 쓰인다.
- 장점: 인프라 자원 관리(OpenStack)와 애플리케이션 배포 관리(Kubernetes)를 나눌 수 있다.

**[문단 2] 계층 분리의 문제**
> 그러나 두 관리 계층은 서로 다른 정보를 본다.
- Kubernetes가 보는 것: Pod, Node
- OpenStack이 보는 것: VM이 놓인 compute 호스트, VM이 쓰는 Neutron port와 Cinder volume
- 그래서 장애의 원인은 한 계층에 있고 조치 수단은 다른 계층에 있는 경우가 생긴다.

**[문단 3] 시나리오 1: 호스트 CPU 경합**
> 같은 compute 호스트의 다른 VM이 CPU를 많이 사용하면, API 서비스의 Pod 자체에는 이상이 없어도 응답이 느려진다.
- Kubernetes에서는 원인이 보이지 않는다.
- 기본 대응인 재시작은 같은 호스트에서 다시 실행되므로 문제를 해결하지 못한다.

**[문단 4] 시나리오 2: 공유 송신 경로 혼잡**
> API 서비스와 대용량 업로드 작업이 같은 송신 경로를 공유하면, 업로드 트래픽 때문에 API 응답이 지연된다.
- Kubernetes의 배치 변경만으로는 대역폭을 제어할 수 없다.
- Neutron QoS는 port 단위로 제한하므로, 두 작업이 같은 port를 쓰면 API까지 함께 제한된다.

**[문단 5] 시나리오 3: 노드 통신 단절과 데이터베이스**
> 노드가 NotReady로 표시되어도 해당 VM과 그 위의 데이터베이스 프로세스는 계속 실행 중일 수 있다.
- 기존 프로세스가 멈췄는지 확인하지 않고 같은 볼륨을 다른 노드에 연결하면, 두 프로세스가 같은 데이터에 쓰는 위험이 생긴다.
- Kubernetes 공식 문서도 out-of-service taint를 붙이기 전에 노드가 실제로 꺼졌는지 확인하도록 요구한다.

**[문단 6] 시나리오 4: worker 노드 VM 정지**
> worker 노드 VM이 멈추면 Kubernetes는 남은 노드에서 Pod를 다시 실행하여 서비스를 회복시킨다. 그러나 멈춘 VM을 대신할 새 VM을 만들지는 못하므로, 클러스터는 노드가 한 대 줄어든 채로 남아 다음 장애를 받아낼 여유를 잃는다.
- 노드 용량을 되돌리려면 인프라 계층에서 새 VM을 만들어 클러스터에 합류시켜야 한다.
- 이를 담당하는 것이 Cluster API, Cluster API Provider OpenStack, MachineHealthCheck다.

**[문단 7] 필요성**
> 따라서 두 계층의 상태를 연결하고, 안전 조건을 확인한 뒤 정해진 순서로 조치하며, 서비스·데이터·용량의 회복까지 확인하는 자동 대응이 필요하다.
- 마지막 문장: 기존 기능(재시작, 재스케줄링, toleration, MachineHealthCheck)만으로 남는 문제가 있는지는 실험으로 확인한다고 쓰고 1.2절로 넘긴다.

근거: [장애 시나리오 정의서 §1, §3~6](../../failure-scenarios.md)

### 1.2 연구논문/작품의 목표 (약 1쪽, 3문단 + 표)

**[문단 1] 목표 세 가지**
> 본 작품의 목표는 세 가지이다.
1. 재현 가능한 OpenStack–Kubernetes 통합 테스트베드를 코드로 구축한다.
2. 네 가지 장애에 대한 대응 모듈을 같은 4단계 구조(자원 관계 확인 → 조치 조건 판단 → 대상 조치 → 결과 확인)로 구현한다.
3. 비교 조건을 둔 실험으로 효과를 검증한다.

**[문단 2] 연구 질문 다섯 가지**
> 평가는 다음 다섯 가지 연구 질문에 답하도록 설계하였다.
- **필요성:** 기존 기능만으로는 서비스나 용량 문제가 남는가
- **계층 간 정보의 기여:** 두 계층의 정보를 결합해야 판단과 조치가 가능한가
- **조치 기전:** 어떤 조치가 효과를 만드는가
- **복구 효과:** 서비스·데이터·용량까지 회복하는가
- **안전성:** 조건이 성립하지 않으면 조치하지 않는가, 실험 후 정리가 완전한가

**[문단 3] 범위**
> 본 작품은 사전에 정의한 네 가지 장애를 대상으로 하며, 임의의 장애를 자동으로 분류하는 기능은 범위에 포함하지 않는다.
- 범위 문장은 서론에서 **한 번만** 쓴다.

**[표 1-1] 대상 장애 시나리오**

| 시나리오 | 장애 | 서비스 영향 | 대응 조치 | 작품 내 역할 |
|---|---|---|---|---|
| 1. 호스트 CPU 경합 | 같은 compute 호스트의 다른 VM이 CPU를 과다 사용 | API 응답 지연 | 다른 compute 호스트의 worker 노드로 API Pod 재배치 | 직접 구현 |
| 2. 공유 송신 경로 혼잡 | API와 업로드가 같은 송신 경로를 공유 | API 응답 지연 | 업로드를 다른 worker 노드로 분리하고 그 port에 Neutron QoS 적용 | 직접 구현 |
| 3. 노드 통신 단절과 데이터베이스 복구 | worker 노드의 제어 통신과 DB 접속 경로 단절 | DB 접근 실패 | 기존 VM의 fencing 확인 → out-of-service taint → 같은 볼륨으로 DB 재기동 | 직접 구현 |
| 4. worker 노드 VM 정지 | worker 노드 VM 한 대 정지 | 일시적 요청 실패, 노드 용량 감소 | MachineHealthCheck 기반 Machine 교체와 용량 회복 확인 | 기존 기능 통합 |

### 1.3 전체 개관과 결과 미리보기 (약 1.5쪽, 3문단 + 그림 + 표)

**[문단 1] 시스템 개관**
> 테스트베드는 Google Cloud의 controller 호스트 1대와 compute 호스트 2대 위에 OpenStack을 배포하고, 그 VM으로 Kubernetes 클러스터를 구성하였다.
- 대응 모듈과 평가 도구는 운영 클라이언트에서 IAP를 통해 두 계층에 접근한다.

**[그림 1-1] 전체 구성 개요 (새로 그림)**
- 아래층: Google Cloud 호스트 3대
- 가운데층: OpenStack 서비스와 VM(control plane 노드 1대, worker 노드 2대)
- 위층: Kubernetes 서비스
- 오른쪽: 대응 모듈·평가 도구. 두 계층 각각에 "상태 읽기"와 "조치" 화살표를 그린다.

**[문단 2] 진행 경과**
> 본 작품은 7월 말 로컬 테스트베드로 시작하여 8월 말 Google Cloud 단일 환경으로 전환하였고, 9월에 노드 자동 확장과 네 시나리오를 구현하였다.
- 10월 초: 1차 평가 완료
- 10월 26일: 비교 조건과 판정 기준의 한계를 확인하고 평가를 새로 설계
- 10월 27~29일: 본평가 수행
- 근거: 첫 커밋 2026-07-28, ADR-0013(2026-08-24), 1차 평가 결과(2026-10-03)

**[문단 3] 결과 미리보기**
> 실험 결과, 네 시나리오 모두 제안 방식에서 서비스가 회복되었고 무조치와의 차이가 관측되었다.
- 표 1-2를 소개한다.
- 마지막 문장: 작업 분리 단독은 효과가 없었다는 점과 업로드 처리량 감소라는 대가를 함께 밝힌다.

**[표 1-2] 시나리오별 핵심 결과**

| 시나리오 | 제안 방식 | 비교 조건 | 핵심 차이 |
|---|---|---|---|

## 3. 제안 작품 소개 (7~8쪽)

### 3.1 이론적 배경 (약 1.5쪽, 6소절 각 1~2문단)

**3.1.1 OpenStack 구성 요소 (2문단)**
- Nova
  - 공유 CPU 정책에서는 여러 VM의 vCPU가 호스트 CPU를 나눠 쓴다. 시나리오 1의 전제다.
  - 정지 API는 비동기로 처리되므로, 요청 접수와 실제 정지를 구분해야 한다. 시나리오 3의 전제다.
- Neutron과 Cinder
  - Neutron port, security group
  - Neutron QoS의 bandwidth-limit 규칙. Open vSwitch 인터페이스의 ingress policing으로 적용된다.
  - Cinder volume과 attachment

**3.1.2 Kubernetes의 장애 처리 (2문단)**
- Node가 NotReady나 Unreachable이 되면 taint가 붙고, Pod는 toleration 시간(기본 300초)이 지나면 축출된다.
- StatefulSet Pod는 이전 Pod가 확실히 종료되기 전까지 대체되지 않는다.
- non-graceful node shutdown 처리에서는 노드가 꺼진 것을 확인한 뒤 out-of-service taint를 붙여야 Pod 정리와 볼륨 분리가 진행된다.
- 6분 뒤 강제 분리하는 동작도 있으며, 본 실험에서는 비활성화했다.

**3.1.3 Cluster API (1~2문단)**
- Cluster API는 클러스터를 Machine 객체로 선언적으로 관리하고, Cluster API Provider OpenStack은 Machine을 Nova VM으로 만든다.
- MachineHealthCheck는 Node 조건으로 Machine을 비정상으로 판정해 교체를 시작한다. 예외 annotation(skip-remediation, paused)으로 교체를 막을 수 있다.
- Cluster Autoscaler는 대기 중인 Pod를 보고 worker 노드 수를 조정한다.

**3.1.4 MAPE-K 자율 대응 모델 (1문단)**
- Monitor–Analyze–Plan–Execute와 공유 Knowledge로 이루어진다.
- 본 작품의 4단계와 대응시키고, [그림 3-3]에 함께 표시한다.

**3.1.5 PSI (1문단)**
- 자원을 기다리며 정지한 시간의 비율이다.
- CPU 사용률만으로는 구분하기 어려운 경합을 판단하는 데 쓴다.

**3.1.6 PostgreSQL WAL과 내구성 설정 (1문단)**
- fsync, synchronous_commit, full_page_writes가 켜져 있으면 커밋이 끝난 트랜잭션은 볼륨에 남는다.
- 그래서 같은 볼륨으로 재기동했을 때 보존을 주장할 수 있는 범위는 "커밋이 끝난 데이터"다.

### 3.2 시스템 구성 (약 2쪽, 4문단 + 그림 2 + 표 1)

**[문단 1] 물리 구성**
> 테스트베드는 Google Cloud의 사용자 정의 VPC 안에 있는 호스트 3대로 구성된다.

**[표 3-1] 테스트베드 구성**

| 계층 | 구성 | 버전·사양 |
|---|---|---|
| Google Cloud 호스트 | controller 호스트 1대, compute 호스트 2대. 중첩 가상화(KVM), IAP 접근 | e2-standard-4 / n2-standard-8 / n2-standard-4 |

**[문단 2] 사양을 비대칭으로 둔 이유**
- compute 호스트 1을 n2-standard-8로 늘렸다.
- 이유: 4 vCPU 구성에서는 재배치 목적지의 여유가 부족해, 1차 실험에서 회복 기준을 간헐적으로 넘었다.
- 임계값을 낮추는 대신 사양을 늘렸다. 이 비대칭은 4.6절의 한계로 연결한다.

**[그림 3-1] 테스트베드 물리·논리 구조 (새로 그림)**
- 호스트 3대를 상자로 그린다.
- controller 상자: OpenStack 제어 서비스, kind management 클러스터
- compute 호스트 1 상자: control plane VM, worker 노드 VM(재배치 목적지)
- compute 호스트 2 상자: worker 노드 VM(서비스의 원래 위치), 시나리오 1의 경쟁 VM

**[문단 3] 계층 간 자원 관계**
> Kubernetes Node와 Nova VM은 Node의 providerID(openstack:///VM 식별자)로 연결되며, VM은 Neutron port와 Cinder volume attachment를 통해 네트워크와 저장소에 연결된다.
- 이름이 비슷하다는 이유로 연결하지 않고, 식별자로만 연결한다는 원칙을 밝힌다.

**[그림 3-2] 계층 간 자원 관계도 (새로 그림)**
- Service / Deployment / StatefulSet → Pod → Node → Machine → Nova VM → compute 호스트
- VM에서 Neutron port와 Cinder volume으로 가지를 친다.
- 연결선마다 식별자를 표기한다: nodeName, providerID, device_id, attachment server_id

**[문단 4] 접근 경로**
- 운영 클라이언트는 IAP로만 호스트에 접근한다.
- workload 클러스터 API는 공개하지 않고 터널로 접근한다.
- Cluster Autoscaler는 management 클러스터 안에서 control plane Floating IP로 직접 접근한다.

### 3.3 구축·운영 설계 (약 1쪽, 8문단)

코드 전체를 검토해 정리한 원칙이다. 각 문단 끝에 근거 코드를 괄호로 단다.

**[문단 1] 단계별 구축 파이프라인**
> 구축은 클라우드 자원 선언에서 Cluster Autoscaler 설치까지 한 방향의 단계로 진행되며, 각 단계는 다음 단계로 넘어가기 전에 검증된다.
- 단계: OpenTofu → Ansible → Kolla → 노드 이미지 생성 → management 클러스터와 Cluster API → workload 클러스터 → Cluster Autoscaler
- 검증된 이미지는 체크섬을 확인해 재사용한다.
- 이미 클러스터가 있으면 재생성을 거부한다.
- (`scripts/lab-up.sh`)

**[문단 2] 기록 우선 상태 관리**
> 환경 기동, 실험, 노드 제어의 모든 작업은 진행 단계를 상태 파일에 원자적으로 기록하며, 외부 자원을 바꾸기 전에 의도를 먼저 기록한다.
- 원자적 기록: 임시 파일에 쓰고 fsync한 뒤 교체한다.
- 중단된 기록이 남아 있으면 다음 작업을 거부한다.
- (`scripts/lib/state.py`, `scripts/graduation_env.py`)

**[문단 3] 식별자 기반 소유권**
> 실행마다 고유 실행 식별자를 만들고 생성한 자원에 label과 UID를 남겨, 정리할 때는 자기 소유 자원만 삭제한다.
- 환경을 다시 켤 때 호스트 ID나 클러스터 UID가 바뀌었으면 거부한다.
- (`experiments/graduation_recovery.py`, `scripts/test_resources.py`)

**[문단 4] 배타 실행과 제어권 전환**
> 파일 잠금으로 중복 실행을 막고, 한 시나리오가 진행 중이면 다른 시나리오를 시작하지 않는다.
- 실험 중에는 Cluster Autoscaler를 0개로 줄인 고정 모드로 두고 worker 노드를 2대로 맞춘다.
- 실험이 끝나면 원래 모드와 노드 수를 복원한다.
- (`scripts/worker_control.py`)

**[문단 5] 변경 전 재확인과 변경 후 확인**
> Kubernetes 객체는 UID와 resourceVersion을 조건으로 건 JSON patch로 변경하여, 다른 주체의 동시 변경을 감지한다.
- 위험한 조치 직전에는 상태를 다시 읽는다.
- 변경 후에는 실제 적용 상태를 읽어 확인한다.
- 응답이 사라진 변경은 다시 보내지 않는다.
- (`experiments/graduation_s1_auto.py`, `graduation_s3.py`, `evaluation/fresh_mutation.py`)

**[문단 6] 실패 시 중단과 증거 보존**
> 조건이 불확실하면 다음 단계를 강행하지 않으며, 요청 원자료·상태 스냅샷·실행 코드의 해시와 사본을 실행별 디렉터리에 남긴다.

**[문단 7] 공통 기반과 시나리오의 분리**
- 환경, 노드, OpenStack 접근은 공통 모듈이 맡는다.
- 공통 모듈은 특정 시나리오를 참조하지 않는다.
- 평가 도구는 별도 계층으로 얹는다.
- (`scripts/lib/runtime.py`)

**[문단 8] 비용과 접근 통제**
- 호스트에 최대 실행 시간 후 자동 정지를 건다.
- 종료는 그 실행이 켠 호스트만 대상으로 한다.
- 핵심 자원에는 삭제 방지(prevent_destroy)를 건다.
- (`infra/gcp/main.tf`)

### 3.4 개념설계: 공통 대응 구조 (약 1쪽, 3문단 + 그림 + 표)

**[문단 1] 4단계 구조**
> 모든 대응 모듈은 자원 관계 확인, 조치 조건 판단, 대상 조치, 결과 확인의 네 단계로 동작한다.

**[그림 3-3] 공통 4단계 대응 흐름 (새로 그림)**

- 조건 판단 상자에서 아래로 "보류(기록 후 종료)" 분기를 낸다.

**[문단 2] 판단 원칙**

**[문단 3] 완료 원칙**

### 3.5 상세설계: 시나리오별 알고리즘 (약 3쪽)

시나리오마다 "구성 → 판단 → 조치 → 회복 판정"의 4문단과 그림 1개를 둔다.

#### 3.5.1 시나리오 1: 호스트 CPU 경합

근거: `experiments/graduation_s1_auto.py`

**[문단 1] 구성**
> API 서비스는 요청마다 PBKDF2 100,000회를 계산하는 CPU 중심 HTTP 서버이며, compute 호스트 2의 worker 노드에서 실행된다.
- 같은 호스트에 4 vCPU 경쟁 VM을 두고 CPU 작업 4개를 실행한다.
- 요청 발생기는 control plane 노드에서 초당 5회 요청한다.

**[문단 2] 판단**
- 60초 창을 최대 6번 관측해, 아래 조건을 2번 연속 만족하면 조치한다.
  - 서비스 영향: 실패가 기준선보다 많거나, p95 지연이 기준선의 1.5배를 넘는다.
  - 호스트 경합: CPU 사용률 0.7 이상, 그리고 CPU PSI가 max(0.02, 기준선 × 2) 이상이다.
- 아래 중 하나라도 해당하면 다른 원인으로 보고 보류한다.
  - Pod CPU throttling
  - 메모리·I/O PSI 0.02 이상
  - 호스트 가용 메모리 512 MiB 미만
  - 요청 기록 누락

**[문단 3] 조치**
> 다른 compute 호스트에 있는 Ready worker 노드 가운데, 배치 제약과 자원 요청을 만족하고 목적지 호스트에 여유가 있는 노드 중 CPU 사용률이 가장 낮은 노드를 고른다.
- 배치 제약: nodeSelector, affinity, taint
- 목적지 여유: CPU 사용률 0.7 미만, PSI 0.02 미만
- Deployment의 nodeSelector를 UID·resourceVersion 조건 patch로 바꾼다.
- maxSurge 1, maxUnavailable 0으로 새 Pod를 먼저 띄운다.
- 900초 동안 다시 옮기지 않는다.

**[문단 4] 회복 판정**
- 30초 대기 후, 60초 창 3번 연속으로 요청 실패 0, p95 지연 기준선의 1.2배 이하를 만족해야 한다.
- 8번 안에 만족하지 못하면 추가 조치 없이 "검토 필요"로 끝낸다.

**[그림 3-4] 시나리오 1 순서도 (새로 그림)**
- 진단 반복 루프 → 보류 분기 → 목적지 후보 필터 → patch → 안정화 루프

#### 3.5.2 시나리오 2: 공유 송신 경로 혼잡

근거: `experiments/graduation_s2.py`, `graduation-s2-network.sh`

**[문단 1] 구성**
> API는 요청마다 256 KiB 응답을 반환하고, 업로드 작업은 1 MiB 조각을 controller 호스트의 수신기로 보낸다.
- 두 트래픽은 controller의 전용 veth를 지난다. 이 veth에는 20 Mbit 송신 제한(tbf)이 걸려 있다.
- 처음에는 두 작업이 같은 worker 노드에 있다.

**[문단 2] 판단**
- 60초 창 2번 모두에서 아래 네 조건을 만족해야 한다.
  - API 영향: p95 지연이 기준선의 1.5배 초과, 또는 실패 발생
  - 송신량 16 Mbps 이상, 그리고 qdisc overlimits 증가
  - 업로드 진행 중
  - 두 호스트 CPU 사용률 0.7 미만

**[문단 3] 조치**
> 업로드를 옮길 worker 노드의 Neutron port에 egress bandwidth-limit 정책을 먼저 적용한 뒤, 업로드 Deployment를 그 노드로 옮긴다.
- 적용 확인: Neutron API readback, Open vSwitch 인터페이스의 ingress_policing_rate
- 사전 조건: 목적지 port에 기존 QoS 정책이 없고, 다른 일반 Pod가 없다.

**[문단 4] 단계 조정과 무결성**
- rate는 6, 10, 14, 18 Mbps 네 단계이며, burst는 250 kbit다.
- p95 지연이 기준선의 1.3배 이하이고 업로드가 진행 중이면 한 단계 올리고, 아니면 내린다.
- 최저 단계에서도 회복하지 못하면 중단한다.
- 업로드 조각은 수신 측 SQLite 기록과 SHA-256으로 검증한다.

**[그림 3-5] 시나리오 2 조치 전후 배치도 (새로 그림)**
- 왼쪽(조치 전): worker A에 API와 업로드. 둘 다 공유 출구로 화살표
- 오른쪽(조치 후): worker A에 API, worker B에 업로드. worker B port에 QoS 표시. 두 화살표 모두 같은 출구로

#### 3.5.3 시나리오 3: 노드 통신 단절과 데이터베이스 복구

근거: `experiments/graduation_s3.py`

**[문단 1] 구성**
> 단일 PostgreSQL StatefulSet이 Cinder CSI volume(1 GiB)을 사용하며, 시작할 때 fsync·synchronous_commit·full_page_writes가 모두 켜져 있는지 확인한다.
- 기준 레코드 1,000건을 기록한다.
- 실험 동안의 설정:
  - toleration 3600초
  - controller-manager의 강제 분리 비활성화
  - Machine에 skip-remediation annotation

**[문단 2] 장애와 판단**
> 대상 worker 노드에서 Kubernetes API(6443) 송신과 데이터베이스 접속(5432) 전달을 iptables로 차단하고, 기존 데이터베이스 컨테이너가 계속 실행 중인지 확인한다.
- Node가 NotReady가 된 뒤 데이터베이스 접속이 15회 연속 실패하면 진단을 완료한다.
- 실행 중인 VM을 fencing 확인 함수가 거부하는지 음성 검사로 함께 기록한다.

**[문단 3] fencing과 복구**
- Nova에 정지를 요청한 뒤, 다음 네 조건을 모두 확인한다.
  - status SHUTOFF
  - task_state 없음
  - power_state 4
  - libvirt domstate "shut off"
- out-of-service taint를 붙이기 직전에 이 상태를 다시 읽는다.
- taint를 붙인 뒤, 같은 PV를 쓰는 새 Pod가 다른 노드에서 Ready가 되기를 기다린다.

**[문단 4] 검증**
- 1,000건 digest 일치
- 새 트랜잭션 COMMIT 후 SELECT 성공
- 60초 연속 접속 성공
- 볼륨이 새 노드에만 연결
- 쓰지 않는 조치: Pod 강제 삭제, 볼륨 강제 분리, finalizer 제거

**[그림 3-6] 시나리오 3 순서도 (새로 그림)**
- 주입 → NotReady → 영향 확인 → 정지 요청 → 꺼짐 4조건 → 재확인 → out-of-service taint → 새 Pod Ready → 데이터 검증
- fencing 확인에 실패하면 "중단"으로 가는 분기를 그린다.

#### 3.5.4 시나리오 4: worker 노드 VM 정지

근거: `experiments/graduation_s4_run.py`, `graduation_s4_workflow.py`, `kubernetes/graduation-s4/`

**[문단 1] 구성**
> 영구 볼륨이 없는 HTTP Deployment(replica 1, toleration 30초)를 worker 노드에서 실행하고, Kubernetes API 서비스 프록시 경로로 초당 1회 요청한다.

**[문단 2] MachineHealthCheck 설정**
- Ready 조건이 Unknown 또는 False로 120초 이어지면 비정상으로 판정한다.
- 동시 교체는 1대까지, 새 노드 시작 대기는 900초다.
- "MachineHealthCheck 미사용" 조건에는 paused annotation을 붙인다.

**[문단 3] 실행과 재개**
- 정확히 한 VM에만 Nova 정지를 요청한다.
- 중단 후 재개할 때는 기록을 대조하고, 정지 요청을 다시 보내지 않는다.

**[문단 4] 판정**
- 서비스 회복과 용량 회복을 따로 판정한다.
- 용량 회복: 목표 worker 수가 Ready이고, 새 노드에 시험 Pod가 실제로 실행된 경우

**[그림 3-7] 시나리오 4 두 경로 (새로 그림)**
- VM 정지에서 두 갈래로 나눈다.
- 서비스 경로: Node 이상 → toleration 30초 → Pod 재실행 → HTTP 회복
- 용량 경로: MachineHealthCheck 120초 → Machine 삭제 → 새 Nova VM → 클러스터 합류 → Node Ready

### 3.6 평가 도구 설계 (약 1쪽, 3문단 + 그림)

**[문단 1] 구성 요소의 분리**
> 평가 도구는 장애 주입기, 대응 정책, 외부 측정기, 독립 판정기를 분리하며, 정책이 남긴 성공 표시는 판정에 사용하지 않는다.

**[문단 2] 실행 고정**
> 실행 전 소스 코드와 설정 파일의 해시를 고정하고, 각 실험 뒤에도 해시를 다시 검사하여 실험 도중 코드가 바뀌지 않았음을 보장한다.
- (`evaluation/fresh_campaign.py`)

**[문단 3] 판정의 세 축**
> 측정 조건 충족, 안전성(대상·순서·식별자), 관측 구간 안의 서비스 회복은 서로 다른 의미이므로 각각 따로 기록한다.

**[그림 3-8] 평가 도구 구조 (새로 그림)**
- 네 구성 요소를 상자로 그린다.
- 흐름: 코드·설정 고정 → 주입·조치 → 원자료(요청, 이벤트, 상태 스냅샷) → 재계산 판정 → 결과표

### 4.2 실험 방법 (약 1쪽, 4문단 + 표 2)

**[문단 1] 측정 방식**
> 외부 측정기는 예정된 시각마다 요청을 보내고, 도착 예정 시각·성공 여부·지연을 모두 기록한다. 서비스 요청은 재시도하지 않는다.

**[표 4-2] 측정 조건**

| 시나리오 | 관측 구간 | 요청률 | SLO | 장애 강도 |
|---|---:|---:|---:|---|
| 1 | 1200초 | 초당 5회 | 200 ms | 4 vCPU 경쟁 VM, CPU 작업 4개 |
| 2 | 1200초 | 초당 2회 | 500 ms | 20 Mbit 병목, 1 MiB × 4,096 조각 업로드 |
| 3 | 900초 | 초당 1회 | 2000 ms | 6443·5432 통신 차단 |
| 4 | 1200초 | 초당 1회 | 2000 ms | worker 노드 VM 1대 정지 |

**[문단 2] 판정 규칙**
- 20초 판정 구간마다 다음 세 조건을 모두 만족하면 정상이다.
  - 예정 요청이 모두 기록됨
  - SLO 위반 비율 5% 이하
  - 성공 요청의 p95 지연이 SLO 이하
- 엄격 회복 판정: 관측 구간 끝까지 정상 구간이 120초 이상 이어지면 회복이다.
- 회복하지 못한 실험은 회복 시간을 기록하지 않는다.

**[문단 3] 비교 조건 설계**
> 각 시나리오는 제안 방식과, 같은 장애·부하·설정에서 제안 조치만 뺀 무조치를 기본 비교로 두었다.
- 시나리오 1에는 두 조건을 추가했다.
  - 동일 노드 재시작: 재시작의 효과를 구분하려고
  - 경합만 있는 대조 조건: 서비스 영향 없이 호스트 경합만 있을 때 조치하지 않는지 보려고
- 시나리오 2에는 작업 분리 단독을 추가했다. Neutron QoS가 필요한지 확인하려고 다른 결과를 본 뒤 추가한 조건이다.

**[문단 4] 평가 원칙** (2장에서 옮겨 온 내용)
- 일시적 정상과 지속 회복을 구별한다.
- 성공 요청만 집계하면 효과가 과대평가되므로, 실패율과 SLO 위반율을 함께 낸다.

**[문단 1] 필요성**
- 시나리오별로, 기존 기능만 썼을 때 남은 문제를 한 문장씩 쓴다.

**[문단 2] 계층 간 정보의 기여**
- 시나리오 2: Neutron QoS를 걸 port를 정하려면 Pod → VM → port 대응 정보가 필요하다.
- 시나리오 3: Kubernetes는 NotReady만 알 뿐이고, 기존 프로세스가 살아 있는지는 OpenStack의 VM 상태로만 판단할 수 있다.
- 시나리오 1: worker 노드가 2대이고 서로 다른 호스트에 있다. 그래서 "다른 노드로 옮긴다"는 Kubernetes만의 규칙도 같은 목적지를 고르게 되어, 대상 선택에서 정보의 효과는 식별할 수 없다.

**[문단 3] 조치 기전**
- 시나리오 2에서 작업 분리가 꼭 필요한지는, 분리 없이 Neutron QoS만 거는 조건이 없어 확인하지 못했다.

**[문단 4] 복구 효과**
- 서비스, 데이터, 용량 순으로 정리한다.

**[문단 5] 안전성**
- 정리 검증을 모두 통과했다.
- fencing 확인 함수가 실행 중인 VM을 거부했다(음성 검사).

**[문단 6] 효과 크기**
> 표본이 작으므로 아래 확률값은 설명용으로만 제시한다.

**[표 4-9] 조건 간 차이의 효과 크기**

### 4.5 판정 지표에 대한 고찰 (약 0.5쪽, 2문단)

**[문단 1] 엄격 회복 판정의 한계**
> 위반율이 2.6% 안팎으로 일정하게 유지되는 조건에서는 엄격 회복 판정이 우연에 크게 좌우된다.
- 계산 근거:
  - 위반율 2.6%(무조치 중앙값)에서 요청 100개인 20초 구간 하나가 5% 기준을 넘을 확률은 이항분포로 약 4.7%다.
  - 마지막 6개 구간이 모두 정상일 확률은 0.953⁶ ≈ 75%다.
- 실제로 무조치 2/3, 작업 분리 단독 2/3이 "회복"으로 판정되었고, 그 시점은 880~1040초로 관측 구간 끝에 몰려 있었다.

**[문단 2] 지표 선택**
> 따라서 시나리오 1·2의 효과는 조치 시점 이후 SLO 위반율로 제시하고, 엄격 회복 판정은 함께 공개한다.
- 이 지표는 실험 후에 정한 것임을 밝힌다.

### 4.6 타당성 위협과 한계 (약 0.5쪽, 1~2문단)

2장에서 걷어낸 단서를 이곳에 모은다.
- **표본:** 조건당 2~4회의 사례 연구다.
- **코드 보완:** 실험 기간 중 운영 코드(읽기 재시도, 시계 보호, security group 동기화 확인)를 보완했다. 측정 조건은 고정했다.
- **사후에 정한 요소:** 조치 후 위반율 지표, 작업 분리 단독 조건
- **구성:**
  - worker 노드 2대, 호스트 3대의 고정 구성
  - compute 호스트 사양의 비대칭. 단, 시나리오 1에서 재배치 후 지연이 기준선보다 더 좋아지지는 않았다.
  - 요청 발생기가 목적지 호스트에 있다.
- **데이터 범위:** 시나리오 3은 커밋된 기준 레코드의 보존만 확인했다. 진행 중이던 트랜잭션의 처리는 확인하지 않았다.

## 5. 결론 및 소감 (2쪽)

### 5.1 결론 (약 0.8쪽, 3문단)

**[문단 1] 요약**
> 본 작품은 OpenStack과 Kubernetes의 자원 관계를 연결하여 네 가지 장애에 대응하는 모듈을 구현하고, 33회의 비교 실험으로 검증하였다.
- 목표 세 가지의 달성 여부를 한 문장씩 쓴다.

**[문단 2] 기여**
1. 재현 가능한 통합 테스트베드와 대응 모듈
2. 실측으로 확인한 효과: 호스트 경합 시 재배치, Neutron QoS의 보호 효과와 처리량 절충, fencing을 앞세운 상태 저장 서비스 복구 순서
3. 원자료에 기반한 독립 판정 평가 체계

**[문단 3] 후속 연구**
1. 작업 분리 없이 Neutron QoS만 거는 조건
2. 단일 계층 정보만 쓰는 판단 규칙을 기존 원자료에 적용해 비교
3. fencing과 out-of-service taint의 개별 효과 분리
4. worker 노드 3대 이상, 같은 호스트에 대체 노드가 있는 구성

### 5.2 소감 (약 1.2쪽, 5문단, 양식상 "가장 중요")

문서에 근거가 있는 경험만 쓰고, 본인의 말로 서술한다.

**[문단 1] 통과와 증명의 차이**
- 1차 평가 34건을 모두 통과했다(2026-10-03, 10-24 재시험).
- 다시 검토하면서 두 가지 문제를 발견했다.
  - 시나리오 3의 "노드 이상 시각"이 실제로는 진단이 끝난 시각이었다.
  - 시나리오 2의 비교가 같은 실행 안의 순차 구간이라 독립 비교가 아니었다.
- 그래서 평가를 다시 설계했다. 근거: [합의 토론 기록](../../consensus-discussion-2026-10-26/README.md)

**[문단 2] 자동화의 가치는 속도가 아니라 안전**
- 1차 평가에서 시나리오 3의 자동 대응과 스크립트 런북의 소요 시간은 비슷했다(중앙값 142.7초 대 143.4초).
- 이를 통해 기여가 빠르기가 아니라 안전한 순서에 있다는 것을 알게 되었다.

**[문단 3] 중첩 가상화 운영의 어려움**
- security group 주소 목록이 비어 DNS가 실패했다.
- IAP 터널이 끊겼다.
- 운영 노트북의 시계 자동 보정이 측정 시각을 흔들어, 시계 보호 장치를 만들었다.

**[문단 4] 결과를 고치지 않는 원칙**
- 목적지 용량이 부족했을 때 임계값을 낮추지 않고 사양을 늘렸으며, 그 한계를 기록했다.
- 회복하지 못한 결과도 다시 실행하지 않고 그대로 보고했다.

**[문단 5] 비용 제약과 배운 점**
- 무료 체험 크레딧 안에서 호스트 가동 시간을 기록하며 실험 일정을 짰다.
