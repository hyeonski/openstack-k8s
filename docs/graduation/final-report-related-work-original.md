## 관련연구

### 2.1 통합 관측과 장애 증거의 연결

OpenStack 위에서 Kubernetes 서비스를 운영하는 환경에서는 서비스 요청의 이상, 컨테이너와 노드의 상태, 가상머신과 물리 호스트의 상태가 서로 다른 관리 계층에서 관찰된다. 본 절은 이러한 정보를 연결하여 장애에 대응하는 과정을 중심으로 관련연구를 검토한다. 국문 논문 세 편과 영문 논문 다섯 편을 통합 관측, 계층 간 장애 정보 전달, 자원 경합과 네트워크 제어, 상태 저장 서비스 복구, 서비스 결과 확인의 관점에서 비교한다. 각 연구의 관찰 대상과 조치 단위, 평가 지표를 구분하여 본 작품이 활용하는 기존 기술과 추가로 검증할 문제를 정리한다.

김지용 등은 OpenStack 환경의 서비스 메시 기반 통합 모니터링 시스템을 제안하였다. 서비스 메시의 관측 정보에 기반 인프라의 다양한 메트릭을 함께 수집·시각화함으로써, 운영자가 마이크로서비스뿐 아니라 전체 시스템의 상태를 확인할 수 있도록 하였다.[1] 이 연구는 본 작품과 같이 OpenStack 위의 Kubernetes 서비스 운영을 대상으로 하며, 서비스 계층의 정보만으로는 하위 실행 환경을 충분히 파악하기 어렵다는 문제를 다룬다. 본 작품은 이 관측 관점을 바탕으로 장애 시점의 Pod–Node–VM 관계를 확인하고, 해당 관계가 실제 조치 대상과 일치하는지를 검증하는 절차에 초점을 둔다.

박주원 등은 OpenStack의 시스템 계층과 응용 서비스 계층에서 발생한 이벤트 로그를 모아 메시지 기반으로 군집화하고, 메시지 그룹 사이의 연관성을 분석하는 기법을 제시하였다. 분산 환경에서 시각이 정확히 일치하지 않는 패턴을 비교하기 위해 동적 시간 왜곡(Dynamic Time Warping, DTW)을 사용한다.[2] 이 연구는 여러 위치에 흩어진 증거를 연결하여 오류 원인을 분석한다는 점에서 관련된다. 다만 본 작품의 실행 ID와 자원 식별자를 이용한 기록 연결은 로그 패턴에서 원인을 추론하는 기법과 목적 및 방법이 다르다. 본 작품은 로그 군집화나 DTW를 구현한 것으로 설명하지 않으며, 실행 기록을 모았다는 사실만으로 자동 원인 분석의 정확성을 주장하지 않는다.

두 연구를 본 작품에 적용할 때 필요한 구분은 관측 범위의 확대와 조치 대상의 확정이다. 서비스 지연과 호스트 부하가 함께 증가한 사실은 대응을 위한 단서가 될 수 있지만, 그 자체로 특정 VM이나 port가 올바른 조치 대상임을 확정하지는 못한다. 본 작품은 서비스 요청 결과와 Kubernetes·OpenStack 자원의 대응 관계를 같은 실행에 기록하고, 조치 전에 대상의 식별 정보와 현재 상태를 확인하는 구조를 평가한다. 이러한 연결은 잘못된 자원에 대한 개입을 줄이기 위한 설계 요소이며, 그 효과는 대상 선택과 실제 실행 결과를 통해 확인해야 한다.

### 2.2 OpenStack–Kubernetes 간 장애 정보 전달

Yang과 Kim은 가상머신 위에서 실행되는 컨테이너 환경의 장애 탐지 지연을 줄이기 위해 Fast Fault Detection Manager(FFDM)를 설계하였다. OpenStack의 Ceilometer·Aodh를 통해 관찰한 VM 장애 정보를 Kubernetes로 전달하고, 해당 노드의 상태 변경을 통해 복구 흐름이 시작되도록 하는 구조이다.[3] 이 연구는 VM 계층에서 얻은 정보를 컨테이너 관리 계층에 직접 전달한다는 점에서 본 작품과 가장 가까운 선행연구이다. 따라서 계층 간 상태 정보를 연계한다는 발상 자체는 기존 연구의 성과로 인정하고, 본 작품의 추가적인 연구 범위를 구체적으로 구분할 필요가 있다.

FFDM 연구의 성능 평가는 장애 발생부터 Kubernetes의 master가 장애 정보를 받기까지의 탐지 시간을 중심으로 이루어진다. 연구진은 기존 Kubernetes의 탐지 매개변수를 조정한 조건과 제안 방식을 비교하고, worker 수와 CPU·네트워크 부하 변화에 따른 탐지 지연도 분석하였다.[3] 여기서 탐지가 빨라진다는 사실과 사용자 서비스가 더 빨리 회복된다는 사실은 동일한 측정 결과가 아니다. 본 작품의 비교 관점에서는 탐지 이후 어떤 제어기가 어떤 자원을 변경하고, 서비스와 실행 용량이 언제 회복되는지를 추가로 추적해야 한다.

본 작품의 S4는 worker VM 정지 후 Node·Machine·VM의 관계와 교체 과정을 확인하고, 서비스 안정화와 새 worker 준비를 별도의 사건으로 기록하도록 구성한다. 이는 FFDM의 빠른 장애 정보 전달과 다른 단계까지 관측 범위를 넓히려는 접근이다. 다만 관측 구간이 더 길거나 항목이 더 많다는 사실만으로 더 우수한 복구 알고리즘이 되는 것은 아니다. 각 단계에서 기다리는 조건과 실행 주체를 구분해야 하며, 기존 기능의 동작을 이용한 부분과 자체 실행기가 추가한 확인·재개·정리 절차를 나누어 평가해야 한다.

계층 간 정보 전달을 비교할 때는 장애 신호의 의미도 중요하다. VM이 정지했다는 관리 계층의 정보와 Kubernetes에서 노드에 접근할 수 없다는 정보는 서로 다른 조건을 나타낸다. 본 작품은 이 구분을 특히 통신 단절을 다루는 S3와 VM 정지를 다루는 S4에 적용한다. 통신 실패를 곧바로 실행 주체의 종료로 해석하지 않고, 해당 시나리오의 복구 절차에 필요한 상태를 확인한 뒤 다음 조치를 수행한다. FFDM의 탐지 지연 개선과 본 작품의 안전 조건·서비스 복구 확인은 상호 관련되지만, 동일한 지표로 직접 우열을 비교할 대상은 아니다.

### 2.3 자원 경합과 서비스 목표를 고려한 제어

Delimitrou와 Kozyrakis가 제안한 Paragon은 서버의 이질성과 함께 배치된 작업 사이의 자원 간섭을 고려하는 데이터센터 스케줄러이다. 이전 작업에 대한 정보를 활용하여 새 작업의 특성을 분류하고, 공유 자원에서의 간섭을 줄이는 방향으로 배치를 결정한다.[4] 본 작품의 CPU 경합 시나리오인 S1도 실행 위치와 공유 자원의 관계가 서비스 성능에 영향을 줄 수 있다는 문제를 다룬다. 다만 Paragon은 작업 배치 알고리즘을 연구하는 반면, 본 작품은 이미 서비스 성능이 저하된 상황에서 계층 간 배치 정보를 활용한 Kubernetes 재배치 절차를 검토한다.

Qiu 등의 FIRM은 마이크로서비스의 서비스 수준 목표(Service-Level Objective, SLO) 위반에 대응하는 자원 관리 프레임워크이다. 온라인 관측 정보와 기계학습을 이용하여 문제가 있는 마이크로서비스와 경합 자원을 식별하고, 동적인 자원 재할당을 통해 서비스 목표 위반을 완화한다.[5] 이 연구는 서비스의 응답 성능을 하위 자원 상태 및 제어 조치와 연결한다는 점에서 S1·S2의 설계와 관련된다. 본 작품은 학습 기반의 범용 식별 모델을 구현하는 대신 사전에 정의한 시나리오에서 허용된 관측 정보, 대상 선택, 실제 조치의 관계를 확인한다.

두 연구를 참고하면 자원 사용률이나 단순한 노드 분산만으로 배치 변경의 효과를 설명하기 어렵다. 본 테스트베드에서는 서로 다른 Kubernetes Node가 같은 compute 호스트 위의 VM일 수 있으므로, Node를 바꾸는 것과 호스트 수준의 경합을 피하는 것을 구분해야 한다. 이에 따라 S1은 Pod–Node–VM–compute의 대응 관계와 목적지 상태를 함께 관찰한다. 실제 조치는 Kubernetes의 배치 변경이므로, 이 시나리오의 결과는 교차 계층 정보의 활용을 평가하는 근거가 될 수 있지만 OpenStack의 제어 명령이 반드시 필요하다는 근거로 곧바로 이어지지는 않는다.

본 작품에서는 정보의 역할과 조치의 효과를 각각 살펴본다. 동일한 재배치라도 목적지 선택에 어떤 정보를 사용했는지에 따라 연구 질문이 달라지며, 동일한 대상에서도 재시작과 배치 변경은 다른 효과를 낼 수 있다. 또한 목적지의 사양이 더 높으면 개선에는 경합 회피와 연산 능력 차이가 함께 포함될 수 있다. 따라서 배치 관계, 목적지 여유, 이동 비용을 공개하고 서비스 요청의 지연과 오류를 함께 확인하는 것이 필요하다. Paragon·FIRM은 이러한 분석 관점을 제공하는 선행연구이며, 서로 다른 실험 환경의 성능 수치를 직접 비교하여 본 작품의 우위를 판단하지 않는다.

### 2.4 네트워크 성능 제어와 작업 배치의 결합

변지섭 등은 엣지 컴퓨팅 환경에서 Kubernetes의 네트워크 성능 제어 방식이 실제 컨테이너 통신 성능에 미치는 영향을 분석하였다. 해당 연구는 요청한 성능 수준에 도달하는 데 시간이 걸리거나, 설정한 성능 목표를 충분히 달성하지 못하는 사례를 보고하였다.[6] 이는 제어 설정의 적용과 실측 성능을 구분해야 함을 보여 준다. 본 작품은 이 관점을 서비스와 업로드 작업이 송신 경로를 공유하는 S2에 적용한다. 다만 해당 논문의 엣지 환경과 본 작품의 OpenStack 환경은 다르므로, 논문에서 관찰한 현상을 모든 가상 네트워크 구성의 특성으로 일반화하지 않는다.

S2에서 사용하는 기반 제어 수단은 OpenStack Neutron의 QoS 기능이다. Neutron은 port 등의 네트워크 자원에 대역폭 제한 정책을 적용할 수 있으며, 지원하는 규칙과 방향은 백엔드 및 드라이버 구성에 따라 달라진다.[7] 본 작품의 연구 대상은 이 QoS 기능 자체가 아니라 Kubernetes의 작업 배치와 정책 적용 대상을 연결하는 절차이다. 서비스와 업로더의 Pod가 어느 worker VM에 있고 어떤 port를 사용하는지 확인하여, 정책이 실제로 영향을 주는 트래픽 범위를 설명해야 한다.

본 작품이 검토하는 공유 송신 구성에서는 업로더의 트래픽을 줄이기 위해 같은 port에 제한을 걸었을 때 API 트래픽도 함께 제약될 수 있다. 이에 따라 작업을 별도 worker로 분리하여 제어 범위를 나누는 조치와 업로더의 port에 QoS를 적용하는 조치를 구분한다. 두 조치의 결합이 유효한지는 실험으로 확인할 문제이며, 배치 분리나 인프라 제어 중 하나만으로 충분한 조건도 비교 대상이 된다. 애플리케이션 자체의 전송률 제한처럼 다른 제어 단위를 사용하는 방식은 필요한 권한과 구현 조건을 함께 밝혀 별도의 대안으로 다룰 수 있다.

이러한 비교에서 중요한 결과는 API의 응답 품질과 업로드 작업의 진척이다. API 지연이 줄었더라도 업로더가 사실상 정지했다면 두 작업의 병행 운용을 회복한 경우와 구별해야 한다. 또한 공유 port와 업로더 전용 port는 제한하는 트래픽의 범위가 다르므로, 같은 rate·burst 값을 적용했다는 이유만으로 공정한 비교가 성립하는 것은 아니다. 본 작품은 각 조건의 설정과 적용 범위를 공개하고 배치 분리, QoS 적용, 서비스 회복의 관계를 관찰한다. 변지섭 등의 실측 연구는 이 평가 관점을 뒷받침하며, S2의 효과는 본 테스트베드에서 수집한 요청 결과와 전송 상태를 통해 판단한다.

### 2.5 상태 저장 서비스의 가용성과 복구 순서

Vayghan 등은 상태 저장 마이크로서비스의 가용성을 관리하기 위해 Kubernetes와 연동하는 HA State Controller를 제안하였다. 애플리케이션 상태 복제와 정상 인스턴스로의 서비스 전환을 결합하여, 실패한 실행 단위가 수리되기 전에도 서비스를 회복할 수 있도록 하는 접근이다.[8] 이 연구는 반응 시간, 수리 시간, 서비스 회복 시간, 전체 중단 시간을 구분한다. 이러한 구분은 새 Pod의 기동과 실제 서비스 제공을 같은 사건으로 취급하지 않는다는 점에서 본 작품의 복구 완료 판정에 직접적인 근거가 된다.

본 작품의 S3는 정상 대기 인스턴스로 요청을 전환하는 방식과 달리, 통신이 단절된 worker에서 실행하던 단일 PostgreSQL 인스턴스와 동일 Cinder 볼륨의 복구 순서를 다룬다. 따라서 Vayghan 등의 상태 복제 구조와 동일한 복구 성능이나 가용성을 기대한다고 설명할 수는 없다. 본 작품이 비교하는 핵심은 서비스 회복을 관리 객체의 수리와 분리하여 판단하는 관점이다. 특히 기존 VM의 실행 상태, 볼륨의 동일성, 새 노드에서의 읽기·쓰기 가능 여부를 연결하여 서비스가 어떤 상태로 재개되었는지 확인한다.

이전 실행 주체의 종료를 확인하는 절차는 기반 기술의 안전 조건과도 연결된다. Kubernetes의 비정상 노드 종료 처리 문서는 out-of-service taint를 추가하기 전에 노드가 실제로 종료되었거나 전원이 꺼졌는지 확인하도록 요구한다. 해당 표시는 조건에 맞는 Pod의 정리와 볼륨 분리 절차에 사용된다.[9] 본 작품은 이전 VM의 실행을 차단하는 fencing과 그 상태 확인을 선행한 뒤 Kubernetes·CSI 복구 절차를 진행하는 순서를 검토한다. 이때 종료 요청의 접수와 실제 실행 중단은 구분하며, 통신 실패만으로 이전 writer가 제거되었다고 판단하지 않는다.

S3의 복구 결과에는 새 데이터베이스의 응답뿐 아니라 장애 전에 완료된 쓰기의 보존과 이후 읽기·쓰기의 정상 수행이 포함되어야 한다. 다른 빈 볼륨에서 서비스를 시작한 경우나 이전 실행 주체의 접근 가능성이 남은 경우는 안전한 상태 복구와 구별한다. 또한 일시적인 통신 단절에 대한 개입은 서비스 중단을 늘릴 수 있으므로, 빠른 재기동과 불필요한 조치 사이의 관계도 살펴야 한다. 본 작품은 상태 복제 알고리즘을 새로 제안하기보다, 인프라의 실행 차단과 상태 저장 서비스 재개를 순서 있는 절차로 연결하고 데이터와 서비스 결과로 확인하는 데 초점을 둔다.

### 2.6 건강 검사와 사용자 관점의 회복 검증

Flora 등은 TeaStore와 SockShop을 대상으로 부하와 결함 주입 조건을 변화시키며 Kubernetes probe의 장애 감지 효과를 평가하였다. 실험에서는 probe가 감지하지 못한 응용 실패가 관찰되었으며, 건강 검사 엔드포인트의 구현과 매개변수 설정이 동작에 미치는 영향도 분석하였다.[10] 이 연구는 컨테이너의 상태 표시와 애플리케이션의 실제 동작을 함께 확인해야 한다는 점에서 본 작품과 관련된다. 다만 결과는 해당 테스트베드, probe 구성, 주입한 결함에 관한 것이므로 Kubernetes probe가 모든 응용 장애에 무효하다는 의미로 확대할 수는 없다.

Flora 등의 설계 지침은 검사 주기와 timeout 설정의 균형을 다룬다. 검사 주기가 길면 이상 상태가 오래 남을 수 있고, timeout이 지나치게 짧으면 정상 처리에 필요한 시간을 주지 못해 오탐이 발생할 수 있다.[10] Kubernetes 공식 문서도 liveness와 readiness의 역할을 구분하며, 부적절한 liveness 검사 설정이 높은 부하에서 재시작과 연쇄적인 서비스 실패를 만들 수 있다고 설명한다.[11] 따라서 본 작품에서는 각 시나리오의 서비스 영향과 기존 검사 설정을 함께 확인하고, 동일한 지연 증상에 대해 항상 재시작을 선택하는 방식으로 문제를 단순화하지 않는다.

사용자 관점의 검증은 본 작품의 네 시나리오에 공통으로 적용된다. S1은 재배치 완료와 요청 지연의 회복을, S2는 QoS 적용과 API·업로드의 동시 진척을, S3는 새 Pod의 기동과 데이터 보존·읽기·쓰기 회복을, S4는 노드 교체와 서비스·용량 회복을 구분한다. 관리 API의 성공 응답이나 Pod Ready는 복구 과정의 중요한 사건이지만, 그 사건만으로 모든 서비스 목표가 충족되었다고 판정하지 않는다. 외부에서 보낸 실제 요청과 시나리오별 결과를 이용하여 제어기 상태와 사용자 경험 사이의 차이를 확인한다.

복구 완료를 판단할 때는 일시적인 정상 응답과 지속적인 회복도 구별해야 한다. 본 작품은 사전에 정한 관측 구간과 안정화 조건에 따라 요청 성공·실패 및 지연을 확인하고, 회복 이후의 재악화도 결과에 남기는 것을 평가 원칙으로 둔다. 성공 요청의 지연만 집계하거나 일정 시간 안에 회복되지 않은 실행을 제외하면 복구 효과가 과대평가될 수 있다. Flora 등의 연구는 이러한 서비스 수준 검증의 필요성을 설명하는 선행 근거이며, 본 작품의 안정화 조건과 관측 시간은 각 시나리오의 부하·장애 조건에 맞추어 별도로 정의한다.

### 2.7 선행연구와 본 작품의 관계

검토한 논문들은 장애 대응 과정의 서로 다른 부분을 다룬다. 김지용 등의 연구는 여러 계층의 관측 정보를 제공하고, 박주원 등의 연구는 로그의 연관성으로 오류 원인을 분석하며, Yang과 Kim은 VM 장애 정보를 Kubernetes로 전달한다.[1][2][3] Paragon·FIRM은 배치와 자원 제어를 서비스 성능에 연결하고, 변지섭 등은 네트워크 제어의 실측 특성을 분석한다.[4][5][6] Vayghan 등은 상태 저장 서비스의 회복을 자원 수리와 구분하며, Flora 등은 건강 검사와 응용 실패의 관계를 평가한다.[8][10] 본 작품은 이 관점들을 OpenStack–Kubernetes 통합 환경의 대응 절차와 결과 확인에 연결한다.

기반 복구 기능과 자체 구현의 역할도 분리할 필요가 있다. Cluster API의 MachineHealthCheck는 정의한 비정상 조건과 지속시간에 따라 Machine의 복구를 유도하고, 기본 흐름에서는 실패한 Machine을 대체할 자원의 생성을 유발한다.[12] Cluster API Provider OpenStack(CAPO)은 이러한 선언적 클러스터 관리를 OpenStack 인프라에 연결한다.[13] 본 작품의 S4는 이 기존 기능을 활용한다. 따라서 VM 교체 자체를 새 알고리즘으로 설명하기보다, Node·Machine·VM 관계 확인과 실행·재개·판정·정리 절차가 통합 환경에서 올바르게 작동하는지를 연구 대상으로 삼는다.

시나리오별로 보면 S1은 compute 배치·경합 정보를 이용한 Kubernetes 재배치, S2는 작업 배치 분리와 Neutron QoS의 결합, S3는 VM fencing과 상태 저장 서비스 복구 순서, S4는 기존 제어기를 활용한 worker 교체와 회복 확인을 다룬다. 이들의 공통 구조는 자원 관계 확인, 조치 조건 판단, 대상에 대한 실행, 서비스·데이터·용량 결과 확인이다. 그러나 필요한 정보와 조치가 서로 다르므로 모든 장애에 동일한 교차 계층 제어가 필요하다고 일반화하지 않는다. 각 단계의 기여는 기존 기능을 포함한 비교 조건과 정보·조치의 역할을 구분하는 평가를 통해 확인한다.

본 작품의 차별화 방향은 이미 존재하는 관측·제어 기능을 사용하면서, 계층 간 대상 식별과 안전 조건, 조치 순서, 서비스 결과를 같은 실행 기록으로 연결하여 검증하는 데 있다. 이러한 통합이 실제로 대응을 개선하는지는 후속 장의 실험 결과에 따라 판단한다. 본 절의 문헌 비교는 주제별 대표 연구를 선택한 개념적 비교이며, 동일 환경에서 선행 시스템을 재현한 성능 비교는 아니다. 사전 정의한 시나리오의 대응을 임의 장애의 자동 분류로 설명하거나, 제한된 테스트베드의 결과를 생산환경 전반의 신뢰도로 확대하지 않고 구현 범위와 관측된 효과에 맞추어 결론을 제시한다.
