## 1. 평가 틀

### 1.1 주장

| 주장 | 내용 |
|---|---|
| C1 | 단일 계층 self-healing(기존 기능)으로는 복구되지 않는 장애가 있다 |
| C2-판단 | 장애 판단에 Kubernetes와 OpenStack·호스트 정보가 모두 필요하다 |
| C2-조치 | 복구 조치에 두 계층의 제어가 모두 필요하다 |
| C3 | 제안 모듈은 서비스·데이터·용량 수준까지 복구한다 |
| C4 | 하지 말아야 할 조치는 하지 않는다 |
| C5 | 사람이 같은 절차를 수행할 때보다 시간·작업 부담이 줄어든다 |
| C6 | 그 대가(자원·처리량·대기·영향 범위)는 감당할 만하다 |

모든 칸은 다음 넷 중 하나로 기록한다.
- 성립(증거)
- 부분 성립
- 이 시나리오에는 주장하지 않음(이유)
- 미검증(한계)

### 1.2 비교군

| 칸 | 의미 |
|---|---|
| B0 | 기존 기능만 (조치 없음 또는 기존 제어기 비활성) |

| B2 | 사람이 런북 수행 |
| P | 제안 자동 대응 |
| N | 조치하면 안 되는 조건(음성) |

### 1.3 공통 사건과 지표

T0 장애 주입 → T1 첫 서비스 영향 → T2 탐지(사람은 증상 확인) → T3 판단 → T4 조치 시작 → T5 첫 안정 확인 → T6 안정 확정 → T7 완전 복원

| 지표 | 계산 |
|---|---|
| SLO 위반 시간 (주 지표) | T5 − T1 |
| 탐지 시간 | T2 − T1 |
| 대응 시간 | T4 − T2 |
| 조치 효과 시간 | T5 − T4 |
| 완전 복원 시간 | T7 − T1 (S3 데이터, S4 용량) |

T6(보수적 확정)는 함께 보고한다. 안정 판정 규칙은 기존 평가 계약을 따른다.

판정 등급:
- 완전 복구
- 부분 복구(서비스만)
- 정확한 보류
- 오조치
- 위험 조치
- 시간 초과
- 조건 불성립

### 1.4 통계

- 비율: Clopper–Pearson 정확 구간.
- 독립 두 군: Mann–Whitney 정확검정과 Cliff's δ. 최소 양측 p는 3:3 0.1, 3:4 0.057, 4:4 0.029, 5:5 0.008이다.
- 짝 비교: Wilcoxon 정확검정과 방향 일관성.
- 결과가 회복 여부처럼 이분형인 대조군(B0·B1·N)은 소수 회차의 일관성으로 제시한다. 검정은 하지 않는다.
- 사람 실험은 회차 순서(학습 효과)를 함께 제시한다.

### 3.2 우선순위 기준

1. **주장의 핵심도:** C1·C2(작품의 중심 주장) > C5(신청서 약속, 상세설계 배점) > C4 > C6.
2. **대체 증거의 유무:** 같은 칸에 기존 증거가 없을수록 높다.
3. **비용:** 구현이 작고 회차가 짧을수록 높다.
4. **위험:** 조건이 성립하지 않을 위험이 크면 낮춘다(V1·V2).

## 7. 실험별 상세 조건

### 7.1 공통 규칙

- 모든 실험은 새 profile과 freeze로 만든 캠페인에서 실행한다. 복구 정책·임계값(S1 `POLICY`, S2 진단·안정 조건, S3 펜싱 조건, S4 MHC 설정)은 바꾸지 않는다.
  바꾸는 것은 장애 조건을 만드는 시험 도구와, 비교군에서 생략하거나 대체하는 조치뿐이다.
- 각 실행은 먼저 **조건 성립**을 원본으로 판정하고, 그다음 결과를 판정한다. 조건이 성립하지 않은 실행은 `조건 불성립`으로 남긴다.
- 기대 결과는 가설이다. 기대와 다른 결과도 그대로 판정하고 보고한다.
- 시험이 만든 자원(Pod, QoS 정책, taint, MHC 변경, VM 상태)은 실행 ID로 소유를 표시한다. 정리는 소유를 확인한 뒤 원래 상태로 복원한다.
  정리 검증이 통과해야 다음 회차로 넘어간다.
- 관측 연장형(S3-B0·S3-B1·S4-B0)의 관측 시간은 10분으로 고정한다. 그 안에 회복되지 않으면 `미회복`으로 판정한다.

### 7.2 S1 CPU 경합

**S1-P 자동 (재측정)**
- 조건·측정·판정: 기존 평가 계약과 같다. 4 vCPU 경쟁 VM, 5 RPS, 요청당 100,000 round, 1,080초.
- 역할: 같은 캠페인 안에서 S1-B1·S1-B2의 비교 기준.

**S1-B1 같은 worker 재시작 (C2-조치)**
- 조건: S1-P와 같은 경합과 같은 자동 진단.
- 대조 조치: 진단 확정 후 `nodeSelector`를 원천 worker로 고정한 채 rollout restart를 1회 실행한다.
  uid·resourceVersion 조건, maxSurge 1, maxUnavailable 0은 그대로 유지한다.
- 성립 판정: 새 Pod UID가 원천 worker·원천 compute에 있음. 재시작 후에도 경쟁 VM이 ACTIVE이고 원천 호스트 경합(CPU ≥70%, PSI 기준)이 지속됨.
- 가설: 회복 판정(30초 대기 + 60초 창 3회 연속) 미충족. 마지막 60초 p95가 무조치(기준선의 약 2.2배)와 비슷함.
- 판정: 회복 여부, 마지막 60초 p95 비율. S1-P와 4:4 Mann–Whitney 정확검정.
- 정리: 기존 S1 cleanup.
- 구현: `EvaluationS1`의 `same-worker-restart` 모드(`move_service` 대체).
- 결과 해석: 회복되면 S1 효과의 일부가 재시작으로 설명되므로, C2-조치 주장의 범위를 줄인다.

**S1-N1 V1: 호스트 경합, 서비스 정상 (C4)**
- 조건: 같은 경쟁 VM. 요청당 연산을 앱 최솟값인 10,000 round로 낮춘다.
- 성립 판정: 진단 창에서 원천 호스트 CPU ≥70%, PSI 기준 충족, p95 ≤ 기준선×1.5, 실패 증가 없음.
- 가설: 진단 미확정. 최대 6개 창 뒤 `deferred`, 사유 `service_impact_not_confirmed`, 조치 0.
- 위험과 대안: 가벼운 요청도 1.5배 넘게 느려질 수 있다. 예비 1회로 확인하고, 실패하면 경쟁 부하를 4→3개 프로세스로 줄여 한 번 더 확인한다. 그래도 성립하지 않으면 "재현하지 못함"으로 기록한다.
- 구현: `host-only` 모드. 진단 미확정을 기대 결과로 수용하고 증명 파일을 남긴다.

**S1-N2 V2: 같은 worker 안의 Pod 간 경쟁 (C4)**
- 조건: 경쟁 VM 대신 원천 worker에 CPU 부하 Pod(시험 소유, `nodeName` 고정, 자원 제한 없음)를 띄운다.
- 성립 판정: p95 > 기준선×1.5. 원천 호스트 CPU <70% 또는 PSI 기준 미달.
- 가설: 진단 미확정, 사유 `host_contention_not_confirmed`, 조치 0.
- 위험: worker VM 포화로 호스트 PSI가 기준을 넘으면 모듈이 재배치할 수 있다. 그 경우 `오조치`로 기록하고 PSI 상승 경로를 분석한다.
- 정리: 부하 Pod를 소유 확인 후 삭제.
- 구현: `service-only` 모드(경쟁 VM 생성·정리를 부하 Pod로 대체).

**S1-B2 사람 런북 (C5)**
- 진행: [최종 평가 잔여 계획](final-plan-2026-10-25.md) 2절의 프로토콜을 따른다(증상만 통보, 허용 도구, 녹화, 표시 명령, 15분 제한, 연습 1회).
- 부하 시간: 1,800초(사람 대응 시간을 담기 위해 연장). 비교 기준 S1-P도 같은 캠페인에서는 같은 부하 시간으로 측정한다.
- 사람이 하는 일: 영향 확인 → Pod→Node→Machine→providerID→Nova→compute 추적 → 호스트 CPU·PSI 확인, 다른 원인 배제 → 다른 compute의 적격 worker 선택 → 공통 변경 도구로 1회 변경 → 회복 관찰과 완료 선언.
- 측정: 증상 → 판단 → 변경 → 배치 준비 → 안정화. 조회·변경 명령 수, 정정 횟수, 목적지 정확성.
- 구현: `manual` 모드, 공통 변경 도구, 표시 명령, 녹화 집계.

### 7.3 S2 송신 혼잡

**S2-P 자동 (재측정) + S2-B1b 공유 포트 QoS만 (C2-조치)**
- 조건: 기존 S2와 같음(API 2 RPS, 256 KiB 응답, 공통 출구 20 Mbit/s).
- 추가 창: 무제어 진단 직후, **업로드를 분리하기 전에** API와 업로드가 함께 있는 worker A의 포트에 고정 10 Mbit/s·burst 250 kbit QoS를 적용한다. 60초 창 1개(`shared-port-qos`)를 측정한 뒤 정책을 해제하고, 이후 기존 흐름(분리 → 고정·동적 비교 → 분리만 창)을 그대로 진행한다.
- 성립 판정: Neutron 값과 worker A의 OVS `ingress_policing_rate`가 10,000으로 확인됨. 측정 중 두 Pod가 모두 worker A에 있음.
- 가설: 포트 제한이 API 응답 트래픽까지 함께 깎아 p95가 안정 기준(기준선×1.3)을 넘거나 실패가 생긴다. "분리만"(K8s 조치만)과 "QoS만"(OpenStack 조치만)이 둘 다 미회복이면 두 계층 조치가 모두 필요하다는 근거가 된다.
- 안전: 제한값 하한 6 Mbit/s를 지킨다. worker 관리 통신(kubelet)이 끊기지 않는지 Node Ready로 확인한다. 해제 후 OVS 값이 제거됐는지 확인한다.
- 판정: 같은 실행 안에서 `shared-port-qos` 창과 분리+QoS 창을 짝 비교한다.
- 구현: S2 평가 변형에 창 추가. 측정 순서가 바뀌므로 새 profile에서만 사용한다.

**S2-N1 CPU 원인 지연 (C4)**
- 조건: 업로드 없이 API worker에 CPU 부하 Pod를 띄운다.
- 성립 판정: p95 > 기준선×1.5. 공통 출구 <16 Mbit/s, overlimits 증가 없음.
- 가설: 진단 미확정(`service impact and shared egress contention not established`), QoS 정책 변경 0.
- 위험: 256 KiB 응답 API가 CPU 부하로 충분히 느려지지 않을 수 있다(조건 불성립 위험).

**S2-B2 사람 런북 (C5)**
- 사람이 하는 일: 영향 확인 → Pod·호스트 CPU 정상 확인 → 호스트에서 출구 카운터(`tc -s qdisc`) 확인 → 업로드 Pod→Node→VM→Neutron 포트 연결 → QoS 정책 생성·적용 → 적용 확인(Neutron, OVS) → 업로드 이동 → API를 보며 제한값 조정 → 완료 선언.
- 사람이 만든 정책은 실행 ID 태그를 붙이게 하고, 정리는 태그로 찾아 제거한다.
- 측정: 같은 항목에 더해 최종 제한값과 업로드 처리량. 사람이 고정값에서 멈추는지 기록한다.

### 7.4 S3 통신 두절·DB

**S3-P 자동 (재측정)**
- 조건·측정: 기존과 같다. controller-manager의 시간 초과 강제 분리는 시험 중 비활성(기존 정책).

**S3-B0 Kubernetes 기본 동작 (C1)**
- 조건: 같은 장애(kubelet→API 6443, DB 5432 차단)를 주입한다. 펜싱·out-of-service를 하지 않는다. controller-manager는 **기본 설정**(강제 분리 활성)으로 둔다.
- 관측 10분: DB Pod 상태(Terminating 고착 여부), StatefulSet 대체 Pod 생성 여부, VolumeAttachment와 Cinder 연결, 6분 강제 분리 발생 시각, 기존 DB 컨테이너 생존(게스트 crictl), DB 접속.
- 가설: 대체 Pod가 Ready가 되지 않는다(미회복). 강제 분리가 일어나면 기존 DB가 살아 있는 상태에서 볼륨이 분리되는 위험 상태가 관측된다.
- 안전: 시험 소유 DB와 볼륨만 사용한다. 데이터 무결성은 주장하지 않는다. 관측 후 기존 S3 cleanup으로 장애 해제, VM 재시작, 자원 제거를 한다.
- 구현: S3 평가 변형 `k8s-default`(펜싱·out-of-service 단계 생략, controller 정책 변경 생략, 관측 루프 추가).

**S3-B1 펜싱만 (C2-조치)**
- 조건: 같은 장애. 기존과 같이 펜싱(Nova stop + SHUTOFF·power_state·libvirt 확인)을 한다. **out-of-service taint는 적용하지 않는다.** controller-manager 정책은 S3-P와 같이 강제 분리 비활성으로 두어, 차이를 out-of-service 하나로 제한한다.
- 성립 판정: 원천 VM 종료 확인, out-of-service taint 없음.
- 관측 10분: 기존 Pod 상태, 대체 Pod, VolumeAttachment.
- 가설: VM은 꺼졌지만 Kubernetes가 기존 Pod 정리를 마치지 못해 대체 Pod가 뜨지 않는다(미회복). OpenStack 조치만으로는 Kubernetes 복구가 시작되지 않는다는 근거가 된다.
- 구현: `fence-only` 모드(`activate_recovery`에서 `mark_out_of_service` 생략).

**S3-N1 일시 NotReady (C4)**
- 조건: 같은 장애를 주입하되, 게스트 안에서 자동 해제를 예약한다. 해제 시각은 NotReady 확인 후 20초 이내가 되도록 장애 주입 후 약 90초로 정하고, 예비 1회로 조정한다.
- 성립 판정: Node가 NotReady가 된 뒤 다시 Ready로 돌아옴. 통신 차단 지속 시간이 기록됨.
- 바람직한 결과: 펜싱하지 않음.
- 예상되는 실제 결과: 현재 정책은 NotReady 확인 후 DB 검사 15회 연속 실패면 곧바로 펜싱하고, 지속 시간 조건이 없다. 해제 시각이 검사 구간보다 늦으면 **펜싱할 가능성이 높다.** 그 경우 `오조치`로 기록하고, 지속 시간 조건 부재를 정책 한계로 보고한다. 정책은 이번 평가에서 고치지 않는다.
- 안전: 펜싱이 일어나면 기존 S3 cleanup으로 VM을 재시작한다.
- 구현: 장애 주입 스크립트에 예약 해제를 추가한 `transient` 모드.

**S3-B2 사람 런북 (C5)**
- 사람이 하는 일: DB 실패·NotReady 확인 → 펜싱 필요성 판단 → MHC remediation 예외 설정 → `openstack server stop` → SHUTOFF, task_state, power_state, 하이퍼바이저 domstate 확인 → 재확인 후 out-of-service taint → 대체 Pod·VolumeAttachment 감시 → 기존 레코드와 새 트랜잭션 검증.
- 측정: 시간 항목에 더해 **안전 순서 준수**(종료 확인 전 taint 여부, 하이퍼바이저 확인 생략 여부, 예외 설정 누락)를 주 지표로 기록한다.
- 안전: 사람이 순서를 어겨도 시험 소유 DB이므로 위험은 시험 범위에 한정된다. 실행기는 강제 삭제·강제 detach 명령을 허용 도구에서 제외한다.

### 7.5 S4 worker VM 중단

**S4-P 자동 (재측정)**
- 조건·측정: 기존과 같다(worker 전용 MHC, 120초, 동시 교체 1대).

**S4-B0 MHC 없음 (C1, C2-조치)**
- 조건: S4 준비에서 MHC를 만들지 않는다. Cluster Autoscaler는 기존과 같이 fixed 모드로 잠근다. 나머지는 같음.
- 관측 10분: HTTP 서비스, Node·Machine 상태, Nova VM 상태, worker Ready 수.
- 가설: Kubernetes가 Pod를 남은 worker로 옮겨 서비스는 회복된다(`부분 복구`). 용량은 관측 시간 내내 worker 1대로 남는다.
- 판정: 서비스는 기존 지표로, 용량은 "목표 worker 수 Ready 미달 지속"으로 판정한다.
- 정리: 관측 후 원 VM을 `openstack server start`로 재기동해 Node Ready를 확인한 뒤 기존 S4 cleanup을 한다.
- 구현: S4 준비·실행에 MHC 생략 옵션.

**S4-N1 V3: 대상 관계 불일치 (C4, C2-판단)**
- 조건: 준비 후 VM 정지 직전, 기록된 대상 관계 중 하나(Machine의 providerID와 기록된 Nova ID)가 일치하지 않는 상태를 시험 소유 범위에서 만든다.
- 가설: VM 정지 거절, 정지 0회, 불일치 사유 기록.
- 비고: 불일치를 현실적으로 만드는 방법을 정해야 해서 설계 비용이 있다.

**S4-N2 일시 VM 중단 (C4)**
- 조건: VM을 정지하고, 정지 확인 후 일정 시간 뒤 같은 VM을 재기동한다. Node unhealthy 지속이 MHC 대기 120초보다 짧도록 재기동 시점을 예비 1회로 정한다(초안: 정지 확인 후 30초).
- 성립 판정: Node가 unhealthy → Ready로 돌아오고, unhealthy 지속 시간이 120초 미만.
- 가설: MHC가 Machine을 삭제하지 않는다. 기존 Machine·Node UID 유지. 서비스는 toleration 30초에 따라 Pod가 이동할 수 있다.
- 판정: Machine 삭제 0이면 `정확한 보류`, 삭제되면 `오조치`.

**S4-B2 사람 런북 (C5)**
- 조건: MHC 없음(S4-B0와 같음).
- 사람이 하는 일: HTTP 실패 확인 → Node NotReady, VM SHUTOFF 확인 → 재기동할지 교체할지 판단 → 서비스 회복 확인 → 교체를 택하면 `kubectl delete machine`으로 CAPI가 새 VM을 만들게 하고, 재기동을 택하면 `openstack server start` → 새 Node Ready와 시험 Pod 실행 확인.
- 측정: 서비스·용량 복원 시간, 선택한 방법, 명령 수.
