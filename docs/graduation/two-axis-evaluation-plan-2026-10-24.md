# 두 축 평가 계획과 S1 수동 런북

작성일: 2026-10-24.
기준 구현: `b82711bff50d68195d8f1058760b4771631e878f`.
상태: 추가 평가 설계안. 수동 실행 진입점·운영자 기록 기능은 아직 구현하지 않았다.
이 문서는 기존 변경을 커밋한 뒤 작성했으며, 그 커밋에 포함되지 않는다.
보고서의 연구 질문 구성과 이 계획의 대응은 [평가 설계](evaluation-design-2026-10-25.md)를 따른다.
이 문서의 실험 계약(3절)과 S1 사람 런북(4절)은 그대로 유지한다.

## 1. 목적과 범위

작품의 목표는 OpenStack과 Kubernetes의 상태·자원 관계를 연결하여, 정의된 장애에
적합한 복구 절차를 수행하고 실제 서비스 회복까지 검증하는 프로토타입 구현이다.
시나리오와 복구 정책·안전 조건을 유지하고, 평가 도구와 비교 방법을 보완한다.

| 평가 축 | 질문 | 대표 근거 |
|---|---|---|
| ① 자동 대응의 유효성 | 적절한 조건에서 올바른 대상에 조치하고 실제로 회복시키는가? | 성능·회복 여부, 데이터 보존, 안전한 보류·거절, 오조치·개입 기록 |
| ② 운영 작업 자동화의 효과 | 같은 절차를 사람이 수행할 때보다 시간·작업 부담이 줄어드는가? | 수동·자동 복구 시간, 판단·조치 시간, 운영자 작업 시간·개입·정정 횟수 |

①을 주평가로 삼고 ②는 S1의 제한된 수동 비교로 보완한다. S2·S3의 인간 비교는
확장 항목이며, S4의 기존 제어기 복구 속도를 작품의 속도 개선 효과로 주장하지 않는다.
자동으로 올바르게 처리했다는 사실과 사람보다 효율적이라는 주장을 구분한다.

앞서 검토한 신청서는 동일 장애의 수동·자동 반복 실행과 복구 시간·성공률 비교를 제시했다.
중간보고서는 S1 무조치·자동 비교를 필수 범위로 구체화하고,
수동 비교는 가능한 경우 수행하되 제외 시 사유를 남기도록 했다. 3월 신청서 메일에서도
수동·자동 비교를 평가 대안으로 제안했으므로, 이번 S1 비교는 그 계획을 보완한다.
중간보고서의 평가 범위 변경에 대한 교수님의 별도 동의 여부까지 확인된 것은 아니다.

## 3. 공통 실험 계약

### 3.1 비교 조건

- 새 수동 비교는 수동·자동군을 모두 새로 측정한다. 기존 자동 결과와 새 수동 결과만을
  짝지어 비교하지 않는다. 기존 결과는 별도 실험의 근거로 참조한다.
- 초기 배치, VM 사양·CPU 플랫폼, 이미지, 요청 부하, 경합 부하, 정책·안전 조건과
  회복 판정 기준을 고정한다. 준비 후 조건이 달라지면 본시험을 시작하지 않는다.
- 수동·자동 순서를 교대 또는 사전 무작위 배정하고, 매 실행 후 초기 상태를 확인한다.
- 사람에게 원인이나 목적지 정답을 미리 알려주지 않는다. 같은 관측 정보와 조회 도구는 제공한다.
  증상 알림은 공통 서비스 관측에 근거하며 자동군의 최종 진단 결과를 수동군에 넘기지 않는다.
- 수치 계산·자료 조회·안전한 단일 변경은 도구로 지원할 수 있다. 원인 판단과 목적지 선택,
  다음 복구 단계 진행 여부를 도구가 대신하면 해당 구간을 인간 수행으로 세지 않는다.
- 예비 실행에서 입력·관측 시각, 표본 구간과 사용 도구를 점검한 뒤 본시험 계약을 고정한다.
  예비 결과는 본시험에 섞지 않는다. 결과를 본 뒤 유리하게 임계값·횟수를 변경하지 않는다.

### 3.2 사건과 시간

| 사건 | 정의 |
|---|---|
| `fault_intent_at` | 장애 주입을 요청한 시각 |
| `fault_confirmed_at` | 장애 부하·상태가 실제 시작됐음을 확인한 시각. 확인 불가능하면 결측으로 남김 |
| `first_impact_at` | 사전에 정한 서비스 영향 조건이 공통 관측에서 처음 확인된 시각 |
| `symptom_notice_at` | 서비스 증상 정보가 대응 주체에게 제공된 시각 |
| `decision_at` | 조치 필요성과 대상 선택을 확정하거나 보류한 시각 |
| `action_started_at` | 최초 복구 변경 요청 시각 |
| `placement_ready_at` | 의도한 배치에서 새 Pod가 준비된 것을 확인한 시각 |
| `service_stable_at` | 공통 회복 기준이 충족된 시각 |
| `operator_declared_complete_at` | 사람이 완료라고 판단한 시각. 객관적 성공 판정과 별도로 기록 |
| `final_verified_at` | 자원·배치·데이터 등 전체 완료 조건의 검증 시각 |

주입 요청, 실제 장애 확인, 서비스 첫 영향은 다른 사건이다. 확인되지 않은 사건 시각을
다른 시각으로 조용히 대체하지 않는다. S1 영향은 요청 실패만이 아니라 지연 기준 초과도 포함한다.
시각은 공통 기준으로 기록하고, 관측 경로·주기·지연과 시계 오차를 명시한다.

주지표는 장애 시작 확인→서비스 안정화와 정상 완료 여부다. 첫 서비스 영향→안정화,
증상 통보→조치 시작, 조치 시작→배치 준비, 배치 준비→안정화를 함께 제시한다.
고정 안정화 확인 구간을 포함한 총시간과 단계별 시간을 모두 보여주고 유리한 구간만 선택하지 않는다.

### 3.3 개입·판정·실패 처리

- 복구 구간과 준비·관측·정리 등 평가 운영 구간의 사람 개입을 분리해 기록한다.
  전체 무개입 운영을 주장할 때는 두 범위를 모두 포함한다.
- 운영자 작업 시간에는 자료 읽기·판단·명령·확인을 포함한다. 작업·대기 구간을 기록하고
  명령 실행 시간의 합만을 운영자 작업 시간으로 사용하지 않는다.
- 개입은 의미 있는 조회·판단·명령 제출·정정·외부 도움 단위로 정의한다. 복사·붙여넣기를
  금지하거나 불필요한 타이핑을 강제하지 않는다. 공통 시험 시작 동작도 동일 규칙으로 센다.
- 실제 사람이 필요한 단계는 사용자가 수행한다. AI가 수행하거나 판단을 알려주면 그 사실을
  개입 기록에 남기며, 인간 단독 런북 실행으로 취급하지 않는다.
- 판정은 정상 완료, 기대한 보류·거절, 복구 실패, 시간 초과, 측정 불완전으로 구분한다.
  안전한 거절을 서비스 복구 성공으로 합산하지 않는다.
- 본시험 시작 이후 실패·중단·재시도·개입은 분모와 이력에 남긴다. 재측정은 별도 attempt로
  연결하고 이전 기록을 없애지 않는다. 장애 주입 전 준비 실패도 별도 준비 이력에 남긴다.
- 미회복 시간에 무한대나 시간 제한값을 임의 대입해 단축률을 계산하지 않는다.
  성공 실행의 시간 통계와 전체 실행의 성공·실패·미완결 수를 함께 제시한다.
- 기존 34건의 무개입 여부는 로그로 재감사한다. 판별 불가는 추정하지 않고 확인 불가로 표시한다.

## 4. 축 ②: S1 사람 런북

### 4.1 상황과 역할

서로 다른 compute에 기존 worker 두 대를 준비하고 한 worker에 시험 API를 배치한다.
같은 compute의 별도 VM에서 CPU 경쟁 부하가 발생하며 Pod·Node가 정상인 상태에서도
API 응답이 느려진다. 목적은 기존 다른 worker로 안전하게 재배치하여 응답 목표를 회복하는 것이다.

시험 도구는 준비·기준선·부하·장애 주입·원본 수집을 담당한다. 운영자는 서비스 증상 알림과
조회 자료를 보고 원인 근거·대상·목적지·조치를 판단한다. 평가용 관측은 장애 대상 worker 밖에서
동일 경로로 수행한다. 준비·공통 정리 시간은 서비스 복구 시간과 분리하되 전체 운영 이력에는 남긴다.

### 4.2 수행 순서

| 단계 | 확인할 내용 | 사람이 실행할 작업 | 측정·증거 |
|---|---|---|---|
| 1. 서비스 영향 | 정상 기준선 대비 지연 증가와 자료 완전성 | 요청 통계 조회, 관측 창 확인 | 확인 시작·p95·요청·오류 수 |
| 2. 계층 추적 | Service→Pod→Node→Machine→Nova VM→compute 관계 | Kubernetes 자원과 OpenStack VM 배치 조회 | 선택한 UID·providerID·VM ID·compute, 판단 시각 |
| 3. 원인 판단 | CPU·PSI와 서비스 영향의 동시 지속, 다른 원인 후보 | 호스트·Pod CPU와 메모리·I/O 압박 조회 | 사용한 표본, 판단·보류 이유 |
| 4. 목적지 선택 | 다른 compute의 Ready·배치 가능 worker와 자원 여유 | Node·Pod 요청량, taint·affinity·selector, 호스트 지표 확인 | 후보별 적격 여부·이유, 선택한 목적지 |
| 5. 변경 전 재확인 | 소스·경쟁 VM·Deployment가 조회 이후 변경되지 않았는지 | 최신 UID·resourceVersion·배치 조회, 단일 재배치 명령 제출 | 변경 전후 spec, 명령 시각·결과 |
| 6. 배치 확인 | 새 Pod가 선택한 worker에 준비되고 필요한 설정이 유지되는지 | rollout과 Pod·VM 배치 조회 | 새 Pod·Node·VM·compute, Ready 시각 |
| 7. 회복 판단 | 소스 경합이 지속되는 가운데 API가 안정화되는지 | 공통 관측 자료 확인, 운영자 완료 판단 기록 | 객관적 안정화 시각과 사람 판단 시각 |

조회에는 `kubectl get`과 `openstack server show` 등 기존 도구를 사용한다.
수동용 조회·계산 보조 도구는 원인이나 목적지를 자동 선택하지 않는다.
복구 동작은 `graduation-s1` 네임스페이스의 `http` Deployment에서
`kubernetes.io/hostname` 배치 조건을 변경하는 현재 방식과 동일하게 한다.
replicas 1, RollingUpdate의 maxSurge 1·maxUnavailable 0 및 다른 workload 설정을 유지한다.
UID·resourceVersion 확인과 갱신 충돌 거절, cooldown 기록은 공통 변경 도구가 보장한다.
기존 자동 실행을 한 번 호출하는 행위를 수동 대응으로 세지 않는다.
배치 진행은 `kubectl -n graduation-s1 rollout status deployment/http --timeout=5m`으로
확인할 수 있지만, 명령 성공만으로 서비스 회복을 판정하지 않는다.

### 4.3 현재 정책을 그대로 적용할 판단 기준

근거: [S1 자동 정책](../../experiments/graduation_s1_auto.py)의 `POLICY`, `diagnose`,
`candidate_reasons`, `stable_window`.

- 지연형 경합에서는 p95가 정상 기준선의 1.5배를 초과하고 호스트 CPU 사용률이 70% 이상,
  CPU PSI가 `max(2%, 기준선 PSI의 2배)` 이상이어야 한다.
- 60초 관측 창 2회 연속 근거를 확인한다. 실제 코드에는 기준선보다 요청 실패가 증가하는
  경로도 있으므로 실패가 있는 경우 p95 조건만으로 판단을 대체하지 않는다.
- 기존 5 RPS 설정에서는 60초 창마다 최소 270개 요청, 중복 인덱스 0개, 최대 표본 간격
  2.5초 이하가 필요하다. 요청 강도와 전체 관측 기간은 두 비교군에 동일하게 고정한다.
- 창별 요청 수·중복·공백을 검증한다. Pod throttling, 메모리·I/O 압박 또는 불충분한
  여유 메모리가 있으면 이번 CPU 경합 정책의 근거로 성급하게 단정하지 않는다.
- 목적지는 다른 compute의 Ready·schedulable worker이며 control plane은 제외한다.
  taint/toleration, selector/affinity, CPU·메모리 요청량을 충족해야 한다.
- 목적지 호스트 CPU <70%, CPU·메모리·I/O PSI <2%, 가용 메모리 ≥512 MiB,
  관측 자료 나이 ≤90초 등 현재 조건을 그대로 적용한다.
- 여러 적격 후보가 있으면 현재 정책과 같이 CPU 사용률, Node 이름 순으로 선택한다.
  적격 목적지가 없거나 최근 조치의 900초 cooldown 조건에 걸리면 보류하고 이유를 남긴다.
- 회복은 재배치 완료 후 30초 대기, 이후 60초 창 3회 연속 요청 실패 없이 p95가
  기준선의 1.2배 이하이고 표본 수·연속성이 충족되는 것으로 판정한다.
  마지막 측정 창의 안정화, 새 배치·설정 유지 및 소스 경합 지속도 검증한다.

운영자가 조기 완료를 선언해도 공통 관측 기준이 충족되지 않으면 성공으로 처리하지 않는다.
180초 이상의 확인 구간 때문에 전체 시간 차이가 작을 수 있으므로 사람의 판단·작업 시간과
시스템의 고정 대기·검증 시간을 분해한다.

### 4.4 비교 실행과 해석

초기 본시험안은 수동 5회·자동 5회의 5쌍이다. 짝별 조건을 맞추고 순서를 사전 배정한다.
연습과 예비 실행은 별도 기록한다. 최종 횟수·시간 제한·표본 수집 기간은 예비 점검 후
본시험 전에 고정하며, 한쪽만 더 긴 회복 시간을 허용하거나 관측을 연장하지 않는다.

개발자 1인의 런북 수행은 제한된 사례 비교로 보고한다. 결과를 일반 운영자의 숙련도나
운영 환경 전체의 신뢰성으로 일반화하지 않는다. 성공한 쌍에서 시간의 절대 차이와 절감률
`(수동-자동)/수동×100`을 산출하고, 실패·시간 초과가 포함된 쌍은 별도 결과와 함께 제시한다.
절감되지 않거나 자동군이 느린 결과도 그대로 보고한다. 5회 통과는 희귀 실패율의 정밀 추정이 아니다.

## 5. 축 ①: 시나리오별 측정·원본·판정

### 5.1 S1: 경합 판단과 재배치 효과

| 측정 대상 | 원본 데이터 | 확인할 결과와 평가 측면 |
|---|---|---|
| 서비스 영향·회복 | `http.jsonl`, 기준선·경합·이동 후·마지막 창 | 무조치 대비 지연, 기준선 대비 비율, 오류, 안정화 시간 |
| 판단 근거 | `hosts-*.json`, Pod CPU 통계, `decisions.jsonl` | 서비스 영향·CPU/PSI·다른 압박 배제 근거의 동시 성립 |
| 대상·조치 | 후보 기록, VM 배치, Deployment·Pod 변경 전후 | 올바른 목적지, 조치 횟수, 의도하지 않은 변경 여부 |
| 회복의 타당성 | 이동 뒤 소스 호스트 지표와 경쟁 VM 상태 | 경쟁 부하가 종료돼 우연히 회복한 것으로 설명되지 않는지 |
| 보류의 적절성 | 정상·근거 부족·목적지 부재 조건의 기록 | 불필요한 재배치 0회, 구체적 보류 사유, 기존 workload 보존 |

기존 자동·무조치 결과는 재배치라는 조치 전체의 효과로 해석한다. 요청 생성기와 서비스의
상대 배치·경로 변화가 있으므로 모든 지연 감소를 CPU 경합 제거 하나의 효과로 단정하지 않는다.
추가 음성 대조는 CPU만 높고 서비스는 정상인 경우와 서비스 지연만 있고 CPU 경합 근거가
부족한 경우다. 실제로 그 조건이 성립했는지 원본으로 먼저 검증한다. 합성 입력 테스트를
실환경 결과로 기재하지 않으며, 조건이 성립하지 않은 실행도 준비·유효성 판정 이력에 남긴다.

### 5.2 S2: 서비스 보호와 업로드 효율

| 측정 대상 | 원본 데이터 | 확인할 결과와 평가 측면 |
|---|---|---|
| API 성능 | 각 60초 창 JSON의 요청별 지연·성공 여부 | 무제어·분리만·고정·동적 조건의 지연과 오류 |
| 업로드 | 수신 byte 차이, 청크 manifest·크기·체크섬 | 서비스 회복과 동시에 진행되고 데이터가 올바른지 |
| 혼잡 근거 | qdisc bytes·overlimits·elapsed, 호스트 CPU | 공통 출구 혼잡이 있고 CPU 경합으로 혼동하지 않았는지 |
| 정책 적용 | 동적 판단·변경 기록, Neutron 포트·OVS 값 | 올바른 포트에 실제 제한 적용, 관측과 조정의 연결 |
| 오류 처리 | API 오류, 변경 의도와 실제 정책 상태, 정리 기록 | 부분 적용을 완료로 오판하지 않고 오류·잔여 상태를 보존하는지 |

현재 `stable`은 구간당 완전한 120개 요청, 오류 0, p95≤기준선×1.3, 업로드 증가를 요구한다.
동적 정책은 6/10/14/18 Mbit/s 범위에서 관측에 따라 움직인다. 고정 10 Mbit/s와 동적 정책의
두 안정 구간을 비교한다. p95 지표는 두 창의 p95 평균이며 전체 요청을 합친 p95가 아니다.
같은 서비스 보호 조건을 충족하면서 업로드를 얼마나 확보했는지 평가한다. 고정 정책보다
동적 정책의 지연이 조금 높다는 tradeoff도 남긴다. 사람 대비 작업 절감으로 바꾸어 해석하지 않는다.

### 5.3 S3: 안전한 상태 저장 서비스 복구

| 측정 대상 | 원본 데이터 | 확인할 결과와 평가 측면 |
|---|---|---|
| 실제 영향 | `fault-impact.json`, 기존 DB 프로세스 상태 | 서비스 접근 실패와 기존 실행 생존이 함께 존재하는지 |
| fencing | `fence.json`, VM·compute 식별자, 단계별 시각 | 해당 VM의 Nova·hypervisor 종료 확인 후 다음 조치를 수행했는지 |
| 저장소 관계 | `volume-before/after.json`, PVC·PV·VolumeAttachment 기록 | 같은 볼륨의 원래 연결과 목적지 단독 연결, 올바른 대상 |
| 데이터·서비스 | 커밋 전후 JSON, 새 transaction, `stabilization.json` | seed에 맞는 1,000건 전후 일치, 새 읽기·쓰기, 60개 연속 DB 검사 성공 |
| 보류·중단 | 거절 근거·원본 상태·오류·재개 기록 | 종료 미확인·중간 오류에서 위험한 조치나 중복 실행을 피하는지 |

장애 주입 의도→DB Ready와 종료 확인→DB Ready를 각각 기록한다. 명령·폴링을 포함하는
관측 시간이지 연속 클라이언트로 측정한 정밀 RTO가 아니다. 특정 커밋 데이터 보존은 모든
쓰기 패턴의 무손실을 뜻하지 않으며, 상태 스냅샷만으로 미관측 구간의 동시 연결 부재를 단정하지 않는다.
순서·종료 증거와 연결 상태를 함께 대조한다.

기본 제어만 적용한 비교는 이번 필수 범위가 아니다. 이를 추가하려면 현재 S3가 사용하는
복구 소유권과 제어기 조정 조건부터 확인하고, 다른 설정 차이가 섞이지 않는 비교 계약이 필요하다.
현재 자동·스크립트 런북의 시간 차이로 기본 제어기 또는 사람 대비 우월성을 주장하지 않는다.

### 5.4 S4: 통합 실행과 완료 판정의 정확성

| 측정 대상 | 원본 데이터 | 확인할 결과와 평가 측면 |
|---|---|---|
| 대상 연결 | Pod·Node·Machine UID와 Nova ID, 준비·주입 기록 | 올바른 VM만 중단하고 불일치 시 거절하는지 |
| 서비스 | `http.jsonl` | Ready 표식과 실제 연속 정상 응답을 구분하는지 |
| 용량 | `observations/*.json`, 새 Machine·Node·VM·시험 Pod | 서비스만 회복한 상태와 목표 용량 복원을 구분하는지 |
| 중단·재개 | 실행 ID·stop 의도·확인·재개·관측 공백 | 중복 주입 없이 이어가고 공백을 정상 관측으로 채우지 않는지 |
| 정리 | `finalization.json`, 원래 상태와 소유 자원 | 자신의 시험 자원·정책만 제거하고 복원하는지 |

HTTP는 연속 정상 30초 이상, 표본 20개 이상, 인접 정상 표본 간격 2.5초 이하를 요구한다.
용량은 목표 worker와 새 worker의 실행 가능 상태를 원본에서 30초 이상 확인한다.
Pod Ready·첫 정상 응답·서비스 안정화·용량 안정화 시각을 분해하여 성급한 완료 판단의
가능성을 설명한다. 기존 제어기의 복구 시간을 자체 모듈의 개선 효과로 계산하지 않는다.
관측 경로는 API Service proxy이며 일반 ingress 서비스의 복구 시간으로 환산하지 않는다.

- 운영자 작업·대기 구간, 명령 결과, 개입·정정·외부 도움.
- 기대 판정, 실제 판정, 실패·시간 초과·관측 공백·재시도 관계, 정리 결과.
- 원본 해시와 독립 재계산 결과. 외부 기관 인증이 아닌 별도 코드에 의한 검산임을 명시.

보고서는 ① 기존 S1·S2 성능 효과 ② 안전 조건과 불필요한 조치 방지 ③ S1 수동·자동 시간·작업량
④ 실패·개입·적용 한계의 네 부분으로 구성한다. 시간·성능의 중앙값·범위와 각 실행을 함께
제시하며, 단일 환경·개발자 1인·소수 반복의 한계를 적는다. 오류 주입 조건의 안전한 거절률을
정상 서비스 복구율과 합산하지 않는다. 사람의 작업 시간 절감과 서비스 복구 시간 단축은 별도 주장이다.
