기준 결과: 캠페인 `graduation-evaluation-20261023T070441Z-30fdde87`(활성 34건).
상태: 최종 보고서의 실험·분석 장 구성을 위한 설계안. 실험 범위·우선순위는 [완전 평가 계획](complete-evaluation-plan-2026-10-25.md)을 따른다. 이 문서의 작성은 새 분석·실험의 완료를 뜻하지 않는다.

## 1. 목적

기존 문서는 무엇을 어떻게 측정할지(실행 계약·독립 검증)를 정의한다. 이 문서는 작품의 주장을
검증 가능한 질문으로 분해하고, 질문별 평가 기준·지표·원본·분석 방법을 연결한다.
보고서의 실험 및 분석 결과와 결론은 이 질문 순서로 구성한다.

### 2.1 두 축 계획과의 대응

두 축 계획의 ①·②는 모두 "모듈이 잘 동작하는가"를 묻는다. 작품의 핵심 주장인
"두 계층의 정보·제어를 함께 써야 복구할 수 있다"는 직접 다루지 않는다.
이 문서는 그 질문을 RQ1(필요성)·RQ2(교차 계층 기여)로 추가하고, 비용·trade-off를 RQ6으로 분리한다.

| 두 축 계획 | 이 문서 | 비고 |
|---|---|---|
| 없음 | RQ1 필요성, RQ2 교차 계층 기여 | 새로 추가. 대부분 기존 원본으로 분석 가능 |
| ① 성능·회복 여부 (5.1~5.4) | RQ3 복구 유효성 | 시나리오별 측정표를 그대로 사용 |
| ① 안전한 보류·거절, V1~V5 | RQ4 정확성·안전성 | 결정 행렬로 재구성 |
| ② S1 사람 런북 (H1, 4절) | RQ5 운영 효율 | 정적 런북 복잡도와 S3 해석을 앞에 둔다. H1은 사례 연구로 축소 가능 |
| 5.2 S2 tradeoff, 4.3 고정 확인 구간 | RQ6 비용·trade-off | 분리해 명시 |
| 3절 공통 실험 계약, 8절 기록 형식 | 7절 공통 원칙 | 그대로 따른다 |

두 축 계획의 사건 시각 정의(3.2), 개입·판정 규칙(3.3), S1 수동 수행 순서(4.2~4.4)는
이 문서가 대체하지 않는다. 새 실험을 수행할 때 그 계약을 따른다.

## 3. 주장의 분해와 연구 질문

| 주장 | 연구 질문 | 평가 기준 |
|---|---|---|
| C1 단일 계층 self-healing으로 복구되지 않는 장애가 있다 | **RQ1 필요성**: 기존 기능만으로 서비스 목표가 회복되지 않는가? | 무조치 시 미회복, 계층별 표준 신호의 정상·이상 |
| C2 판단·복구에 두 계층 정보가 모두 필요하다 | **RQ2 교차 계층 기여**: 한 계층의 정보·조치만 쓰면 실패하는가? | ablation 조건 대비 회복 여부 |
| C3 모듈이 서비스 수준까지 복구한다 | **RQ3 복구 유효성** | 성공률, SLO 충족, 복구 시간과 분해 |
| C4 위험·불필요한 조치를 하지 않는다 | **RQ4 정확성·안전성** | 결정 행렬, 의도하지 않은 변경 0, 데이터 무결성, 멱등성 |
| C5 수동 대응보다 운영 부담·시간을 줄인다 (신청서) | **RQ5 운영 효율** | 단계·도구·판단 지점 수, 수동·자동 시간 |
| C6 그 대가가 감당할 만하다 | **RQ6 비용·trade-off** | 지연·처리량, 고정 대기 비중, 파라미터 민감도 |

S4는 기존 제어기(MHC·CAPI·CAPO)를 사용한 시나리오다. RQ1·RQ2의 필요성 근거로 쓰지 않으며
RQ3·RQ4의 통합·완료 판정 정확성 사례로 보고한다.

## 4. RQ별 설계

### 4.1 RQ1 필요성

**계층별 신호 표.** 장애 구간에서 각 계층의 표준 신호가 보이는 상태를 원본에서 추출한다.

| 시나리오 | Kubernetes 신호 | OpenStack·호스트 신호 | 서비스 | 원본 |
|---|---|---|---|---|
| S1 | Node Ready, Pod Ready, throttling 여부 | 동일 compute 배치, host CPU·PSI | 지연 증가 | Node/Pod snapshot, `hosts-*.json`, `http.jsonl` |
| S2 | Node·Pod 상태 | qdisc bytes·overlimits, egress | 지연 증가 | 창별 JSON |
| S3 | NotReady, Pod 정리 상태 | VM ACTIVE, DB 프로세스 생존 | DB 접근 실패 | `fault-impact.json`, volume 기록 |
| S4 | NotReady, eviction | VM SHUTOFF | 일시 중단 | `observations/*.json`, `http.jsonl` |

표의 각 칸은 실제 원본 값으로 채운다. 예상과 다르면 예상이 아니라 원본을 기재한다.
원본 값으로 채운 표와 한계는 [A단계 분석](analysis-2026-10-25.md) 3절에 있다.

| 시나리오 | 기존 근거 | 공백과 보완 |
|---|---|---|
| S1 | 무조치 5회, 마지막 60초 p95 중앙값 171.086 ms(기준선 대비 2.2122배) | 없음 |
| S2 | 무제어 p95 중앙값 443.160 ms(기준선 100.514 ms) | 없음 |
| S3 | ACTIVE VM에서 out-of-service 거절 1회 | 기본 설정만 둔 경우의 관측 없음. (a) 장애 주입 후 Pod·VolumeAttachment를 관찰하는 1회 관측, 또는 (b) 정의서 [R6]·[R8] 근거와 거절 시험으로 논증. 위험한 강제 경로는 실행하지 않는다 |

### 4.2 RQ2 교차 계층 기여

| ID | 비교 | 조건 | 상태 |
|---|---|---|---|
| A1 | S2 무제어 → 분리만 → 분리 + QoS | 분리만은 업로드를 다른 worker로 옮긴 뒤 포트 QoS를 해제한 `split-unlimited` 구간 ([graduation_s2.py](../../experiments/graduation_s2.py)) | 집계 완료. 분리만으로 미회복 ([A단계 분석](analysis-2026-10-25.md) 1절) |
| A2 | S1 같은 worker 재시작 vs 다른 compute 재배치 | 같은 경합에서 같은 worker로 rollout restart. 재시작 효과와 호스트 변경 효과를 분리 | 새 실행 필요(2~3회) |
| A3 | 판단 규칙 replay | 기록된 창에 K8s 신호만·호스트 신호만·교차 계층 규칙을 재적용 | 오프라인 분석. 실환경 결과로 기재하지 않는다 |
| A4 | 계층 의존 행렬 | 탐지·원인 판단·대상 선택·안전 확인·조치·검증 단계별로 사용한 계층 정보와 API | 정성 분석. 가능하면 `decisions.jsonl` 등의 실제 참조 필드로 근거를 단다 |

A1에서 분리만으로 지연이 회복되지 않으면 Kubernetes 배치 조치만으로는 부족하고
Neutron QoS가 필요하다는 근거가 된다. 회복되면 그 결과를 그대로 보고하고 주장을 조정한다.
A2는 재배치 효과에 요청 생성기·배치 변화가 섞일 수 있다는 기존 한계를 줄인다.
A3에서 음성 조건 원본(V1·V2)이 없으면 오탐에 관한 결론은 논증 수준으로 제한한다.

### 4.3 RQ3 복구 유효성

| 시나리오 | 지표 | 기존 값(중앙값, 범위) |
|---|---|---|
| S1 | 마지막 60초 p95, 기준선 대비 비율, 진단→안정화 | 78.239 ms, 1.0338배, 254.151초(253.345~261.792) |
| S2 | 고정·동적 안정 구간 p95 | 107.312 / 114.343 ms |
| S3 | 커밋 레코드 보존, 장애 의도→Ready, 펜싱→Ready | 1,000건×5회, 147.080초, 47.475초 |
| S4 | 첫 실패→서비스 안정화, VM 종료→용량 안정화 | 106.799초(103.853~298.501), 246.557초 |

- 성공률은 정확 신뢰구간과 함께 쓴다. 5/5의 Clopper–Pearson 95% 구간은 [47.8%, 100%]다.
- **시간 분해.** 총시간과 구성 요소를 함께 제시한다.
  - S1: 진단→안정화의 약 85%가 정책상 확인 구간(30초 대기, 60초 창 3개)이고, 조치는 약 38초다.
  - S4: 서비스 복구 약 107초 중 대체 Pod 기동은 약 2초다. 나머지는 Kubernetes Node 감시,
    실험 서비스에 설정한 toleration 30초, 30초 안정 확인이다. 모듈의 속도 개선으로 해석하지 않는다.
  - S3: Node 이상 판정이 약 절반이고, 모듈의 펜싱·out-of-service 단계는 약 36초다.
  - 결과: [A단계 분석](analysis-2026-10-25.md) 2절.
- 최댓값(S4 298.501초, S1 기준선 144.211 ms, 경합 2,430.421 ms)을 회차별 표와 함께 남긴다.
  S4의 298.501·153.938초는 실패 없는 표본 공백·역순으로 고정 판정의 연속 구간이 다시 시작된 결과다.
  보조 지표(첫 안정 확인)와 함께 제시한다([A단계 분석](analysis-2026-10-25.md) 2.4절).

### 4.4 RQ4 정확성·안전성

결정 행렬로 정리한다. n은 실환경 실행 수이며 합성 테스트를 포함하지 않는다.

| 조건 | 기대 | 결과 | n |
|---|---|---|---:|
| S1 경합·영향·목적지 있음 | 재배치 1회 | 충족 | 5 |
| S1 목적지 없음 | 보류, 변경 0 | 충족 | 1 |
| S1 CPU 압박, 서비스 정상 (V1) | 보류 | 미실행 | 0 |
| S1 서비스 지연, 경합 근거 부족 (V2) | 보류 | 미실행 | 0 |
| S2 잘못된 QoS 요청 | 오류 전파, 기존 정책 보존 | 충족 | 1 |
| S3 VM ACTIVE | out-of-service 거절 | 충족 | 1 |
| S4 대상 관계 불일치 (V3) | VM 중단 0 | 미실행 | 0 |
| S4 중단 후 재개 | 중복 주입 0, 공백 보존 | 충족 | 1 |

- 지표: 조치한 실행 중 기대 조건을 충족한 비율, 보류·거절의 정확성,
  조치 전후 상태 diff의 의도하지 않은 변경 수, S3 데이터 보존과 볼륨 단독 연결, 재개 시 중복 조치 수.
- 안전한 거절은 복구 성공률에 합산하지 않는다.
- S1의 고유 기여는 경합 판단이므로 V1·V2가 가장 큰 공백이다. 두 축 계획 6절의 반복안을 따른다.
- 원본 기준 결정 행렬과 정확 구간은 [A단계 분석](analysis-2026-10-25.md) 4절에 있다.
  모듈 판단 25/25(95% 구간 [86.3%, 100%]), 모듈 거절 3/3, S4는 통합·시험 경로로 분리했다.

### 4.5 RQ5 운영 효율

신청서는 수동·자동 대응의 복구 시간과 성공률 비교를 계획했다. 다음 세 단계로 다룬다.

1. **정적 런북 복잡도.** 시나리오별 수동 런북에서 조회 명령 수, 변경 명령 수,
   사용 도구·계층 수(kubectl, openstack CLI, 호스트 접속), 판단 지점 수,
   식별자 매핑 단계 수(Pod→Node→providerID→VM→compute)를 센다. 사람 없이 재현 가능한 지표다.
2. **S3 해석.** 자동 147.080초와 스크립트 런북 141.708초는 차이가 작다.
   명령 단계를 이미 스크립트로 실행하면 실행 속도 차이는 작다. 자동화의 차이는 사람의 판단·반응
   시간과 안전 순서 준수에 있다는 분석으로 보고한다. 인간 대비 시간 단축을 주장하지 않는다.
3. **S1 사람 런북(H1).** 두 축 계획 4절을 따른다. 개발자 1인이 시나리오를 알고 수행하므로
   사례 연구로 보고하고, 결과는 일반 운영자 시간의 하한으로만 해석한다. 일정이 부족하면 3쌍으로 줄인다.

정적 런북 복잡도 결과는 [A단계 분석](analysis-2026-10-25.md) 5절에 있다.

### 4.6 RQ6 비용·trade-off

- **S2 지연·처리량.** 고정 p95 107.312 ms·창당 업로드 12,058,624바이트,
  동적 114.343 ms·24,641,536바이트(중앙값). 두 정책 모두 기준선 1.3배 안정 기준 이내다.
  두 축의 산점도로 제시한다.
  - 실효 업로드는 고정 약 1.6, 동적 약 3.3 Mbit/s로 명목 제한의 약 15~23%다. 창 정의·도구·공통 출구의
    문제가 아니며, burst 250 kbit의 OVS policing과 일치한다. burst는 API 보호를 위해 사전 보정한 값이다
    ([A단계 분석](analysis-2026-10-25.md) 1.2절). 보고서에는 실효 처리량으로 쓴다.
- **고정 확인 구간.** S1·S4의 시간 분해(4.3)로 확인 구간을 짧게 할 때의 속도와 오판 위험을 논의한다.
  가능하면 A3 replay로 판정 창 수에 따른 탐지 시각 변화를 보인다.
- **조치 비용.** S1 재배치 중 요청 실패 수와 Pod 교체 횟수, S2 업로드 재개의 중복·체크섬 결과.

## 5. 통계 처리

- 회차별 값, 중앙값, 최솟값·최댓값을 기본으로 제시한다. n=5에서 평균·표준편차를 주 지표로 쓰지 않는다.
- S1 자동/무조치(독립 2군): 마지막 60초 p95가 자동 최댓값 81.425 ms, 무조치 최솟값 158.456 ms로
  완전히 분리된다. Mann–Whitney 정확검정 U=0, 양측 p=2/252≈0.008, Cliff's δ=1.
- S2 고정/동적(같은 실행 내 짝): n=5의 Wilcoxon 부호순위 검정은 양측 최소 p=0.0625다.
  검정 대신 짝별 차이와 방향 일관성을 제시한다.
- 성공·거절 비율에는 Clopper–Pearson 정확 구간을 붙인다.
- 결과를 본 뒤 임계값·구간·검정을 바꾸지 않는다. 새 분석 방법은 적용 전에 이 문서에 고정한다.
- 계산 결과: [A단계 분석](analysis-2026-10-25.md) 4.2·4.3절. S3 자동/런북(Mann–Whitney p=0.31)도 같은 방식으로 제시한다.

## 7. 공통 원칙

- 새 실행은 두 축 계획 3절의 비교 조건·사건 시각·개입 규칙과 [평가 계약](final-evaluation.md)의 freeze·분모 보존을 따른다.
- 기존 캠페인의 원본·집계·해시를 덮어쓰지 않는다. 기존 원본에서 새로 집계한 값(A1 등)은
  별도 분석 산출물과 계산 스크립트, 원본 해시로 남긴다.
- 합성 입력·replay 결과는 실환경 결과와 다른 표에 둔다.
- 기대와 다르거나 불리한 결과도 그대로 보고하고 주장을 조정한다.
