## 보고서의 위치와 핵심 메시지

> 다계층 장애 대응을 위한 OpenStack–Kubernetes 공통 기반과 실험 자동화를 구축하고, worker VM 중단 시나리오(S4)에서 서비스 응답 회복과 목표 worker 수 복원을 구분하여 구현·기본 검증한 1차 프로토타입을 소개한다.

중간보고서의 중심은 **공통 기반의 설계·구현, CAPI 기반 복구 연동, S4 전체 실행 과정과 기본 테스트 결과**다. S1~S4는 작품 전체의 대상이며, S1~S3 대응 모듈의 완성과 본격적인 반복·비교 평가는 최종보고서 단계로 둔다. S1 정상 기준선 측정은 후속 준비에 해당하며 S1 장애 대응 완료로 취급하지 않는다.

Kubernetes와 MHC/CAPI/CAPO의 복구 기능을 활용한 시스템 통합도 구현 성과로 설명한다. 기존 도구의 담당 기능과 직접 작성한 환경 준비·대상 식별·실험 실행·관측·판정·분석·정리 기능을 구분한다.

## 국문 요약

- OpenStack과 Kubernetes의 여러 계층에 걸친 상태 확인·복구의 필요성.
- 자원 관계 연결과 기존 제어기 연동, 공통 환경 준비 및 S4 실험 자동화라는 접근.
- 단일 worker VM 중단에 대한 전체 복구 경로와 서비스·용량의 별도 완료 판정.
- 실환경 실행 3회를 통한 기본 동작 확인과 검증 범위의 한계.
- S1~S3 확장 및 최종 반복·비교 평가 계획.

## 1. 서론

### 1.1 제안 배경 및 필요성

- OpenStack VM 위에서 Kubernetes 서비스를 운영하는 다계층 구조.
- 서비스, Pod, Node, VM의 상태를 함께 확인해야 하는 이유.
- 정상 worker 2대 중 1대가 중단되면 Pod가 남은 1대로 옮겨 HTTP 응답이 먼저 돌아올 수 있음. 이때 대체 worker가 아직 합류하지 않았다면 서비스는 응답하지만 정상 worker는 목표 2대보다 1대 적다. 따라서 HTTP 회복과 새 worker의 생성·가입을 별도로 확인할 필요.
- 기존 복구 기능을 연결하고 실행 결과를 일관된 기준으로 확인할 필요성.

### 1.2 작품의 목표와 범위

- 사전에 정의한 대표 장애에 대한 상태 연결·복구 절차·결과 검증 자동화.
- S1 CPU 경합, S2 공통 송신 경로 혼잡, S3 stateful 복구, S4 worker VM 중단의 선정 이유와 역할.
- 신청서의 목표를 유지하면서 장애 범위·테스트베드·관측 구성을 구체화한 내용.

### 1.3 작품 전체 개요와 중간 성과

- 공통 환경 준비 → 시나리오 준비 → 장애 주입 → 복구 관측 → 분석 → 정리의 전체 흐름.
- CAPI/CAPO·MHC 연동과 직접 구현한 자동화의 역할.
- 기반 검증과 S4 전체 경로 3회 확인 결과의 간단한 소개.
- 이번 보고서에서 확인한 범위와 남은 S1~S3 구현·평가 범위. 이는 연구 목표가 아닌 현재 진행 상태로 설명.

### 1.4 보고서 구성

- 관련연구, 제안 작품, 구현·결과분석, 결론의 내용을 순서대로 안내.

## 2. 관련연구

이 장은 **선정한 논문을 읽고 연구별 방법·실험·한계와 작품 전체 주제의 관계를 서술**한다. 기존 2.1~2.3의 주제 구분은 논문 선정 전 임시 분류였으므로 고정 목차로 사용하지 않는다. [작품 전체 주제 기준 논문 후보 조사](literature-candidates.md)를 함께 검토하고 국문·영문 각 3편 이상을 선정한 뒤, 공통 논점이 드러날 때만 소절을 만든다.

- 각 논문의 해결 문제, 사용하는 관측 정보, 제어·복구 방식, 검증 방법을 요약한다.
- OpenStack의 VM·가상 네트워크와 Kubernetes의 Node·Pod·Service에 걸친 장애 관측·원인 파악·자동 대응이라는 작품 전체 문제를 기준으로 비교한다.
- 중간 구현 범위인 S4는 본문 3·4장의 사례로 제시하며, 관련연구의 검색·선정 기준으로 삼지 않는다.
- CAPI/CAPO·MHC 공식 문서는 시스템 배경 및 구현 근거로 인용하되, 양식의 논문 3+3 요건에 포함하지 않는다.
- 인용은 해당 사실을 설명하는 문장마다 붙이고, 논문을 읽지 않은 상태에서 결론·수치를 옮기지 않는다.

## 3. 제안 작품 소개

### 3.1 이론적 배경 및 테스트베드 구성

- GCP 시험 호스트의 OpenStack controller·compute와 그 위 Nova VM의 Kubernetes 구성.
- management/workload cluster, CAPI/CAPO·MHC, 관측·기록 경로.
- 본문 1.3에서 물리 서버 대신 GCP Compute Engine 인스턴스(VM)를 썼음을 한 번만 밝힌다. 이후 GCP 측 자원은 controller·컴퓨트로, OpenStack 게스트는 Nova VM으로 구분한다. `osk8s-compute01/02`는 각각 별도 인스턴스에 배치됐으며 Google Cloud 하부 물리 서버의 배치는 확인하지 않았다.

### 3.2 공통 환경·실행 기반

- 현재 환경 상태 확인, 필요한 기존 자원의 기동·복구, 준비 상태 검증.
- 이미 정상인 환경의 재사용과 환경 준비·시나리오 실행의 독립 및 통합 실행.
- 실행 ID·자원 소유권·시간 제한·실패 기록·중단 후 재개·정리 설계.
- Pod–Node–Machine–Nova VM 관계와 서비스 검사 결과를 같은 실행에 연결.

### 3.3 S4 복구 연동과 실행 절차

- 사전 조건: 정상 control plane, worker 2대, 단일 복제본 stateless HTTP 서비스, 대체 실행 여유.
- worker 전용 MHC 정책, 장애 대상 VM 식별, 한 대의 VM 중단.
- Kubernetes의 Pod 재배치와 MHC/CAPI/CAPO의 Machine·VM 교체 관측.
- HTTP 서비스 안정화와 목표 worker 2대의 복원·신규 worker 실행 검사의 독립 완료 조건.
- 분석 결과 저장, 시험 자원 제거, 원래 worker 제어 상태 및 소유 호스트 상태 복원.

### 3.4 역할 분담과 후속 확장

- 직접 구현: 환경·실험 자동화, 식별자 연결, 관측·완료 판정, 원본 분석, 정리.
- 기존 기능 활용: Pod 재생성, 장애 Machine 판정·교체, Nova VM 생성·삭제.
- S1~S3의 전제·대응 방향·완료 기준은 요약표로 제시하고 구현 완료 항목과 구분.

## 4. 구현 및 결과분석

### 4.1 구현 환경과 공통 기반 검증

- 사용 버전·호스트/VM 구성·실험 서비스·요청 경로와 판정 기준.
- 테스트베드, worker 제어, 지표·로그 수집 및 식별자 추적 검증.
- 환경 기동 과정에서 발견한 문제와 제한된 재시도·진단 보완. 환경 준비가 항상 성공한다고 일반화하지 않음.

### 4.2 S4 구현 과정과 기본 테스트

- 준비 검증 → 실제 VM 중단 실험 → 자동 분석 → 독립·통합 실행 및 정리 검증.
- 실제 HTTP 검사 경로는 **Kubernetes API Service proxy**임을 구성도와 본문에 명시.
- 정상 상태, 장애 영향, Pod 재배치, 대체 worker, 최종 정리를 단계별 증거로 연결.
- 중단·재개와 오류 거부 등의 로컬 테스트를 실환경 검증과 나눠 설명.

### 4.3 실험 결과

- 실환경 실행 3회의 공통 UTC 시간선과 실행별 결과표.
- 첫 관측 실패 → 첫 정상 응답과 첫 관측 실패 → 30초 이상 안정화 확인을 별도 표시.
- VM `SHUTOFF` 확인 → 목표 worker 2대 복원 및 신규 worker 실행 검사 완료를 별도 지표로 제시.
- HTTP 성공/전체 요청 수, 새 worker 검사, 자원 정리 여부 및 원본 실행 ID 기록.
- 수치·정의는 [최신 착수 점검](../interim-report-readiness-2026-09-26.md)을 기준으로 원본 분석 결과와 대조.

### 4.4 결과 해석과 한계

- HTTP 서비스 회복과 목표 worker 2대 복원을 나눠 측정한 의미와 단계별 대기 요인.
- 기존 제어기의 복구 기능과 통합·판정·분석 자동화의 기여.
- API proxy 관측값은 일반 사용자 ingress 지연·중단시간이 아님.
- 세 실행 사이 코드 보완과 HTTP 관측 공백이 있어 동일 코드·조건의 통계 실험으로 해석하지 않음.
- 실행 내 HTTP 요청 성공 비율과 장애 복구 실행 성공률을 구분.
- 실제 실환경에서 실행기를 의도적으로 중단한 뒤 재개하는 검증은 후속 과제.

## 5. 결론 및 소감

### 5.1 중간 성과

- 공통 기반과 S4 전체 복구 실험 자동화, 기본 검증 결과 요약.
- 구현·실환경 검증·로컬 테스트·미검증 사항의 경계를 명시.

### 5.2 구현 과정에서 얻은 경험

- 설치 완료와 서비스 회복의 차이, 식별자 기반 추적, 제어기 간 역할 분담.
- 실패·재시도·재실행을 고려한 자동화와 재현 가능한 결과 기록의 중요성.
- 실제 경험을 바탕으로 작성하고 본인의 소감을 확인해 보완.

### 5.3 최종보고서까지의 계획

- 10월 초: S1 대응 구현과 S2·S3의 네트워크·스토리지 전제 확인.
- 10월 중순: S2·S3 구현·통합 및 기능 동결 목표.
- 10월 하순: 조건을 고정한 반복·비교 실험, 한계 분석, 최종보고서·시연 정리.
- 중간 결과를 유지하면서 최종 양식의 관련연구·작품 소개·결과분석을 각각 7쪽 내외로 확장.

## 6. 참고문헌

- 국문·영문 논문 각각 3편 이상. 실제 읽고 본문에서 인용한 문헌만 수록.
- Kubernetes, CAPI/CAPO·MHC, OpenStack의 공식 문서를 구현 전제와 설정 근거로 추가.
- 본문 등장 순서에 따라 번호를 정하고, 설치 버전과 문헌의 적용 범위를 확인.
