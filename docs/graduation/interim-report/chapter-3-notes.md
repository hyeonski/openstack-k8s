# 3장 집필 메모 — 서론에서 옮긴 설계 세부사항

각 시나리오의 대응은 등록한 시험 서비스와 자원에 한정한다. 조치 전에 대상이 여전히 같은 Node·VM에 있는지 확인하고, 이미 복구가 진행 중이면 중복 명령을 피한다. 실패하거나 상태 조회가 불완전한 경우에는 성공으로 넘어가지 않고 시각·근거·오류를 기록한다. 실험 전에는 정상 요청의 성공과 배치 상태를 확인하고, 실험 후에는 서비스 조건 외에 시험이 남긴 자원과 정책도 점검한다. 이 절차는 자동화가 어느 한 번의 성공 화면에 의존하지 않도록 하는 공통 평가 기준이다.

시험 서비스와 제어 기능의 위치를 분리한 이유는 장애 주입의 영향을 관측기까지 확대하지 않기 위해서다. 워커 VM 한 대를 중단하더라도 Kubernetes 및 OpenStack의 제어 경로와 HTTP 검사를 수행하는 클라이언트는 계속 동작해야 복구 사건의 순서를 기록할 수 있다. 이 전제가 깨지면 관측 공백과 실제 서비스 중단을 구분하기 어렵다. 따라서 준비 단계는 클러스터 API, 대상 워커, 관리 제어기와 시험 서비스가 모두 사용 가능한지 검사한 후에만 장애 주입을 허용한다.

공통 실행 기록은 명령의 접수와 실제 자원 상태 변화를 구분한다. 예를 들어 Nova에 VM 중단을 요청한 시점, VM이 SHUTOFF로 확인된 시점, Node 이상 판정과 대체 Pod 준비 시점을 각각 남긴다. 덕분에 서비스 영향이 시작된 순간과 복구 제어기가 반응한 순간을 같은 시간선에서 분석할 수 있다. 자원 정리에서도 실행 ID와 소유권을 확인하여 해당 시험이 만든 서비스·MHC 및 설정만 제거한다. 이 구조는 S4를 반복 실행할 수 있게 하면서 후속 시나리오가 같은 기록·판정 방식을 사용하도록 한다.

S4 준비 단계는 MHC의 선택 범위를 워커 Machine으로 제한하고 control plane은 제외한다. 시험 HTTP 서비스는 영구 볼륨에 의존하지 않아 워커 이동과 데이터 재연결 문제를 분리할 수 있다. 중단 뒤에는 남은 워커에서 대체 Pod가 Ready인지 확인하는 한편, 실제 HTTP 요청이 연속으로 성공하는지 별도로 검사한다. 새 워커에 대해서도 Node Ready 표시만 확인하지 않고 시험 Pod의 실행 가능 여부를 확인한다. 이처럼 제어기 상태, 애플리케이션 응답, 새 자원의 실제 사용 가능성을 서로 다른 관측 항목으로 유지한다.

S3 완료 조건을 3장에서 상세화할 때에는 데이터 보존과 새 읽기·쓰기 성공을 구분해 서술한다.
