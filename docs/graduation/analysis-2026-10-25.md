### 1.1 분리만으로는 회복되지 않는다

- 5회 모두 분리만 구간의 p95가 458~503 ms다. 각 실행 기준선의 약 3.8~5.0배이며 안정 기준(1.3배)을 넘는다.
- 업로드는 분리 후에도 약 14.7 Mbit/s를 보내고, 공통 출구는 약 19.8 Mbit/s로 포화된다.
  Kubernetes 배치 조치(다른 worker로 분리)만으로는 같은 병목이 해소되지 않는다.
- 분리 후 해당 VM 포트에 Neutron QoS를 적용한 구간에서만 기준을 충족했다.
  RQ2의 교차 계층 기여 근거로 사용한다.
- 각 실행의 수용 판정에도 `split_alone_insufficient` 검사가 이미 포함돼 있었고, 5회 모두 통과했다(`run.json`의 `result.checks`).
  이번 재집계로 추가된 것은 구간 수치의 집계와 실행 간 요약이다.
- 분리만 구간의 p95는 5회 모두 같은 실행의 무제어 평균보다 높았다(중앙값 473.7 vs 443.2 ms).
  측정 순서와 구간 수(1개)가 다르므로 분리가 지연을 악화시킨다고 해석하지 않는다.
- 한계: 분리만 구간은 실행당 1개다. 측정 순서는 fixed-first에서 고정 뒤·동적 앞,
  dynamic-first에서 동적 뒤·고정 앞이다.

### 1.2 업로드 1.6 Mbit/s의 확인 결과

원본으로 확인한 사실:

1. **실측값이 맞다.** 고정 10 Mbit/s 구간의 업로드 진행량은 60초에 11~12개 청크(1 MiB)로,
   약 1.54~1.68 Mbit/s다. 구간 길이는 59.7~60.3초이며 창 정의의 오류가 아니다.
   청크 단위로 집계하므로 구간당 약 ±0.14 Mbit/s의 양자화가 있다.
2. **업로드 도구의 한계가 아니다.** 같은 도구가 QoS 없는 구간에서 약 14.7 Mbit/s를 보냈다.
3. **공통 출구 병목도 아니다.** 고정 구간의 공통 출구는 약 6.1 Mbit/s로 20 Mbit/s 제한에 크게 못 미친다.
4. **적용된 제한은 OVS ingress policing이다.** `run.json`의 `policy_changes`에서 모든 변경이
   업로드 VM의 `qvo*` 인터페이스에 `ingress_policing_rate`(6000~18000 kbps)와
   `ingress_policing_burst` 250 kbit로 반영된 것을 확인했다.
5. **실효 처리량은 명목 제한의 약 15~23%다.** 구간별로 6 Mbit/s에서 1.26~1.40, 10 Mbit/s에서 1.54~1.68,
   14 Mbit/s에서 2.10~2.25, 18 Mbit/s(탐색·안정 구간)에서 2.81~3.93 Mbit/s다.

해석:

- Neutron QoS 문서는 TCP에 대해 burst를 제한값의 80%로 둘 것을 권고한다
  ([Neutron 2025.2 QoS](https://docs.openstack.org/neutron/2025.2/admin/config-qos.html)).
  10 Mbit/s 기준 약 8,000 kbit인데, 사용한 250 kbit는 그보다 훨씬 작다.
  작은 burst의 policing에서 TCP가 제한값에 도달하지 못하는 현상과 일치한다.
  OVS 인터페이스의 policing drop·TCP 재전송 카운터는 수집하지 않았으므로 직접 증명하지는 않는다.
- 250 kbit는 의도한 보정값이다. [2026-10-02 검증](recovery-validation-2026-10-02.md)의 사전 측정에서
  10 Mbit/s·burst 1000 kbit는 업로드 약 48 MiB/60초였지만 API p95가 약 214 ms로 기준을 넘었다.
  burst 250 kbit에서는 p95 약 105 ms였다. 보정은 이번 캠페인 고정 전에 수행됐다.
- 따라서 burst는 API 꼬리 지연 보호와 업로드 처리량 사이의 trade-off다. TCP 처리량 권고와
  서비스 보호 목적이 충돌하며, 이 환경에서는 서비스 보호를 택했다.

보고서 반영:

- 업로드 성능은 설정 제한값이 아니라 수신 byte 기반의 실효 처리량으로 쓴다.
  "18 Mbit/s 정책"은 정책 상한이고 실효 업로드는 약 3.3 Mbit/s다.
- 동적 정책의 업로드 약 2배(3.30 vs 1.61 Mbit/s)는 유효한 비교다. 같은 burst에서 명목 상한만 달랐다.
- 고정 구간에서 공통 출구 용량의 약 14 Mbit/s가 사용되지 않았다. 현재 policing 방식은
  API를 보호하지만 여유 용량을 활용하지 못한다. 한계와 향후 과제(burst·shaping 방식 비교,
  우선순위 큐)로 기록하며, 현재 정책을 결과에 맞추어 바꾸지 않는다.
- 다른 burst나 shaping 방식이 더 나은지는 이번 데이터로 판단할 수 없다.

### 2.4 S4 서비스 안정화의 외곽값

고정 지표인 `first_failure_to_service_stable_seconds`의 두 회차는 서비스 실패가 아니라 관측 표본의 연속성 때문에 길어졌다.

| 실행 | 고정 지표 | 첫 안정 확인 | 원인 |
|---|---:|---:|---|
| s4-normal-04 | 153.938 | 107.605 | 첫 안정 확인 뒤 표본 시각 역순 1건(-0.658초). 요청은 모두 성공 |
| s4-normal-05 | 298.501 | 107.043 | 첫 안정 확인 뒤 지연 1,680.6 ms 요청으로 표본 간격 2.69초(>2.5초). 요청은 모두 성공 |

- 고정 판정([graduation_s4_run.py](../../experiments/graduation_s4_run.py)의 `stable_http_window`)은
  마지막 연속 구간만 인정한다. 공백·역순 뒤에는 새 구간으로만 회복을 인정하는
  [평가 계약](final-evaluation.md)의 보수적 정의다. 고정 지표와 판정은 바꾸지 않는다.
- 보조 지표는 같은 규칙(30초, 정상 표본 20개 이상, 간격 2.5초 이하)이 처음 충족된 시각이다.
  5회 모두 103.9~107.6초이며, 그 뒤 실패한 요청은 없다.
- 보고서에는 고정 지표를 주 지표로 쓰고, 외곽값의 원인과 보조 지표를 함께 제시한다.
  보조 지표로 고정 지표를 대체하지 않는다.
- 역순 시각은 표본 기록 순서의 문제로 보이지만 원인을 추가로 확인하지 않았다.

### 2.5 보고서 반영

- 세 시나리오 모두 복구 시간의 대부분은 탐지·확인 대기다. 정책으로 정한 창, Kubernetes Node 감시,
  MHC·toleration 설정이 여기에 해당한다. 실제 조치 구간은 짧다
  (S1 약 38초, S3 모듈 단계 약 36초, S4 대체 Pod 약 2초).
- 복구를 빠르게 하는 수단은 대기 설정의 단축이며, 오판·성급한 완료 판정 위험과 trade-off다(RQ6).
  이번 평가는 대기 설정을 바꾼 비교를 하지 않았다.
- S3 자동과 런북의 총시간 차이(약 5초)는 Kubernetes·CSI 구간의 편차 범위 안에 있다.
  두 방식의 실행 시간이 같다는 RQ5 해석을 뒷받침한다.

### 3.1 결과

- S1·S2에서는 장애 중 Kubernetes가 관측하는 Pod 수준 신호가 모두 정상이다. 서비스 영향은 분명하고,
  원인과 조치 대상은 OpenStack 배치·호스트 지표 또는 네트워크 경로 카운터에만 나타난다.
  Kubernetes 기본 self-healing이 동작할 계기가 없다는 RQ1의 근거로 사용한다.
- S3는 계층 간 상태가 불일치하는 사례다. Kubernetes의 NotReady는 "기존 프로세스가 멈췄다"를 뜻하지 않는다.
  실제로 기존 DB 컨테이너는 실행 중이었고 VM은 ACTIVE였다.
  Kubernetes 정보만으로 대체 Pod를 띄우는 것은 안전하지 않다는 정의서 [R6]·[R8]의 전제를 실측으로 확인했다.
- S4는 두 계층의 신호가 일치하는 대조 사례다. 교차 계층 판단이 필요하다는 주장의 근거로 쓰지 않는다.

### 3.2 한계

- S1·S2의 Node Ready 조건은 장애 중 snapshot으로 수집하지 않았다. 단일 복제본 서비스가 ClusterIP로
  모든 요청에 응답했으므로 Pod endpoint가 유지됐다고 추론한다. 이는 snapshot이 아니라 추론이다.
- S1 자동군의 Pod 상태는 경합 전 snapshot만 있다. 경합 중 Pod Ready는 무조치군 5회로 확인했다.
- S3의 서비스 영향은 장애 주입에서 DB 포트(5432) 차단을 함께 적용해 만든 것이다. 제어 통신 두절의
  자연스러운 결과로 해석하지 않는다. 기존 컨테이너 생존은 장애 주입 명령 직후 시점의 확인이다.
- S3에서 Kubernetes만 동작할 때의 결과(Pod 정리 대기, 6분 강제 분리 등)는 관측하지 않았다.
  펜싱이 NotReady 약 6초 뒤에 시작됐기 때문이다. 이 부분은 [평가 설계](evaluation-design-2026-10-25.md) 4.1절의 보완 항목으로 남는다.
- S4의 첫 snapshot은 SHUTOFF 확인 시점(정지 의도 후 약 70초)이다. 이전의 상태 전이는 2절의 시간 분해를 따른다.

### 4.2 비율과 95% 정확 신뢰구간 (Clopper–Pearson)

| 대상 | k/n | 95% 구간 |
|---|---:|---|
| 모듈 판단, 정상 조건 | 25/25 | [86.3%, 100%] |
| 모듈 거절, 오류 주입 조건 | 3/3 | [29.2%, 100%] |
| 통합·시험 경로 (S4 정상) | 5/5 | [47.8%, 100%] |
| 단일 조건 5회 (예: S1 자동 복구, S3 자동 데이터 보존) | 5/5 | [47.8%, 100%] |
| S3 데이터 보존 (자동 + 런북) | 10/10 | [69.2%, 100%] |
| 단일 거절 시험 | 1/1 | [2.5%, 100%] |

- 5회 통과가 보장하는 하한은 약 48%다. 거절 시험은 조건별로 1회씩이라 개별 거절 신뢰도를 추정할 수 없다.
  "안전 장치가 실환경에서 한 번 이상 의도대로 동작했다"는 존재 증명으로만 쓴다.
- 모듈 판단 25/25는 서로 다른 시나리오를 합친 값이다. 시나리오별 신뢰도로 해석하지 않는다.

### 4.3 비교 검정

| 비교 | 값 (중앙값, 범위) | 검정 | 결과 |
|---|---|---|---|
| S1 마지막 60초 p95, 자동 vs 무조치 (독립 5:5) | 78.239 (76.629~81.425) vs 171.086 (158.456~739.144) ms | Mann–Whitney 정확검정 | U=0, 양측 p=0.0079(가능한 최솟값), Cliff's δ=−1 |
| S3 장애 주입 → DB Ready, 자동 vs 런북 (독립 5:5) | 147.08 (128.99~149.84) vs 141.71 (140.33~148.48) s | Mann–Whitney 정확검정 | U=18, 양측 p=0.31, Cliff's δ=0.44 |
| S2 안정 구간 p95, 동적 − 고정 (같은 실행 짝 5) | 114.343 vs 107.312 ms | Wilcoxon 부호순위 정확검정 | 5/5 동적이 높음, 양측 p=0.0625(가능한 최솟값) |
| S2 창당 업로드, 동적 − 고정 (같은 실행 짝 5) | 24,641,536 vs 12,058,624 bytes | Wilcoxon 부호순위 정확검정 | 5/5 동적이 큼, 양측 p=0.0625(가능한 최솟값) |

- **S1:** 자동군의 모든 값이 무조치군의 모든 값보다 작다(25쌍 모두). 5:5 설계에서 얻을 수 있는 가장 강한 결과다.
- **S3:** 두 방식의 차이를 보일 근거가 없다(p=0.31). 실행 시간이 같다는 RQ5 해석과 일치한다.
  δ=0.44는 자동이 다소 긴 쪽으로 기운 것을 뜻하지만, 2.2절의 Kubernetes·CSI 구간 편차 범위 안에 있다.
- **S2:** n=5 짝 비교는 구조적으로 p<0.05에 도달할 수 없다. 대신 5회 모두 같은 방향이었다는
  일관성(지연 소폭 증가, 업로드 약 2배)을 효과로 제시한다. 두 정책 모두 안정 기준(1.3배)을 충족했다.
- 검정은 사전에 정한 세 비교에만 적용했다. 다중 비교 보정은 하지 않았으며, 탐색적 비교를 추가하지 않는다.

## 5. 정적 런북 복잡도 (RQ5)

자동 복구 경로의 코드를 그대로 사람이 수행한다고 할 때 필요한 작업량을 센다.
사람의 시간이 아니라, 같은 판단·안전 조건을 지키려면 최소한 무엇을 확인하고 바꿔야 하는지를 보는 정적 지표다.
실제 사람의 시간은 [두 축 평가 계획](two-axis-evaluation-plan-2026-10-24.md)의 H1에서 따로 측정한다.

### 5.1 계수 규칙

- 기준 구현: `b82711b`. 대상은 장애 확인 이후 복구 완료 판정까지의 코드다.
  준비·장애 주입·측정 도구·정리는 제외한다.

- 이 표는 코드를 직접 읽고 센 수작업 집계다. 판단 기준을 바꾸면 수치도 바뀌므로 규칙과 코드 위치를 함께 남긴다.

사람이 할 일은 완료 확인이다. snapshot당 조회 9회(MachineDeployment, MHC, Machine, OpenStackMachine,

### 5.4 해석

- S1·S2·S3는 한 번의 복구에 서로 다른 인터페이스 4~6개와 식별자 홉 4~9단계가 필요하다.
  Kubernetes만 다루는 운영자 도구(kubectl)로는 끝나지 않는다. RQ2의 교차 계층 필요성을 작업 구조로 보여준다.
- 자동화가 대신하는 것은 주로 **반복 확인과 순서 강제**다. 변경 자체는 S1·S3에서 1~3회뿐이다.
  반면 판단 조건은 수십 개이고 그중 상당수는 창 단위로 반복된다.
  2.2절에서 S3 자동과 런북의 실행 시간이 같았던 것도 같은 맥락이다. 런북도 같은 판단 코드를 호출했다.
- S3의 "종료 확인 → 재확인 → out-of-service" 순서는 어기면 이중 마운트·데이터 손상 위험이 있는 조건이다.
  사람이 수행할 때 가장 오류가 나기 쉬운 지점으로 보고서에 기술할 수 있다. 다만 사람의 오류율은 측정하지 않았다.
- 이 지표는 사람의 실제 소요 시간이나 오류율을 뜻하지 않는다. 숙련도·도구에 따라 달라지는 실제 부담은 H1로만 측정할 수 있다.

**시나리오 변경 사유.** 신청서의 Pod 반복 실패와 Ingress controller 장애는 Kubernetes 계층 안에서 탐지·복구가 끝나는 부류다.
"두 계층을 함께 봐야 하는 장애"라는 연구 목적에 맞추어 교체했다. worker NotReady는 S3(통신 두절)와 S4(VM 중단)로 구체화했다.
3절의 신호 표가 이 구분의 근거다. S1·S2는 Kubernetes 신호가 정상인 장애이고, S3는 계층 간 상태 불일치 장애다.

**조치 종류 변경 사유.** 신청서의 Pod 재시작·rollout restart는 같은 노드나 같은 compute에 다시 배치될 수 있어 S1·S2의 원인을 해소하지 못한다.
kubelet 재기동은 통신 두절 노드(S3)에 닿을 수 없다. 실제 조치는 원인 계층에 맞춘 배치·QoS·펜싱으로 바꿨다.
같은 노드 재시작이 효과가 없다는 실측(평가 설계 A2)은 아직 하지 않았다.

**보고서에 남길 미달 항목.** Grafana 대시보드, 사람 수행 수동 대응 비교. 대체 근거는 각각 OTel 수집 경로와 5절의 정적 복잡도·S3 런북 비교다.
