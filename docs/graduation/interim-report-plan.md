# 졸업작품 중간보고서 구성 및 최종 구현 계획

- 작성 기준: 2026-09-25
- 성격: 보고서 작성·구현 범위에 대한 제안. 제출용 본문이나 구현 완료 선언이 아님.
- 주제 기준: 사용자가 제공한 연구논문/작품 신청서
- 장애 기준: [장애 시나리오 정의서](failure-scenarios.md)의 S1~S4
- 일정 가정: 중간보고서 전 추가 구현 1일(약 8시간), 최종 제출은 10월 말. 정확한 제출일은 미확인하므로 10월 28일 제출본 완성을 내부 목표로 설정.
- 이번 검토에서는 문서·코드·보존된 결과만 확인했다. 클라우드 재기동이나 새로운 장애 실험은 수행하지 않았다.

> **2026-09-26 최신 판정:** 아래에는 구현 전 작성한 작업 순서와 가정이 일부 남아 있다. S4 구현·실험의 현재 상태와 보고서에 사용할 수치·한계는 [중간보고서 착수 점검](interim-report-readiness-2026-09-26.md)을 우선한다. 실제 worker VM 중단 실험 3회, 독립 실행·통합 실행, 자동 분석과 정리가 완료됐다.

> **2026-09-26 범위 수정:** 중간보고서의 구현 목표는 공통 인프라·환경 상태 확인·필요시 복구 자동화와 S4 전체 복구 실험 자동화, 기본 반복 검증이다. 두 자동화는 독립 실행할 수 있고 선택적으로 한 명령으로 연결한다. 이미 정상인 환경은 재구축하지 않는다. 아래 최초 8시간 표는 착수 순서와 작업량의 초기 추정으로만 사용한다. 현재 저장소 점검 결과와 구체적인 완료 조건은 [S4 구현 범위 점검](s4-implementation-assessment.md)을 따른다.

## 1. 보고서의 중심 주장

작품명은 신청서의 **OpenStack 기반 Kubernetes 환경에서 대표 장애 대응 자동화 모듈 프로토타입 설계 및 구현**을 유지한다. 개인 작품이며 분야는 시스템/네트워크다.

보고서의 중심은 다음과 같이 잡는다.

> Kubernetes의 서비스·Pod·Node와 OpenStack의 VM·compute·네트워크·볼륨 사이의 관계를 연결하고, 사전에 정의한 장애 조건에서 복구 순서를 제어한 뒤 실제 서비스 회복을 검증하는 모듈을 설계·구현한다.

OpenStack 설치, Kubernetes 구축, 자동 증감은 이를 위한 기반이다. 작품의 직접 기여는 계층 간 상태 연결, 시나리오별 판단, 안전한 실행 순서, 중복 조치 방지, 서비스 기준의 완료 판정이다. CAPI/CAPO가 수행한 VM 생성과 Kubernetes가 수행한 Pod 재생성을 직접 개발한 기능으로 표현하지 않는다.

신청서와 달라진 사항을 서론에 짧게 설명한다.

| 구분 | 신청서 | 현재 보고서에서 설명할 내용 |
|---|---|---|
| 장애 범위 | worker 이상, Pod 반복 실패, Ingress 이상 | 사용자 지정 정의서에 따라 S1 CPU 경합, S2 송신 경로 혼잡, S3 stateful 복구, S4 VM 중단으로 구체화 |
| 테스트베드 | 물리 서버 3대 계획 | GCP VM 3대에 OpenStack을 배치하고 compute 2대에서 중첩 가상화 사용 |
| 관측 도구 | Prometheus/Grafana 계획 | 현재는 OpenTelemetry, Cloud Monitoring/Logging 및 로컬 실행 증거. Grafana 구축 완료로 쓰지 않음 |
| 일정 | 8월 구현, 9월 평가 계획 | 현재 기반 검증 완료와 남은 장애 대응 구현을 구분하고 10월 수정 일정 제시 |

범위 조정 문장 예시:

> 초기 신청 단계에서는 Node·Pod·Ingress의 이상 상태를 중심으로 장애 유형을 분류하였다. 이후 OpenStack과 Kubernetes 사이의 상태 연결 및 복구 제어를 구체적으로 평가하기 위해 CPU 경합, 공통 송신 경로 혼잡, 영구 볼륨을 사용하는 서비스의 복구, worker VM 중단의 네 시나리오로 대상 범위를 구체화하였다.

이는 원래 세 시나리오까지 모두 완료하겠다는 추가 약속이 아니다. 신청서의 큰 목적은 유지하고, 실제 구현·평가 대상은 S1~S4로 명확히 한다.

## 2. 양식에 맞춘 분량과 구성

양식은 서론 6쪽, 관련연구 4쪽, 제안 작품 4쪽, 구현 및 결과분석 4쪽, 결론 및 소감 1쪽, 참고문헌 1쪽으로 합계 20쪽을 안내한다. 여기에 요약 약 0.5쪽을 더하면 본문 약 20~21쪽이다. 표지와 코드 부록의 포함 여부는 안내만으로 확정되지 않으므로 최종 편집 때 확인한다.

### 요약: 약 0.5쪽

문제 → 목적 → 접근 → 현재 확인한 결과 → 남은 검증의 순서로 쓴다. 아직 측정하지 않은 복구 시간 단축률은 넣지 않는다.

현재 증거만으로 가능한 문장 예시:

> 본 작품은 OpenStack 기반 Kubernetes 환경에서 계층 간 상태를 연결하여 대표 장애의 탐지와 복구 절차를 자동화하는 프로토타입을 목표로 한다. 중간 단계에서는 테스트베드, 계층별 관측 및 실행 이력 관리 기반을 구축하고 네 가지 장애 시나리오의 복구 절차와 완료 기준을 정의하였다. 기존 검증에서는 정상 상태의 30분 관측과 worker 자동 증감 과정의 자원 식별자 추적을 확인하였다. 향후 시나리오별 대응 로직을 구현하고 서비스 회복 시간, 성공 여부 및 복구 과정의 안전 조건을 평가한다.

하루 추가 구현 후에는 실제 통과한 S4 범위만 이 요약에 추가한다.

국문 논문 최소 3편, 영문 논문 최소 3편을 실제로 인용한다. 공식 문서 여섯 개로 이 조건을 대신하지 않는다. 후보와 확인 범위는 7절에 정리했다.

| 절 | 분량 | 비교 관점 |
|---|---:|---|
| 2.1 간섭과 성능 저하 대응 | 1쪽 | 공동 배치 간섭, 자원 사용량과 서비스 품질의 차이. S1의 목적지 선택과 연결 |
| 2.2 Kubernetes 정책·자원 제어 | 1쪽 | 오퍼레이터, 자원 조정, 탐지와 대응의 연결. S1/S2 정책 구조와 연결 |
| 2.3 stateful 서비스 가용성 | 1쪽 | 상태 복제, checkpoint/restore, 영구 볼륨 재연결의 차이. S3의 범위 명시 |
| 2.4 기존 도구와 본 작품 | 1쪽 | Kubernetes, MHC/CAPI/CAPO, Neutron QoS, CSI가 제공하는 기능과 직접 구현 부분 비교 |

비교표 열은 “대상 문제 / 관측 계층 / 제어 대상 / 상태 보존 방식 / 본 작품과의 관계”로 잡는다. 논문마다 요약을 나열하기보다 설계 선택의 근거로 연결한다. 직접 재현하지 않은 연구의 수치를 본 실험의 우수성 근거로 사용하지 않는다.

### 3장 제안 작품 소개: 약 4쪽

| 절 | 분량 | 쓸 내용 |
|---|---:|---|
| 3.1 이론적 배경과 시스템 구성 | 1쪽 | OpenStack compute와 worker VM, Kubernetes 제어기 역할, 제어·관측 경로 |
| 3.2 공통 모듈 | 1쪽 | 서비스 검사기, 자원 매핑, 정책 판단, 단계 실행, 결과 저장. 실행 ID·UID·시간·소유권 |
| 3.3 장애별 복구 정책 | 1.5쪽 | S1~S4 각각의 전제·판단 근거·절차·완료 조건. 자세한 단계는 시나리오 정의서를 준거로 작성 |
| 3.4 실패 처리와 구현 상태 | 0.5쪽 | 보류·실패·부분 회복, 재시도 상한, 중복 방지. 현재 구현과 예정 부분을 표시 |

공통 실행 모델은 `관측 → 의심 → 조건 확인 → 조치 중 → 안정화 검사 → 완료/실패/보류`로 제안한다. 이것은 목표 설계이며 기존 autoscaling runner에 해당 상태가 모두 구현돼 있다는 뜻이 아니다.

필수 설계 설명:

- Pod → Node → providerID → Nova VM → compute를 연결하고, S2에서는 Neutron port, S3에서는 PVC/PV → Cinder volume을 추가한다.
- 오래된 배치 정보만 믿지 않고 조치 직전에 다시 조회한다. 관계가 모호하면 변경하지 않는다.
- 복구 모듈의 현재 판단은 Kubernetes/OpenStack 조회와 서비스 검사에 기반한다. GCP 관측 저장소는 실행 증거와 사후 분석에 사용한다.
- S1: 다른 compute의 기존 worker로 대체 Pod를 먼저 기동하고 준비 후 기존 Pod를 종료한다.
- S2: API와 업로드를 별도 VM 포트로 분리한 뒤 업로드 포트의 QoS를 조정한다. 공통 병목 자체를 우회하는 구조로 그리지 않는다.
- S3: 기존 VM의 실제 종료 확인 → out-of-service 처리 → CSI 분리·재연결 → PostgreSQL 데이터 검증 순서다.
- S4: 서비스 회복과 대체 worker 용량 회복을 별도로 추적한다. VM 교체 구현은 기존 도구를 활용한다.

| 절 | 분량 | 쓸 내용 |
|---|---:|---|
| 4.1 구현 환경 | 0.5쪽 | 저장소에 고정한 버전, GCP 중첩 가상화, controller 1대·compute 2대, workload 구성 |
| 4.2 기반 구현·검증 | 1쪽 | 계층 관측, 자원 관계 추적, timeout/cancel/resume, 자동 증감. 시험 범위와 원본 경로 |

S4가 끝까지 성공하지 못하면 4.3은 “S4 예비 실험 및 미완료 단계 분석”으로 쓴다. 설계 그림을 실험 결과로 대체하지 않는다. HTTP 요청이 성공했다는 로그와 worker가 Ready라는 로그는 별도의 증거다.

### 5장 결론 및 소감: 약 1쪽

앞부분은 현재 달성한 것과 남은 것을 요약하고, 뒷부분은 본인이 실제 경험한 판단의 변화를 쓴다. 다음은 작성 소재이지 본인의 감정을 대신하는 완성 문장이 아니다.

- 설치 성공과 서비스 복구 성공을 다른 기준으로 봐야 했던 경험
- 서로 다른 계층의 이름 대신 UID/providerID로 관계를 추적해야 했던 이유
- 실행 중단·재시도에서 중복 조치와 상태 보존을 다룬 경험
- 자료 수집 지연·조회 실패·실제 장애를 구분한 과정
- 모든 복구 기능을 새로 구현하기보다 기존 제어기의 책임을 정하는 설계상의 배움

현재 기록에 나타난 TLS/수집 순서 문제와 재검증, 중단 후 실행 복구 사례는 구체적인 소재가 된다. 경험하지 않은 사용자 장애나 운영 사고를 만들어 쓰지 않는다.

### 6장 참고문헌: 약 1쪽

논문 6편과 본문에서 직접 사용하는 공식 문서 약 4~6개를 우선 배치한다. 양식의 “1쪽 내외”에 맞춰 편집하되 글자를 과도하게 줄이지 않는다. 본문에 인용 번호를 붙이고, 실제 사용하지 않은 자료를 목록만 채우기 위해 넣지 않는다.

## 4. 하루 추가 구현의 권장 범위

**수정된 완료 목표: 공통 관측·기록 경로에 S4를 연결하고 실제 VM 중단 후 서비스·worker 용량의 전체 복구를 검증한다.** 기본 동작 뒤 독립 실행을 추가해 재현성을 확인한다.

S4를 먼저 하는 이유는 현재 CAPI/CAPO, worker 제어, providerID, 실행 이력 기반을 가장 많이 재사용할 수 있기 때문이다. 현재 workload template에는 MHC 정의가 없으므로 “설정 하나면 반드시 끝난다”고 예상하지 않는다. 삭제·drain·가입 경로에서 시간이 소요될 수 있다.

### 8시간 배분안

| 시간 | 작업 | 산출물·판정 |
|---|---|---|
| 0~1시간 | 환경 준비, worker 2대, stateless HTTP Deployment 1개, 외부 검사 경로 | 정상 기준선. API 서버 port-forward를 서비스 경로로 오인하지 않음 |
| 1~2.5시간 | HTTP 연속 요청 기록, Node–VM–Machine 매핑, run ID와 시각 기록 | 지연·성공 여부·대상 식별자를 같은 실행에서 조회 |
| 2.5~4시간 | worker 대상 MHC 조건과 복구 허용 범위, CAPI 삭제·대기 설정 확인 | control plane을 제외하고 한 worker만 처리하는 시험 구성 |
| 4~6시간 | worker VM 한 대 중단, Kubernetes 서비스 회복과 CAPI/CAPO 교체 관측 | HTTP 회복 시점과 대체 worker Ready 시점 분리 |
| 6~7시간 | 여건이 되면 재실행 또는 실패 단계 수정·확인 | 성공 1회는 기능 예비 검증. 반복 성공률로 과장하지 않음 |
| 7~8시간 | 상태 복원, 결과 JSON/CSV·시간선·구현 상태표 작성 | 보고서에 넣을 증거를 확보하고 코드 동결 |

기존 클라우드 기동·준비가 예상보다 길면 뒤 작업 시간을 줄여야 한다. 하루를 넘겨 환경을 대규모 개편하지 않는다. 서식 편집과 20쪽 본문 작성은 이 8시간 외의 작업으로 잡는다.

시험 중 worker 목표를 2대로 고정하려면 기존 fixed 모드를 사용하고 CA 상태를 기록한다. 이는 비교 조건을 고정하기 위한 것이며, 기본 Kubernetes 복구나 MHC를 끄고 제안 모듈에 유리한 결과를 만드는 방식은 사용하지 않는다. 최초 S4 구현은 기존 MHC 복구를 통합·관측하는 범위이며, 자체 VM 교체기를 새로 작성하지 않는다.

### S4 완료 판정

- 장애는 실제 서비스 Pod가 있는 worker VM 한 대에 주입하고 나머지 worker 여유를 사전 확인한다.
- 장애 주입·서비스 영향·Node 이상·Machine 교체·HTTP 안정화·새 worker Ready 시각을 남긴다.
- 목표 복제본이 준비되고 실제 HTTP 요청이 미리 정한 안정화 구간 동안 성공해야 서비스 회복이다.
- 목표 worker 수가 Ready이고 새 worker에서 시험 Pod가 정상 실행되어야 용량 회복이다.
- 기존 Machine/VM의 최종 상태와 잔여 자원을 확인한다.
- VM 교체는 되었지만 HTTP가 계속 실패하면 서비스 복구 성공으로 기록하지 않는다.
- Pod가 기존 기능으로 먼저 회복됐다면 그 사실과 실제 담당 제어기를 그대로 기록한다.

**중간 상태:** 정상 HTTP 측정, 대상 관계 매핑, 장애 감지와 단계 기록까지만 되었다면 “S4 탐지·관측 구현”이라고 쓴다. 이는 중간보고서의 목표 완료 범위가 아니다.

**목표 완료선:** S4 서비스 회복과 worker 용량 회복의 전체 흐름을 실환경에서 통과하고, 독립 실행을 최소 1회 추가하며 원본 증거와 실패 시도를 정리한다.

**여유가 있을 때:** 목적지 없음·시간 초과에서의 실패 기록을 추가 검증한다.

## 5. 10월 말 최종 완료 범위와 일정

### 시나리오별 최소 완성형

| 시나리오 | 최종 구현 범위 | 완료 조건 | 확장하지 않을 부분 |

## 6. 최종 실험 설계

신청서의 수동 대응과 자동 대응 비교 목적을 유지하되, 기존 기능만으로 회복되는 효과를 분리한다.

| 대상 | 비교 조건 | 핵심 측정 |
|---|---|---|
| S1 | 기본 기능 유지, 같은 절차의 수동 런북, 자동 정책 | API p95·오류율·처리량, 서비스 회복 시간, 배치·호스트 경합. 필요 시 같은 compute 내 재시작 대조 |
| S2 | 무추가 제어, 합리적인 고정 QoS, 제안 동적 제어 | API p95·오류율 + 업로드 완료 시간·진행률·총 처리량. 수동 런북은 조작·대기 부담 비교로 보조 |
| S3 | 안전한 동일 절차의 수동 런북, 제안 자동화 | VM 종료 확인, 볼륨 분리/연결, DB 기동, 커밋 데이터 보존, 새 읽기·쓰기 |
| S4 | 기존 Kubernetes+MHC/CAPI/CAPO 복구, 통합 모듈을 통한 관측·판정 | 서비스 회복과 용량 회복 각각의 시간, 관계 추적·단계 기록의 완전성 |

S4는 통합 모듈이 복구 엔진을 바꾸지 않는다면 시간 단축이 없어도 이상하지 않다. 기여를 통합 관측·판정·증거 수집으로 정직하게 설명한다. 수동 worker 교체는 별도 운영 절차 비교로 추가할 수 있지만 MHC가 켜진 기준선을 숨기지 않는다.

측정 정의:

- 서비스 복구 시간 = 서비스 영향 시작부터 목표를 안정화 구간 동안 만족하기까지
- 감지 지연 = 서비스 영향 시작부터 장애 확정까지
- 조치 시간 = 자동 또는 수동 조치 시작부터 해당 복구 단계 완료까지
- S4 용량 복구 시간 = 장애 주입부터 목표 worker 수 Ready 및 신규 worker 실행 검사 완료까지
- 수동 대응의 인지·작업 시작 시각은 기록하고, 본인이 미리 준비한 시험이라는 편향도 기술
- 영향이 없던 실행은 중단 시간을 꾸며내지 않고 “서비스 중단 없음, 복제본/용량 저하”로 기록

구현 확인은 1회, 예비 반복은 조건당 3회, 최종은 주요 조건당 5회부터 시작하는 소규모 계획을 권장한다. 변동이 큰 조건은 10회로 늘릴 수 있으나 달력 시간과 비용을 먼저 확인한다. 5/5 성공을 운영 환경의 100% 신뢰성으로 표현하지 않는다. 각 실행의 값, 중앙값, 범위와 실패 사유를 함께 제시하고 서비스 요청 p95와 복구 실행 시간의 통계를 구분한다.

모든 실행은 코드·버전·요청 패턴·배치·임계값을 고정한다. 임계값은 정상 기준선과 예비 실험으로 정한 뒤 비교 실험 중 결과에 맞춰 변경하지 않는다. 요청 수가 적어 p95가 불안정하면 표본 수와 측정 구간부터 보완한다.

대표 실패/보류 검증은 시나리오당 최소 하나를 잡는다: S1 목적지 없음, S2 QoS 적용 실패, S3 종료 확인 실패, S4 대체 worker 가입 지연. 완료 판정과 재시도 상한이 작동하는지 검사한다.

## 8. 중간보고서 제출 시 사용할 완료 표현

현재 확정 가능한 표현:

> OpenStack 기반 Kubernetes 테스트베드와 계층별 관측·실행 관리 기반을 구축·검증하였으며, 네 가지 대표 장애 시나리오의 판단 조건, 복구 절차 및 완료 기준을 설계하였다.

S4 전체 예비 검증까지 실제 통과한 경우에만 추가할 표현:

> worker VM 중단 시나리오에서 기존 Kubernetes 및 CAPI/CAPO 기반 복구 흐름을 통합하고, 서비스 회복과 worker 용량 회복을 각각 추적하는 예비 실험을 수행하였다.

남은 계획:

> CPU 경합 대응, 공통 송신 경로의 QoS 제어, 영구 볼륨을 사용하는 서비스의 복구를 순차적으로 구현하고, 10월 중순 이후 동일 조건의 반복 실험을 통해 효과와 한계를 평가할 계획이다.

완료율 하나로 묶기보다 “기반 실환경 검증 / 공통 모듈 구현 / 시나리오별 설계 / 예비 검증 / 반복 평가” 상태표를 사용한다. 가장 중요한 미완료 기능이 기반 코드의 분량에 가려지지 않게 한다.
