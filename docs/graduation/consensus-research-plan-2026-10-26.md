# Codex·Claude 연구 평가 합의안

작성: 2026-10-26, Asia/Seoul. 대상 코드 검토 기준: `44b5a8c`.

사용자의 요청으로 Codex와 Claude CLI가 두 독립 계획을 대조하고 논의한 연구 설계다. 합의 경과와 문서 보존 범위는 [토론·승인 기록](consensus-discussion-2026-10-26/README.md)으로 확인한다. 현행 실행 범위는 [새 실행 상세안](fresh-evaluation-run-plan-2026-10-26.md), 사용자가 선택한 구축 범위는 [구현 시작 프롬프트](fresh-evaluation-implementation-prompt-2026-10-26.md)에 둔다. 이 문서는 구현·실험 완료나 성능 우위를 선언하지 않는다.

2026-10-26 사용자가 기존 결과를 제외하고 S1~S4 모두 새로 평가하기로 확정했다. 중간 초안·초기 실행안·대화 원본은 로컬 아카이브로 정리하고, 이 문서는 연결 안내만 갱신했다. 아래 연구 설계 본문은 승인 당시와 동일하다. 현재 기준은 이 연구 설계와 새 구축·실행 상세안이며, 이전 계획과 충돌하는 부분은 현행 문서를 따른다. 과거 원자료와 평가 계약은 소급 변경하지 않는다.

## 1. 연구적으로 완전하다는 의미

완전한 평가란 모든 장애를 무한히 반복하는 것이 아니라, 선언한 연구 질문마다 적절한 비교, 관측, 반증 조건, 분석, 허용되는 결론이 연결된 평가다. 결과가 불리해도 질문에 정직하게 답할 수 있으면 평가 자체는 유효하다.

연구를 다음 두 범위로 구분한다.

- **범위 내 평가:** 정의한 S1~S4와 테스트베드에서 필요성·기전·복구·안전·운영 부담·비용을 평가한다. 표본 수와 불확실성을 공개하며 프로토타입에 관한 제한된 결론을 낸다.
- **주장 확장 평가:** 높은 신뢰도 수치, 다른 topology·배포·workload, 일반 운영자, 대규모·장시간 운영으로 결론을 넓히는 추가 모듈이다. 전체 설계에 포함하되 모든 졸업 논문의 필수 통과 조건으로 만들지 않는다.

99% 복구율·299회, cell당 30 block, 운영자 24명, 72시간 soak는 보편적 필수값이 아니다. 주장할 정밀도와 파일럿에서 결정하는 규모 또는 산식 예시다. Codex의 이전 전체안에서 99%를 기본 목표로 놓은 부분은 철회한다. 반대로 기간이 부족하다는 이유로 평가하지 않은 안전성·일반화를 이미 입증했다고 쓰지 않는다.

## 2. 무엇이 이 작품의 기여인가

| 시나리오 | 정보 | 실제 조치 | 기여와 한계 |
|---|---|---|---|
| S1 CPU 경합 | 서비스·Pod와 VM·compute 배치/CPU/PSI 연결 | Kubernetes Deployment 배치 변경 | 교차 계층 정보를 이용한 K8s 재배치. OpenStack actuator가 필요하다는 증거가 아님 |
| S2 공유 송신 혼잡 | API 영향, port·공유 경로·queue·업로드 상태 | K8s workload 분리 + Neutron QoS | port 제어 단위를 분리하고 서비스와 업로드를 조정하는 결합 |
| S3 통신 단절·DB | Node/Pod, VM·hypervisor 상태, volume identity | VM fencing + out-of-service·CSI 복구 | 안전한 기존 writer 차단과 stateful 복구 순서 |
| S4 worker VM 정지 | Node·Machine·VM와 서비스/용량 연결 | 기존 MHC·CAPI·CAPO의 교체 | 기존 기능의 통합, 자체 실행·재개·판정·정리의 정확성 |

시나리오별 실행기를 시험 도구가 선택했다면 범용 원인 분류를 구현한 것이 아니다. 실제 시스템이 허용하는 등록 정보와 선택된 시나리오는 모든 비교군에 공개한다. 주입 원인·정답 대상·발생 시각은 정책에 전달하지 않는다.

## 3. 주장 등록부

| 주장 | 질문 | 필요한 증거 | 반증·제한 |
|---|---|---|---|
| R1 필요성 | 기존 기능으로 남는 서비스·용량 문제가 있는가? | N/M 비교와 실제 서비스 관측 | 기존 기능이 이미 같은 목표 충족 |
| R2 정보 기여 | 계층 간 정보가 판단·대상 선택을 개선하는가? | 단일/결합 정보 규칙, 음성 조건, replay와 live 비교 | 신호 표만 있으면 동기·관측 증거에 한정 |
| R3 조치 기전 | 어떤 조치가 효과를 만들었는가? | 동일 진단에서 재시작·분리·QoS·fencing 등 제거 비교 | 개별 조치로 동등하게 복구되면 결합 필수 주장 축소 |
| R4 복구 효과 | 서비스·데이터·용량까지 회복하는가? | 원자료 기반 효과·안전 복구율·시간·미복구 | 성공 반환·Pod Ready만으로는 불충분 |
| R5 안전·강건성 | 불완전한 조건·부분 실패에서 적절히 행동하는가? | 반례, stale identity, API·실행기 실패, 중복·충돌 | 정상 run 반복만으로 넓은 강건성 주장 불가 |
| R6 운영 효율 | 실제 사람의 대응 시간·작업을 줄이는가? | 실제 운영자, 동일 정보·도구·판정과 작업 기록 | 스크립트 런북·정적 명령 수는 인간 시간 측정 아님 |
| R7 비용·범위 | 비용과 효과가 어느 조건까지 유지되는가? | overhead, 부하/규모·전이·민감도·장시간 시험 | 측정하지 않은 규모·환경·운영 조건은 미검증 |

각 실행 cell에는 `주장 ID, 환경/장애/부하, E-ID, 비교군, 계획/실행 n, 증거 종류, 허용/금지 문장`을 붙인다. 결과는 `지지 / 반박 / 불확실 / 범위 밖`으로 기록한다. 실측·replay·문헌·코드 근거를 같은 완료 표시로 합치지 않는다.

## 4. 비교군과 변경 통제

| 군 | 정의 |
|---|---|
| N-native | 버전과 실제 배포 설정을 공개한 기존 시스템. 자체 모듈만 제외 |
| M-matched | P와 동일한 timer·기존 제어기·배치·부하에서 자체 조치만 억제 |
| P-proposed | 평가할 버전의 전체 제안 정책 |
| A-ablation | 특정 정보·조치 한 개를 제거/대체한 군 |
| F-fixed | 별도 calibration으로 정한 합리적 고정 정책·안전 runbook |
| H-human | 실제 운영자가 같은 안전 조건·도구로 대응 |
| Q-oracle | 정답 진단/대상 제공 참조. 실행 지연 분석용이며 현실 대안과 구분 |

N과 M이 실제로 같으면 합치되 다르면 둘의 의미를 분리한다. MHC-off는 특정 기능 제거군이며 ‘표준 CAPI보다 자체 알고리즘이 우월하다’는 baseline이 아니다. 같은 조치를 하는 두 군을 별개 증거로 중복 계수하지 않는다.

부하·이미지·최종 replica·자원·관측 해상도·안전 executor를 맞춘다. 단일 정보 정책은 허용된 정보에서 작동하는 합리적 규칙이어야 한다. 전체 정책에서 필수 필드만 삭제해 항상 오류가 나게 하는 대안은 금지한다. derived mapping을 통해 제거한 정보가 새어 들어오지 않도록 실제 읽은 필드와 출처를 기록한다.

### S3 설정 통제의 합의

현재 fixture는 not-ready/unreachable toleration 3,600초와 timeout force-detach 비활성화를 사용한다. remediation skip의 실제 효과는 실행 중 MHC가 있는지 확인해야 알 수 있다. 코드에 annotation이 있다는 사실만으로 MHC 영향을 제거했다고 단정하지 않는다.

- 원래 구성의 P3600 대 M3600은 그 구성에서의 추가 효과다.
- out-of-service 한 조치의 효과를 보려면 **P300 대 fencing-only300**처럼 양쪽 toleration과 나머지 설정을 맞춘 새 cohort를 사용한다. ‘P에서는 timer가 영향 없을 것’이라는 예상으로 통제를 면제하지 않는다.
- N은 admitted Pod·controller-manager·MHC의 실제 설정으로 확인한다. 300초는 확인할 후보 기본값이며 모든 배포에 선험적으로 적용하지 않는다.
- H는 native/matched timer chain을 확인한 뒤 고정한다. 10~15분 내 미복구는 그 관측 구간의 결과이며 영구적 복구 불가능을 뜻하지 않는다.
- 보호를 제거한 위험 경로를 안전한 성능 baseline으로 쓰지 않는다. guard 제거는 replay/mock 등 별도 안전 검증으로 분리한다.

## 5. 계측·판정·데이터 안전

주입기, 정책, 외부 측정기, 독립 판정기를 분리한다. 정책 summary는 원자료 위치를 찾는 보조 정보이며 성공 판정의 정답이 아니다.

사건 시각은 `주입 요청 → 실제 적용 → 서비스 영향 → 증상 통보 → 탐지/진단 완료 → 조치 요청/적용 → 지속 회복 시작 → 안정 확인 → 용량/데이터 최종 확인`으로 구분한다. UTC와 프로세스 내 monotonic duration을 사용하며 서로 다른 host의 monotonic 값을 빼지 않는다. clock offset·sampling gap·주입 지연을 기록한다.

E00에서 모든 사건 필드의 이름·기록 코드 위치·실제 의미·clock·관측 간격·분석 가능 지표를 감사표로 만든다. 이름과 의미가 다르면 실제 의미로 재정의하기 전까지 분석에 사용하지 않는다. 기존 자료의 지표별 `계산 가능/구간 추정/불가` 열을 필수로 둔다.

| 지표 | 정의 |
|---|---|
| 영향→지속 회복 경과 | 첫 영향부터 지속 정상 구간 시작까지. 중간 정상 구간을 포함하는 경과 시간 |
| 실제 SLO 위반 시간 D | 사전 정의된 bin에서 목표를 위반한 시간의 합. 연속 관측이 있어야 계산 |
| bad request | 실패·timeout·잘못된 응답·deadline 초과의 합집합 |
| goodput | deadline 안에 정확하게 완료한 요청 또는 ACK된 고유 업로드 byte |
| 안전 복구율 | 같은 H 내 서비스·데이터·자원 목표와 안전 불변식을 모두 만족한 run 비율 |
| 용량 결손 | 목표 usable worker/CPU와 실제 상태의 차이를 시간 적분. 실제 scheduling 확인 병기 |
| 운영 부담 | 인지·조회·판단·명령·정정·검증의 hands-on 시간과 개입 수. 시스템 대기는 별도 |
| 부수 피해 | 대상 이외 workload의 실제 오류·중단·작업 손실. Pod 수만으로 대체하지 않음 |

full 연구에서는 workload별 SLO·H·안정창을 calibration하고 동결한다. 기존 결과의 1.2/1.3배 기준이나 시나리오별 안정창을 소급 바꾸지 않는다. 마감 실행은 기존 계약을 유지하고, 새 외부 SLO 분석을 추가하면 별도 사전 분석 계약으로 표시한다.

요청 생성기는 offered load를 보존하고 scheduled/start/end를 기록한다. 현 S1은 open-loop 구조지만 예정시각이 모두 저장되는 것은 아니다. 현 S2 역시 scheduler queue 지연을 포함한 완전한 offered-load 증거인지 확인해야 한다. 부족한 시각은 추측으로 채우지 않는다. generator 포화와 서비스 실패를 구분한다.

### S3 시간 귀속 정정

`experiments/graduation_s3.py`의 `node_not_ready_at`은 Node가 NotReady가 된 순간이 아니라, NotReady 대기 이후 15회 DB 실패 검사까지 끝난 **진단 완료 시각**에 기록된다. 따라서 기존 분석에서 이 구간 전체를 Kubernetes의 Node 이상 감지에 귀속한 설명은 사용하지 않는다.

기존 raw·숫자는 보존한다. `fault-impact.json`의 첫 probe 시각은 실제 NotReady 관측 이후의 경계값으로 사용할 수 있지만 정확한 NotReady 시각을 대신하지 않는다. 재분석으로 실제 사건을 확인하지 못하면 `주입→진단완료`로 이름을 바꾸고 미분해 구간을 남긴다. 기존 72.5초·36초 같은 단계 귀속을 근거 없이 새 숫자로 고치지 않는다.

과거 원자료로 D를 계산할 수 있는지는 시나리오별 `계산 가능 / 구간 추정 / 불가`로 판정한다. S3의 구간별 probe와 5초 폴링만으로 전체 연속 DB RTO를 만들지 않는다. S4 API proxy 관측을 일반 ingress 중단시간으로 바꾸어 부르지 않는다.

### 안전과 결과를 별도 축으로 기록

대상·identity·ownership, 최신 상태 재확인, 기존 writer 접근 차단, ACK 데이터 보존, 중복 부작용 억제, 기존 제어기와의 충돌 처리, cleanup을 불변식으로 둔다.

결과는 가용성(회복/부분/미회복/불명), 안전·행동(적절한 조치/정상 보류/불필요·위험 조치/불명), 실행(정상 완료/예외 중단/개입/timeout)을 나눈다. 예외로 멈춰 파괴적 조치가 없었다는 사실을 정상적인 보류·자동 재개 성공으로 표현하지 않는다. 원인 오진과 조치의 실제 효과도 분리한다.

DB는 외부 durable ACK 원장, 고유 transaction ID·payload digest·재시도 이력으로 손실·변조·중복 부작용을 확인한다. ACK 소실로 결과가 불명확한 in-flight transaction은 commit 손실과 구분한다. seed 보존만 한 실험은 지속 쓰기 내구성으로 확대하지 않는다. 단일 attachment 표시만으로 실제 single writer를 단정하지 않는다.

## 6. 전체 실험 카탈로그

E00~E12를 모두 연구 설계에 유지한다. 아래는 주장별 필요한 실험이고, 실제 마감용 선택은 실행 합의안에서만 한다.

| ID | 핵심 설계 | 필요한 결과 |
|---|---|---|

### E01/E02: topology 식별 조건

현 두 worker가 서로 다른 compute에 있으면 ‘다른 노드’와 ‘다른 compute’ 선택이 같은 결과가 된다. 이 환경에서는 위치 정보가 없으면 잘못된 목적지를 고른다는 인과 효과를 식별할 수 없다.

현재 topology에서 같은 worker 재시작 대 다른 compute 이동은 재시작과 배치 기전을 시험한다. host-only/service-only 반례는 결합 판단의 경계를 설명한다. 목적지 topology 정보 자체의 효과는 같은 compute의 다른 worker, 다른 compute의 혼잡 worker, 정상 worker가 공존하는 확장 환경에서 평가한다.

서비스 지연만 있는 V2가 실제 host 경합도 만들면 목표 음성 조건 재현 실패다. 다른 원인으로 느려진 서비스가 재배치로 좋아질 수도 있으므로 `원인귀속`, `행동 적절성`, `서비스 효과`를 별도 판정한다. 무조건 이동=오조치, 보류=성공으로 라벨링하지 않는다.

### E03: S2 비교를 강하게 만드는 조건

공유 port에 제한을 건 조건은 API 트래픽도 함께 제한한다. 업로더 전용 port에 맞춘 rate/burst 하나만 공유 port에 적용하고 실패했다고 모든 인프라 단독 대응이 불가능하다고 결론 내리지 않는다.

공유 port용 rate×burst와 uploader 전용 port용 값을 별도 calibration에서 고르고 본실험 전 고정한다. API 목표를 만족시키는 합리적인 고정 대안을 사용한다. application-level rate limit 등 다른 제어 granularity의 대안은 그 권한·구현 가정과 함께 다룬다.

독립 run의 reset과 run 내 crossover는 모두 정당한 설계가 될 수 있다. crossover를 주 설계로 사용하려면 순서 균형, queue/TCP·정책의 잔류 영향 해소, uploader 진척·job 상태의 동등성, 동일 길이 창을 확인해야 한다. 분석 단위는 run이다. 이를 확인하지 못한 고정순서 stage는 기전 관측으로 보고한다. 기존 순차 자료를 엄밀한 무편향 factorial 효과추정으로 소급 바꾸지 않는다.

동적 제어는 최적 제한값이 달라지는 사전 등록 부하 trace에서도 평가한다. 마지막 rate가 항상 같은 고정 부하만으로 적응성을 주장하지 않는다. API 피해와 uploader 성능의 두 목표를 함께 판정한다.

### E04/E06: S3 transient의 해석

현재 코드는 일시 장애에서 명시적 보류·재개 정책을 갖췄다고 가정할 수 없다. 해제가 NotReady 전이면 대기 timeout, DB probe 중이면 sustained-impact 검사 예외, 진단 후이면 fencing으로 진행할 수 있다.

이른/늦은 해제를 실제 probe·진단 사건과 연결해 기록한다. 정책이 사전에 알 수 없는 미래 해제를 알고 행동해야 한다고 요구하지 않는다. 허용 중단·persistence 목표를 실행 전에 등록하고, 결과는 예외 중단 여부·파괴적 요청/적용·서비스 자가 회복·불필요한 중단 비용으로 보고한다. 한두 번의 경계 사례는 존재 증거이지 낮은 오개입 확률의 추정이 아니다.

### E07: 상태 기계 기반 부분 실패

각 변경의 intent 저장 전후, 요청 전후, 적용 후 응답 전, 결과 저장 전후, cleanup 단계에서 failpoint를 시험한다. 적용 전 실패와 적용 후 응답 소실을 구분한다. 같은 사건 중복, 연속 재시작, 외부 rollout/CA/MHC/GitOps 변경과의 충돌을 포함한다.

실제 API side effect·identity·volume writer 상태로 중복·안전성을 판단한다. 같은 명령을 한 번 보냈다는 기록만으로 exactly-once를 선언하지 않는다. 무한 retry, 잘못된 rollback, 잔존 자원도 실패다. 소수의 체계적인 failpoint 시험과 많은 정상 반복은 서로 대체하지 않는다.

## 7. 환경·부하·사람·확장 모듈

기본 환경 T0의 nested virtualization, 비대칭 host 사양, control-plane 동거, 고정 worker 수를 공개한다. source/target 사양 차이가 있는 결과를 동급 host에서도 같은 효과라고 일반화하지 않는다. 부하와 장애 강도는 독립 calibration에서 고정하고 actual physical effect를 함께 기록한다.

대표 부하 수준·강도·지속시간·목적지 여유를 교차시키되, 모든 축의 무한 직교곱 대신 식별할 상호작용을 지정한다. 부하×강도, 관측지연×지속시간, API 응답 소실×프로세스 중단, rate×burst는 명시적 조합으로 다룬다. pairwise coverage로 모든 고차 상호작용을 검증했다고 말하지 않는다.

사람 실험은 동일한 증상·도구·안전 executor를 제공하고 진단/선택을 대신하는 보조 도구를 금지하거나 별도 조건으로 둔다. H-D와 H-E, 인지·판단·명령·검증·대기를 구분한다. 원인·목적지 정답을 아는 개발자 1인 결과는 유리한 수동 조건의 사례이며 일반 운영자 시간의 엄밀한 하한이 아니다.

| 확장 | 새로 허용할 주장 | 필요한 추가 증거 |
|---|---|---|
| X1 신뢰도 수치 | 특정 stratum의 높은 성공률/낮은 오개입률 | 사전 확률·신뢰수준·분포 가정과 그에 맞는 독립 반복 |
| X2 topology | 물리 위치 정보의 선택 기여 | 같은/different compute와 건강/혼잡 목적지를 구분할 topology |
| X3 환경·workload | 다른 배포·서비스로의 일반화 | 독립 환경·미사용 workload, 무튜닝/재보정 결과 분리 |
| X4 운영자 | 더 넓은 운영자 집단의 효과 | 여러 독립 참여자·숙련도 층·학습 통제·participant 분석 |
| X5 장시간 | 오개입 노출율·누적 결함 | 시간 노출, 반복 campaign, 군집·정상성 가정 검토 |
| X6 규모 | 관리 규모·동시 장애의 확장성 | 규모별 overhead·queue·수렴·rate limit |
| X7 민감도 | 특정 threshold에 국한되지 않는 효과 | 사전 격자·상호작용·별도 holdout |

확장하지 않으면 그 주장을 제한하는 것이며 해당 항목을 ‘통과’로 표시하지 않는다. full 설계에서 확장 모듈은 삭제하지 않는다.

## 8. 표본 수와 통계

성능 비교는 독립 episode와 block을 표본 단위로 한다. request·관측창·동일 run의 S2 stage를 독립 반복으로 세지 않는다. workload·host session·날짜·순서를 통제하고 block 내부에서 비교군을 균형화한다.

pilot에서 분산·군집·timeout 비율을 추정하고, 서비스상 의미 있는 최소 차이와 목표 CI 폭을 본실험 전에 정한다. 그 가정에 맞는 표본 수와 분석 절차를 등록한다. 효과가 큰 기존 자료는 pilot 설계에 참고할 수 있지만, 본실험 결과를 보다가 유의해지는 순간 멈추거나 경계 조건으로 예산을 임의 이동하지 않는다.

raw 점·paired 차이·중앙값/범위·효과 크기·CI를 함께 제시한다. primary contrast와 다중 비교 처리를 사전 고정한다. 4:4의 최소 p가 0.05보다 작다는 이유로 그 수를 과학적 최소 표본이라고 하지 않는다. p>0.05를 동일 성능 또는 안전성의 동등성 증명으로 쓰지 않는다.

X1을 선택한다면, 독립 동일 확률 이항 시행에서 실패 0건의 성공확률 단측 95% 하한은 `0.05^(1/n)`이다. 95% 하한은 59회, 99%는 299회, 99.9%는 2,995회가 필요한 산식 예시다. 여러 stratum 동시 보장·시행 상관·실패 발생이 있으면 그대로 적용할 수 없다. 이 수치는 이번 마감용 실행 횟수가 아니다.

안전 위반·영구 실패·구조 개입은 단순한 무정보 censoring으로 지우지 않는다. H 종료의 미회복, 성공 run의 조건부 시간, 전체 D/오류를 함께 보고한다. 결측은 정상으로 채우지 않고 가능한 상하한과 원인을 표시한다. 회복 뒤 재악화도 유지한다.

## 9. 실행·freeze·재현

준비 실패, 주입 실패, 주입은 됐지만 서비스 영향 없음, 목표 음성 조건 미성립, 복구 실패, 관측 불완전을 구분하고 모든 attempt를 남긴다. ‘기대한 장애가 크게 난 run’만 선택하지 않는다. 재실행은 이전 시도를 대체하지 않는다.

source/fixture/profile/분석 hash, seed, 배치·identity, 실제 actor와 주입·계측 경로, 원본 요청·ACK·state/audit·결정·cleanup을 보존한다. 과거 자료를 새 계약에 맞춰 수정하지 않는다. 소스 수정 후에는 새 cohort를 만든다.

현재 실행기는 scripts/experiments/evaluation/tests 등의 광범위한 hash를 검증한다. campaign 중 같은 checkout에서 후속 변형을 구현하면 계약이 깨질 수 있다. 병행 개발은 실행 checkout과 원격 배포 파일을 바꾸지 않는 별도 checkout에서만 하며, 격리·전환 검증 비용을 포함한다. 그 환경이 없으면 순차 구현·freeze·실행한다.

hash 검사는 freeze 때뿐 아니라 각 case 이후에도 수행된다. 신규 모드는 cohort 밖에서 smoke를 통과시킨다. freeze가 다른 P, 기존 1,080초 S1 부하와 새 1,800초 부하의 결과는 하나의 cohort로 합치지 않는다. 사람이 빠진 부분 block의 처리·순서 불균형·허용되는 비교도 실행 전에 고정한다.

판정기 자체는 known trace·결측·중복·timestamp 역순으로 검증한다. 독립 재분석은 raw에서 표를 재생성하는 것이고, 독립 환경 재현은 다른 수행자가 fresh 환경에서 실험하는 것으로 구분한다.

## 10. 완료와 문서의 사용법

연구 완료는 모든 질문에 좋은 답이 나오는 것이 아니다. 예정 cell의 수행 상태가 분명하고, 원자료·불리한 결과·결측·개입이 보존되며, 주장별로 허용되는 문장이 정해져야 한다.

본문 결과는 R1~R7 순서로 환경·비교군, 기전, 효과, 반례, 인간 사례, 비용·한계를 연결한다. 실행안에서 제외된 cell은 그 주장 등록부에도 미검증으로 남긴다. 좁은 프로토타입 사례의 성공을 범용 자동 장애 진단, 생산환경 신뢰도, 임의 장애 안전성으로 확대하지 않는다.

이후 시간·비용 선택은 별도 실행 문서의 gate와 산식을 따른다. 사용자 참여·제출일·클라우드 예산 같은 미확인 정보는 가정 또는 의존성으로 남기고, 두 에이전트의 합의를 사용자 확인이나 실험 수행으로 바꾸어 표현하지 않는다.
