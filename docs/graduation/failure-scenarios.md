# 졸업작품 장애 시나리오 정의서

- 작성일: 2026-09-25
- 버전: 0.1
- 상태: 대화에서 구체화한 설계 기준선. 본 문서의 작성은 구현·실환경 검증 완료를 의미하지 않는다.
- 작품 주제: **OpenStack 기반 Kubernetes 환경에서 대표 장애 대응 자동화 모듈 프로토타입 설계 및 구현**
- 적용 관점: 일반적인 OpenStack 위의 Kubernetes 클러스터에서 운영되는 서비스의 장애와 복구

## 1. 목적과 범위

Kubernetes의 서비스·Pod·Node 상태와 OpenStack의 VM·compute·네트워크·볼륨 상태를 연결하여, 사전에 정의한 장애에 대한 복구 절차를 자동화한다. 장애의 원인을 특정 사용자의 소프트웨어로 한정하지 않는다.

졸업작품의 주제는 신청서를 따르며, 대상 장애 시나리오는 논의 결과를 반영해 구체화한다. 제품 PRD의 고객·제품 요구사항은 이 문서의 선정 기준으로 사용하지 않는다. 현재 저장소의 구현 상황은 실행 계획을 세울 때 참고하되, 시나리오 자체의 타당성과 분리한다.

시나리오는 다음 조건을 함께 만족해야 한다.

1. 실제로 발생 가능한 서비스 장애이며, 발생 조건과 영향을 설명할 수 있다.
2. Kubernetes와 OpenStack의 상태 또는 제어를 연결하는 실질적인 이유가 있다.
3. 복구 조치와 완료 조건이 명확하며 자동화할 수 있다.
4. 직접 구현할 부분과 기존 기능을 활용하는 부분을 구분할 수 있다.

CAPI·CAPO 등 기존 도구로 해결할 수 있는 장애도 포함한다. 기존 도구 활용 비중은 직접 구현 범위와 우선순위에 반영한다. 모든 장애를 새 모듈만이 해결할 수 있다고 주장하지 않는다.

### 1.1 선정 시나리오

| ID | 시나리오 | 서비스 영향 | 복구 방향 | 작품 내 역할 |
|---|---|---|---|---|
| S1 | 동일 compute의 VM 간 CPU 경합 | API 응답 지연·타임아웃 | 다른 compute의 worker로 API Pod 재배치 | 직접 구현 핵심 |
| S2 | 공통 송신 경로 혼잡과 혼재 워크로드 | API 응답 지연·타임아웃 | 업로드 작업 분리 후 Neutron QoS 동적 조정 | 직접 구현 핵심; 효과 실험 필요 |
| S3 | 노드 제어 통신 두절 후 stateful 서비스 복구 | DB 접근 실패·대체 Pod 기동 지연 | 기존 VM 종료 확인 후 영구 볼륨 재연결·DB 재기동 | 직접 구현 핵심 |
| S4 | worker VM 중단 | 서비스 실행 중단 또는 복제본·처리 여력 감소 | Pod 재실행과 대체 worker 생성 | 기존 도구를 활용한 기본 복구 |

worker 메모리 압력, 디스크 I/O 경합, 부분 통신 장애, conntrack 고갈 등은 후속 후보로 남긴다. 본 문서의 네 시나리오에 자동으로 포함하지 않는다.

## 2. 공통 설계 원칙

### 2.1 상태 연결과 관측

기본 관계는 다음과 같다.

```text
Service / Deployment / StatefulSet
  → Pod → Node → Nova VM → compute
                       ├→ Neutron port / network
                       └→ Cinder volume attachment
```

Node와 VM은 providerID 등 검증 가능한 식별자로 연결한다. 이름이 유사하다는 이유만으로 대상을 결정하지 않는다. 호스트 배치는 변경될 수 있으므로 조치 직전에 다시 확인한다.

최소 관측 대상은 서비스 성공률·응답 시간, Pod 배치·준비 상태, Node 상태, 대상 VM 및 관련 인프라 상태다. 호스트 경합을 다루는 S1·S2는 OpenStack API 조회 외에 호스트·네트워크 지표가 필요하다. 지표 접근 권한과 수집 위치는 구현 전에 확인한다.

### 2.2 장애 판단과 복구 완료

자원 사용률이 높다는 이유만으로 장애를 선언하지 않는다. S1·S2에서는 서비스 영향과 해당 자원·경로의 이상 증거를 함께 확인한다. S3·S4에서는 실제 서비스 영향과 인프라 복구 상태를 각각 기록한다.

임계값은 아직 확정하지 않았다. 다음 항목을 정상 부하 측정과 사전 실험으로 정한 뒤 실행별로 고정한다.

| 항목 | 정의할 내용 |
|---|---|
| 서비스 목표 | 요청 종류, 목표 지연, 허용 오류율, 필요한 최소 처리량 |
| 판정 창 | 관측 주기, 집계 구간, 최소 표본 수, 이상 지속 시간 |
| 자원·경로 기준 | CPU 대기, 네트워크 포화 등 시나리오별 판단 근거 |
| 조치 상한 | 동시 복구 수, 단계별 제한 시간, 재시도 횟수 |
| 안정화 기준 | 복구 후 목표를 연속 만족할 시간, 재조치 대기 시간 |

한 번의 정상 응답이나 Pod Running만으로 완료하지 않는다. 목적에 맞는 서비스 요청이 안정적으로 성공해야 한다. 지표가 없거나 근거가 충돌하면 판정을 보류한다.

### 2.3 제어와 실패 처리

- 관리 대상으로 등록된 서비스·작업과 인프라에만 조치한다.
- 대상별 복구 진행 상태를 기록하고, 중복 이벤트나 모듈 재시작으로 조치가 중복되지 않게 한다.
- CAPI, Cluster Autoscaler, GitOps 등 기존 제어기와 자원 소유권·동시 변경 정책을 정한다.
- Kubernetes 스케줄링 제약과 워크로드의 가용성 요구를 지킨다.
- 조치가 실패하거나 안전 조건을 충족하지 못하면 다음 단계를 강행하지 않고 상태와 원인을 남긴다.
- 기존 자동 복구 기능은 평가에 포함한다. 효과를 만들기 위해 기본 복구 기능을 임의로 끄지 않는다.

## 3. S1 — 동일 compute의 VM 간 CPU 경합

### 3.1 시나리오 정의

> 공유 CPU를 사용하는 OpenStack 환경에서 동일 compute의 다른 VM이 CPU를 많이 사용하여 stateless API 서비스의 응답 지연이 지속된다. 서비스와 호스트의 상태를 연결해 경합을 판단하고, 여유 있는 다른 compute의 worker에 API Pod를 재배치한다.

### 3.2 구성과 전제

```text
compute A
 ├─ worker VM A: API Pod
 └─ VM B: CPU 집약 작업

compute B
 └─ worker VM C: API Pod를 수용할 여유
```

- VM은 shared CPU 정책을 사용한다. CPU pinning으로 격리된 환경은 최초 범위에서 제외한다.
- API는 CPU를 사용하는 stateless HTTP 서비스이며, DB·외부 통신 의존성은 최소화한다.
- 경쟁 작업은 API와 다른 VM에서 실행한다. 같은 worker 내부의 Pod 간 CPU 경쟁과 구분한다.
- 실제 동시 실행 수요가 공유 CPU 자원의 경합을 유발해야 한다. vCPU 할당 수만으로 경합을 입증하지 않는다.
- 목적지 worker와 compute에 CPU·메모리 여유가 있고, API의 스케줄링 조건을 만족한다.
- 최초 복구 범위는 기존 worker로의 재배치다. 목적지가 없을 때 새 VM을 만드는 기능은 후속 확장이다.

Nova의 shared CPU 정책에서는 vCPU가 호스트 CPU를 공유하며, 심한 경합은 개별 VM의 성능과 지연에 영향을 줄 수 있다. [R1]

### 3.3 장애 발생과 판단

정상 요청량에서 API 응답을 측정한 뒤 VM B에 지속적인 CPU 부하가 발생한다. API VM과 Node는 정상 실행 상태를 유지할 수 있지만 API 지연·오류가 목표를 초과한다.

| 관측 | 의미 |
|---|---|
| API 지연·오류의 지속 증가 | 서비스 영향 확인 |
| Pod CPU throttling 및 자체 CPU 수요 | Pod 설정·자체 과부하와 구분 |
| API VM과 경쟁 VM의 동일 compute 배치 | 공유 자원 관계 확인 |
| compute CPU 실행 대기·경합 및 VM 관측 | 호스트 경합 가설의 근거 |
| 목적지의 실제 부하와 Node 자원 여유 | 복구 목적지의 유효성 |

게스트 steal time은 제공되는 환경에서 보조 지표로 사용한다. 단일 지표를 모든 환경의 필수 조건으로 고정하지 않는다. 메모리·I/O·외부 의존성 장애와 구분할 수 없으면 자동 재배치를 보류한다.

### 3.4 자동 복구 절차

1. Pod–Node–VM–compute 관계와 장애 증거를 확인한다.
2. 다른 compute의 worker 중 조건을 만족하는 목적지를 선택한다.
3. 관리 대상 Deployment의 배치 조건을 조정해 목적지에 대체 Pod를 먼저 실행한다.
4. 대체 Pod의 준비 상태를 확인한 뒤 기존 Pod를 종료한다.
5. 최종 복제본 수를 원래 값으로 유지하고, 실제 서비스 회복을 확인한다.
6. 조치 결과와 배치 변경을 기록하고 반복 이동 방지 시간을 적용한다.

목적지 준비 실패 시 기존 Pod를 성급하게 종료하지 않는다. 배치 조건 변경은 기존 선언형 관리와 충돌하지 않는 방식으로 수행한다.

### 3.5 구현 경계와 완료 기준

| 직접 구현 | 기존 기능 활용 |
|---|---|
| 서비스 영향과 compute 경합 연결 | Nova VM·호스트 정보 조회 |
| 물리 배치를 고려한 목적지 선택 | Kubernetes affinity 등 배치 기능 |
| 교체 순서·실패·반복 이동 제어 | Deployment의 Pod 교체와 readiness |
| 서비스 회복 판정과 실행 기록 | 기존 지표·로그 수집 |

완료 조건은 다른 compute에서 목표 복제본 수가 준비되고 API가 안정화 구간 동안 서비스 목표를 만족하는 것이다.

경쟁 부하와 API 요청은 재배치 후에도 유지한다. 최종 복제본 수·요청량·이미지·Pod 자원 설정을 동일하게 유지해 단순 증설 효과와 구분한다. 초기화·캐시 준비 시간을 포함한다. 필요하면 같은 compute 내 재시작·재배치를 대조해 호스트 변경의 효과를 확인한다.

CPU pinning과 Watcher의 VM 이동은 기존 대안이다. 본 시나리오의 기여는 서비스 상태와 Pod 단위 복구를 연결하는 판단·실행 절차이며, 유일한 해결책이라고 주장하지 않는다. [R1][R2]

## 4. S2 — 공통 송신 경로 혼잡과 혼재 워크로드

### 4.1 시나리오 정의

> 같은 worker의 API 서비스와 대량 업로드 작업이 공통 외부 출구를 사용한다. 업로드와 API 트래픽의 경합으로 API 응답이 악화되면 업로드를 별도 worker로 분리하고, 해당 VM 포트에만 QoS 제한을 적용·조정하여 API를 회복시키면서 업로드를 계속 진행한다.

재배치는 공통 병목을 우회하기 위한 것이 아니라, **API와 업로드를 서로 다른 VM 포트의 제어 대상으로 분리하기 위한 것**이다.

### 4.2 구성과 전제

```text
초기
worker A [ API + 업로드 ] ───────────→ 공통 송신 출구
worker B [ 수용 여유 ]

복구 후
worker A [ API ] ──────────────────→ 공통 송신 출구
worker B [ 업로드 ] ── Neutron QoS ─→ 공통 송신 출구
```

- API는 파일·보고서 등 비교적 큰 응답을 반환한다. 배치 작업은 외부 저장소로 대량 업로드한다.
- 두 트래픽이 실제로 공유하는 송신 경로와 유효 용량을 사전에 파악한다.
- 제한은 공통 병목에 도달하기 전 업로드 VM의 송신 포트에 적용할 수 있어야 한다.
- worker B에는 API 등 중요한 서비스가 섞이지 않도록 배치를 관리한다. VM 포트 QoS가 다른 트래픽에도 미칠 영향을 확인한다.
- 업로드는 중단·재개 또는 재실행이 가능하다. 원본·진행 정보가 A의 로컬 디스크에만 있으면 안 된다. 중복 업로드 처리 규칙도 정한다.
- 대상 Neutron 백엔드의 대역폭 제한 기능과 권한을 확인한다. 기존 Pod별 대역폭 제어·동등한 서비스 보호 정책이 있다면 비교 대상에 포함한다.
- 제한으로 worker의 관리 통신을 끊지 않도록 최소 허용량과 변경 범위를 정한다.

Neutron은 포트 등에 대역폭 제한을 적용하고 실행 중 정책을 변경할 수 있다. 지원 규칙과 방향은 백엔드별로 다르다. [R3]

### 4.3 장애 발생과 판단

한가한 시간에는 API와 업로드가 공존할 수 있다. API 수요가 증가해 합산 송신 수요가 출구 용량을 초과하면 대기·드롭·재전송 등으로 API 응답이 악화된다.

설명용 1Gbps 등의 수치를 실제 용량이나 임계값으로 사용하지 않는다. 장애 판단에는 다음을 함께 사용한다.

- API 응답 지연·오류가 목표를 초과하여 지속됨
- 알려진 공통 출구의 포화·큐·드롭 등 병목 증거
- 업로드 트래픽이 해당 경로를 사용하며 혼잡에 기여한다는 근거
- API CPU·DB 등 다른 주요 원인과 구분할 수 있는 상태

모든 네트워크 장애를 자동 진단하는 기능은 범위 밖이다. 병목 위치나 트래픽 기여도를 확인할 수 없으면 이 정책을 실행하지 않는다.

### 4.4 자동 복구 절차

1. API 영향과 공통 출구의 혼잡을 확인한다.
2. 업로드 Pod–Node–VM–Neutron port 관계를 확인한다.
3. worker B의 배치 조건을 확인하고 전용 포트에 초기 QoS 제한을 먼저 적용한다.
4. 업로드를 안전하게 중단·재개하여 B에서 실행한다. 이전 실행의 종료와 진행 정보 보존을 확인한다.
5. API 지연·오류와 업로드 진행 상태를 확인한다.
6. API가 안정적이면 업로드 상한을 단계적으로 높이고, 재악화되면 낮춘다.
7. 해제 조건을 만족하면 사전에 정한 정상 정책으로 복귀한다. 공유 정책 전체를 변경하지 않고 관리 대상 정책만 조정한다.

최초 구현은 몇 단계의 제한값·상하한·관측 대기 시간으로 구성한다. 안정화 전에 연속 변경하지 않으며, API가 회복되지 않으면 제한을 무한히 강화하지 않는다. 한 번 분리한 뒤에는 매번 재배치할 필요 없이 QoS 조정으로 대응할 수 있다.

### 4.5 구현 경계와 완료 기준

| 직접 구현 | 기존 기능 활용 |
|---|---|
| API 영향과 출구 혼잡 연결 | 서비스·호스트·포트 지표 |
| 역할별 작업 식별과 포트 매핑 | Kubernetes 객체, Nova·Neutron 정보 |
| 제한 준비와 작업 분리의 순서 제어 | Kubernetes 배치, 작업의 재개 기능 |
| 제한값 조정·해제·실패 처리 | Neutron QoS |
| API 회복과 업로드 진행 검증 | HTTP 검사, 업로드 결과·진행률 |

완료 조건은 API가 안정화 구간 동안 목표를 만족하고 업로드도 계속 진행되는 것이다. 업로드를 완전히 중단시켜 API만 정상화한 결과는 이 시나리오의 완료로 간주하지 않는다.

고정 QoS가 충분한 환경보다 항상 우수하다고 가정하지 않는다. 무제어, 합리적인 고정 QoS, 제안 제어를 동일한 부하 패턴에서 검토한다. 이미 유효한 우선순위·여유 용량 공유 정책이 있다면 그것도 평가에 포함한다. 주요 지표는 API 지연·실패율, 업로드 완료 시간·진행률, 총 처리량, 분리·정책 변경 비용이다.

현재 미확정 사항은 공유 경로의 구체적 구성, 혼잡 관측 방법, 업로드 재개 방식, QoS 단계값이다. 이들이 확정되고 효과가 확인되기 전에는 구현 효과를 입증했다고 기록하지 않는다.

## 5. S3 — 노드 제어 통신 두절 후 stateful 서비스 복구

### 5.1 시나리오 정의

> 독립적으로 접근 가능한 Cinder 볼륨에 데이터와 WAL을 저장하는 단일 PostgreSQL 서비스에서 worker의 제어 통신이 두절된다. 기존 VM의 실행 중단을 확인한 뒤 같은 볼륨을 정상 worker에 연결하여 DB 서비스를 다시 기동한다.

### 5.2 상태의 위치와 복구 의미

```text
장애 전: worker A의 PostgreSQL → 볼륨 V → 정상 스토리지 백엔드
복구 후: worker B의 PostgreSQL → 같은 볼륨 V → 같은 스토리지 백엔드
```

데이터를 접근 불가능한 A에서 복사해 오는 것이 아니다. 데이터는 이미 영구 볼륨에 저장돼 있으며, B가 같은 볼륨을 다시 연결해 읽는다. Cinder는 영구 블록 저장소를 제공하지만, Cinder 사용 자체가 저장소의 고가용성을 보장하지는 않는다. [R4]

| 상태 | 복구 범위 |
|---|---|
| 영구 볼륨에 내구성 있게 저장된 DB 데이터·WAL | 같은 볼륨 재연결과 DB 자체 복구의 대상 |
| 메모리 캐시·진행 중 요청·미완료 트랜잭션·연결 | 실행 상태 그대로 이전하지 않음; 실패·재시도 가능 |
| 접근 불가능한 노드의 로컬 디스크에만 있는 데이터 | 본 시나리오로 복구할 수 없음 |

새 PostgreSQL 프로세스는 데이터와 WAL을 이용해 재기동한다. 기존 프로세스의 메모리·실행 순간을 그대로 복원하는 기능은 범위 밖이다. [R5]

### 5.3 구성과 전제

- 단일 PostgreSQL 인스턴스와 Cinder CSI 기반 영구 볼륨을 사용한다.
- 데이터 디렉터리와 WAL을 영구 볼륨에 저장하고, 정상적인 내구성 설정과 저장소 동작을 사용한다.
- 저장소 백엔드와 정상 worker의 접근 경로가 살아 있다. 대상 볼륨의 가용 영역·접근 조건을 만족한다.
- worker A의 kubelet 제어 통신이 끊겨도 DB 프로세스는 계속 실행 중일 수 있다.
- OpenStack 관리 경로와 해당 compute가 동작하여 VM을 정지하고 실제 종료를 확인할 수 있다.
- control plane, 복구 모듈, 정상 worker는 장애 범위 밖에 있다.
- 초기 실험에서 외부 요청도 영향받도록 실제 접근 실패·미완료 요청을 확인한다. 제어 통신 두절만으로 DB 서비스 전체가 즉시 중단됐다고 가정하지 않는다.

### 5.4 장애 판단과 안전 조건

Node 이상, 서비스 영향, Pod 정리·대체 기동 상태, 볼륨 연결 상태를 함께 확인한다. `NotReady`만으로 DB 프로세스가 종료됐다고 판단하지 않는다. StatefulSet Pod 강제 삭제는 기존 프로세스 종료를 보장하지 않으므로 종료 확인 없이 새 실행을 허용하지 않는다. [R6]

VM 정지 요청의 접수와 실제 완료를 구분한다. Nova API 상태와 작업 진행을 확인하고, 관리 경로가 불확실하면 신뢰할 수 있는 하이퍼바이저·fencing 근거 없이 종료됐다고 판단하지 않는다. 상태값을 수동 변경하는 것은 fencing이 아니다. Nova 정지 API는 비동기 동작이다. [R7]

### 5.5 자동 복구 절차

1. 지속적인 장애를 확인하고 Node–VM–Pod–PVC/PV–Cinder volume 관계를 검증한다.
2. 해당 자원에 대한 복구 소유권을 확보하고 기존 제어기와의 중복 조치를 방지한다.
3. Nova를 통해 기존 VM 정지를 요청하고 실제 종료 완료를 확인한다.
4. 종료가 확인된 Node에 out-of-service 처리를 적용한다.
5. Kubernetes·CSI의 기존 Pod 정리와 볼륨 분리를 감시한다.
6. 정상 worker에서 동일 볼륨을 사용하는 대체 Pod가 실행되는지 확인한다.
7. PostgreSQL 재기동 후 기존 데이터와 새 읽기·쓰기를 검증한다.
8. 기존 VM은 재사용·교체 정책이 결정될 때까지 자동 재진입시키지 않는다. 재사용할 경우 정상 상태를 확인한 뒤 격리를 해제한다.

out-of-service 적용 전 노드 종료 확인은 Kubernetes가 요구하는 조건이다. Pod toleration과 컨트롤러 설정에 따라 처리 여부가 달라지므로 실행 구성을 확인한다. [R8]

### 5.6 실패 처리와 기존 기능의 관계

- VM 종료 확인 실패: Pod 강제 삭제·볼륨 강제 분리 단계로 진행하지 않는다. 별도 호스트 fencing이 없다면 복구를 보류한다.
- 볼륨 분리·재연결 실패: finalizer 제거·연결 상태 강제 덮어쓰기로 완료 처리하지 않는다.
- 목적지 자원·가용 영역 조건 불충족: 대체 Pod 기동 실패를 기록하고 성공으로 보고하지 않는다.
- DB 기동은 성공했지만 데이터 검증 실패: 복구 실패로 판정한다.

Kubernetes에는 조건에 따른 6분 후 강제 볼륨 분리 동작이 있다. 실행 버전·설정에서 이 동작과 fencing의 순서를 함께 점검한다. 자체 모듈의 순서만으로 전체 시스템의 안전성을 보장했다고 주장하지 않는다. 설정 변경이 필요하면 운영 정책으로 명시하고, 기본 설정의 결과도 별도로 기록한다. [R8]

CAPI의 drain·볼륨 분리 대기와도 조율해야 한다. fencing 완료 전에 복구 절차가 서로 기다리거나, 별도 제어기가 VM을 재기동하지 않도록 소유권과 순서를 정한다. Fence Agents Remediation 등 기존 미들웨어는 비교·재사용 가능한 대안이다. [R9][R10]

### 5.7 구현 경계와 완료 기준

| 직접 구현 | 기존 기능 활용 |
|---|---|
| 장애·관계 확인과 복구 시작 조건 | Node·Pod·볼륨 상태, Nova 정보 |
| 종료 요청·완료 확인·실패 시 중단 | Nova VM 제어 또는 검증된 fencing 수단 |
| 종료 확인 후 K8s 복구를 시작하는 순서 | out-of-service와 StatefulSet controller |
| 단계별 진행·재시도·중복 조치 관리 | Cinder CSI의 분리·재연결 |
| 서비스·데이터 복구 검증 | PostgreSQL 자체 WAL 복구 |

장애 전에 성공적으로 커밋한 시험 레코드의 ID·내용을 별도로 기록한다. 복구 후 해당 레코드의 보존, 새 트랜잭션의 읽기·쓰기, 서비스 안정화, 이전 VM의 실행 중단을 확인한다. 미완료·응답 불명 요청의 결과는 별도 분류한다.

## 6. S4 — worker VM 중단 후 서비스·노드 용량 복구

### 6.1 시나리오 정의

> stateless HTTP 서비스를 실행하던 worker VM 한 대가 중단되어 정상 복귀하지 않는다. 남은 worker에서 서비스 실행을 회복하고, 대체 VM을 생성·가입시켜 클러스터의 목표 worker 용량을 복구한다.

### 6.2 구성과 전제

- 대상은 노드 로컬 데이터나 영구 볼륨에 의존하지 않는 Deployment다.
- control plane과 OpenStack 관리 기능은 정상이며, 한 대의 worker VM만 중단된다.
- 남은 worker에는 대체 Pod를 실행할 여유가 있다.
- 대체 VM을 생성할 OpenStack 자원·quota와 정상 이미지·bootstrap 구성이 있다.
- 일시 재기동 후 복귀하는 경우와 계속 중단되어 교체가 필요한 경우를 구분한다.
- MHC를 사용하면 한 대의 장애를 처리할 수 있는 조건·복구 허용 범위를 설정한다.

시연 대상으로 단일 복제본의 개발·내부 HTTP 서비스를 사용할 수 있다. 여러 복제본인 서비스가 계속 응답했다면 서비스 중단으로 기록하지 않고 복제본·처리 여력 감소를 기록한다.

### 6.3 장애 발생과 복구 흐름

```text
worker VM 중단
 ├─ 서비스 복구
 │   └─ Node 이상 판정 → 기존 절차에 따른 Pod 재실행 → HTTP 응답 회복
 └─ worker 용량 복구
     └─ 장애 Machine 교체 → 대체 Nova VM 생성 → 클러스터 가입 → Node Ready
```

Kubernetes의 Node 이상 판정과 Pod toleration 등에 따른 대기 시간을 포함한다. Pod가 즉시 이동한다고 가정하지 않는다. [R11]

MHC·CAPI·CAPO를 활용해 Machine 교체와 인프라 생성·삭제를 수행할 수 있다. drain·삭제 대기 등의 동작과 시간 제한은 실제 설치 버전의 설정으로 확인한다. [R9][R12]

서비스 복구와 worker 용량 복구는 별개로 진행될 수 있다. 기존 Kubernetes 기능으로 먼저 회복된 서비스 결과를 자체 모듈의 기여로 계산하지 않는다.

### 6.4 구현 경계와 완료 기준

| 항목 | 담당 |
|---|---|
| Pod 재실행·재배치 | Kubernetes |
| 장애 Machine 판정·교체 | MHC·CAPI |
| Nova VM 생성·삭제 | CAPO |
| Node–VM 관계·진행 상태 연결 | 작품의 통합 모듈 |
| 서비스·worker 용량의 별도 완료 판정과 기록 | 작품의 통합 모듈 |

| 복구 대상 | 완료 기준 |
|---|---|
| 서비스 | 목표 복제본이 준비되고 실제 HTTP 요청이 안정적으로 성공 |
| worker 용량 | 목표 worker 수가 Ready이며 새 worker에 시험 Pod를 정상 실행 |

생성 실패·quota 부족·가입 실패·삭제 지연은 단계별 실패로 남긴다. 이 경우 무제한 VM 생성이나 성공 처리를 하지 않는다. 중단된 기존 Machine과 대체 Machine의 최종 정리 상태도 확인한다.

VM 교체 기능 자체를 새로 만드는 것은 최초 범위가 아니다. 기존 기능을 통합한 기본 복구 시나리오로 보고한다.

## 7. 공통 검증 계획과 산출물

### 7.1 실행 절차

1. 이미지·버전·배치·자원 설정·요청 패턴과 판정 기준을 기록한다.
2. 정상 서비스 동작과 필요한 관측·제어 경로를 확인한다.
3. 격리된 시험 환경에서 정의한 장애 조건을 만든다. 부하 발생 도구는 해당 원인을 재현하는 수단이며 발생 빈도의 근거가 아니다.
4. 서비스 영향·장애 판단·조치·회복의 시간과 근거를 수집한다.
5. 실패·보류·부분 회복을 성공과 구분하고 반복 실행 결과를 남긴다.
6. 시험 자원·정책을 정리하거나 다음 실행의 명시된 초기 상태로 복원한다.

### 7.2 기록 항목

| 분류 | 필수 기록 |
|---|---|
| 실행 조건 | 실행 ID, 코드·정책 버전, 컴포넌트 버전, 구성, 배치, 부하·장애 조건 |
| 판단 근거 | 서비스 지표, 계층별 상태, 식별자 관계, 진단 결과·불확실성 |
| 시간 | 장애 주입, 서비스 영향 시작, 감지, 조치 시작·단계 완료, 서비스 안정화 |
| 시나리오별 결과 | S1 배치·경합, S2 QoS·업로드, S3 종료·볼륨·데이터, S4 서비스·용량 |
| 예외 | 타임아웃, 재시도, 보류·실패 사유, 수작업 개입 |
| 최종 상태 | 서비스 상태, 자원·정책 변경, 잔여 자원과 복원 여부 |

서비스 복구 시간은 서비스 영향 시작부터 안정적인 정상화까지로 정의한다. 영향이 없었다면 중단 시간을 만들어 기록하지 않는다. S4의 worker 용량 복구 시간은 별도 지표로 기록한다.

필요한 비교는 시나리오 성립과 효과 확인을 위한 검증이다. 수동 런북, 기본 기능, 기존 도구, 제안 모듈의 역할을 구분하되 모든 대안에 대한 우월성 입증을 목표로 확장하지 않는다.

### 7.3 구현 전 확정할 사항

- 공통: 대상 버전, 지표 수집·권한, 서비스 목표·판정 창, 제어기 간 소유권, 실패·재시도 정책
- S1: 경합 재현 부하, 호스트 경합 지표, 목적지 선택·Deployment 교체 방식
- S2: 실제 공유 송신 경로, QoS 지원·적용 지점, 전용 worker 정책, 업로드 재개 방식과 조정값
- S3: 독립 스토리지 구성, DB 내구성 설정, fencing 완료 근거, 기존 강제 분리·CAPI와의 순서 조율
- S4: 복제본·worker 목표, MHC 복구 조건과 삭제·가입 시간 제한

중간보고서에는 이 정의서를 목표 설계로 사용하고, 구현·시험 결과는 별도 증거와 함께 기재한다. 현재 구현 상황이나 문서에 정의된 절차만으로 검증 완료율을 산정하지 않는다.
