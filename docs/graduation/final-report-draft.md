# 요약

OpenStack VM 위에서 Kubernetes를 운영하는 환경에서는 서비스 장애의 원인과 조치 수단이 서로 다른 관리 계층에 나뉘어 있어, 한 계층의 정보만으로는 적절한 대응을 결정하기 어렵다. 본 작품은 두 계층의 자원 관계를 연결하여 대표 장애 네 가지에 대응하는 모듈을 설계·구현하고 비교 실험으로 검증하였다. Google Cloud 호스트 3대 위에 중첩 가상화로 OpenStack 2025.2와 Kubernetes 1.35.7을 코드로 구축하고 Cluster API와 Cluster Autoscaler를 연동하였다. 대응 모듈은 자원 관계 확인, 조치 조건 판단, 대상 조치, 결과 확인의 네 단계로 동작하며, 외부 요청 원자료로 결과를 독립 판정하는 평가 도구를 함께 구현하였다. 평가 규모는 11개 조건, 총 33회다. 호스트 CPU 경합에서 재배치 후 SLO(Service Level Objective) 위반율은 0.08~0.14%였고, 무조치는 2.44~2.63%, 동일 노드 재시작은 2.24~3.54%였다. 공유 송신 경로 혼잡에서는 작업 분리와 Neutron QoS(Quality of Service)를 적용한 4회 모두 조치 후 위반율이 0%였다. 작업 분리 단독의 조치 후 위반율은 2.63~3.02%로 무조치(1.72~2.34%)보다 낮아지지 않았으며, 제안 방식은 그 대가로 관측 구간 평균 업로드 처리량이 약 66% 감소하였다. 노드 통신 단절에서는 fencing 확인 후 3회 모두 데이터베이스가 회복되고 커밋된 1,000건이 보존되었다. worker 노드 VM 정지에서는 서비스가 약 73~81초 중단된 뒤 남은 노드에서 회복되었고, MachineHealthCheck가 정지 요청 후 283~298초에 노드 용량을 3회 모두 복원하였다. 본 작품은 계층 간 자원 연결과 안전한 조치 순서를 구현하고, 서비스·데이터·용량의 회복을 구분하여 관측하였다. 평가는 고정된 소규모 테스트베드에서 조건당 2~4회 수행한 비교 실험이다.

# 1. 서론

## 1.1 제안 배경 및 필요성

사설 클라우드에서는 OpenStack이 제공하는 VM 위에 Kubernetes 클러스터를 구성하여 컨테이너 서비스를 운영할 수 있다. OpenStack은 VM의 생성과 삭제, 네트워크 연결, 영구 저장소의 제공을 담당한다. Kubernetes는 그 VM을 Node로 사용하여 애플리케이션의 배치와 실행 상태를 관리한다. 이러한 구성은 인프라 자원 관리와 애플리케이션 배포 관리를 나누어 수행하게 한다. 서비스 개발자는 컨테이너와 Pod를 중심으로 실행 환경을 표현하고, 인프라 운영자는 호스트와 VM을 중심으로 자원을 배분한다. 본 작품은 이와 같이 역할이 나뉜 환경에서 장애 대응에 필요한 정보를 연결하는 문제를 다룬다. 정상 운용을 위한 역할 분리는 장애 대응에서도 각 계층이 제공하는 기능을 활용할 수 있는 기반이 된다. 동시에 서비스의 실행 위치와 하위 자원의 상태를 함께 확인해야 할 필요를 만든다.

두 관리 계층은 같은 서비스를 서로 다른 자원 단위로 관측한다. Kubernetes가 보는 대상은 Pod와 Node이며, 서비스가 어느 Node에 배치되어 있는지를 확인할 수 있다. OpenStack은 VM이 놓인 compute 호스트와 해당 VM의 Neutron port, Cinder volume을 관리한다. 하나의 Pod에 요청 지연이 발생해도 원인은 같은 호스트를 쓰는 다른 VM이나 공유 네트워크 경로에 있을 수 있다. 이때 서비스 상태를 읽는 위치와 원인을 확인하는 위치가 달라진다. 조치 수단도 원인에 따라 달라진다. 배치를 바꾸는 조치는 Kubernetes에서 수행하고, port의 대역폭 제한이나 VM 정지는 OpenStack에서 수행한다. 따라서 본 작품은 서비스에서 시작한 자원 조회가 실제 제어 대상까지 이어지도록 구성한다. 자원 사이의 관계를 명확히 기록하면, 관측한 상태가 어느 서비스와 어느 VM에 해당하는지 같은 실행 안에서 대조할 수 있다.

시나리오 1은 호스트 CPU 경합이다. VM의 vCPU 수는 그 VM이 쓸 수 있는 CPU의 상한이며 물리 CPU의 전용 사용을 보장하지 않는다. OpenStack의 기본인 공유 CPU 정책에서는 비용 효율을 위해 호스트 CPU 수보다 많은 vCPU를 배치하는 overcommit이 흔히 쓰이고, 여러 VM의 vCPU가 같은 물리 CPU를 나누어 사용한다. 따라서 같은 compute 호스트에 있는 다른 VM이 CPU를 많이 사용하면 서비스 Pod가 정상 실행 중이어도 API 응답이 느려질 수 있다. 이 경우 Pod의 실행 상태와 서비스의 응답 품질은 서로 다른 결과를 나타낸다. Kubernetes에서 확인한 Node 정보만으로는 그 Node의 VM과 경쟁 VM이 같은 호스트에 있는지를 직접 알기 어렵다. 동일 노드에서 Pod를 다시 시작하면 서비스 프로세스는 새로 만들어지지만 하위 호스트의 경합 관계는 유지된다. 본 작품은 서비스 지연과 호스트 경합을 함께 확인한 뒤 다른 compute 호스트의 worker 노드로 Pod를 옮기는 절차를 대상으로 삼는다. 목적지의 여유도 함께 확인해야 이동 이후의 서비스가 안정적으로 실행될 수 있다. 이 시나리오는 프로세스의 재시작과 실행 위치의 변경이 서로 다른 조치라는 점을 비교하기에 적합하다.

시나리오 2는 공유 송신 경로 혼잡이다. API 서비스와 대용량 업로드 작업이 같은 송신 경로를 사용하면 업로드 트래픽의 증가가 API 응답 지연으로 이어질 수 있다. 두 작업을 다른 worker 노드에 배치해도 두 VM이 같은 출구를 거쳐 나가면 병목은 그대로 남는다. 업로드가 출구 대역폭을 채우는 동안 API 응답 패킷도 같은 큐에서 기다리기 때문이다. Kubernetes의 배치 변경은 실행 위치를 바꾸는 수단이고, Neutron QoS는 VM의 port에 대역폭 제한을 적용하는 수단이다. 두 작업이 같은 port를 사용하는 상태에서 제한을 걸면 API 트래픽까지 같은 제한을 받는다. 본 작품은 업로드 작업을 별도 worker 노드의 port로 연결한 뒤 그 port를 제어하는 구성을 사용한다. 작업 분리는 제한 대상을 업로드로 한정하기 위한 전제이고, 출구의 혼잡을 줄이는 것은 port의 대역폭 제한이다. 목표 상태는 API 응답이 기준 안에 머물면서 업로드가 남은 대역폭으로 계속 진행되는 것이며, 공유 출구의 용량이 고정되어 있으므로 API 보호의 대가로 업로드 처리량이 줄어든다. 이 구성에서는 API의 응답 품질과 업로드의 진행을 함께 확인해야 한다. API 응답이 빨라졌다는 사실과 두 작업이 함께 지속되고 있다는 사실을 구분하기 위해 업로드 처리량을 결과에 포함한다.

시나리오 3은 노드 통신 단절과 데이터베이스 복구다. Kubernetes에서 Node가 NotReady로 표시되어도 해당 VM과 그 위의 데이터베이스 프로세스는 계속 실행 중일 수 있다. 통신 상태는 원격에서 응답을 확인할 수 있는지를 나타내며, 프로세스의 실행 종료는 별도의 상태다. 이전 프로세스가 멈췄는지 확인하기 전에 같은 volume을 다른 노드에서 사용하면 두 실행 주체가 같은 데이터에 쓰는 위험이 생긴다. Kubernetes는 노드가 꺼졌는지 통신만 끊겼는지를 스스로 구분할 수 없으므로, 단일 volume을 쓰는 StatefulSet의 Pod는 기존 Pod의 삭제가 확정될 때까지 다른 노드에서 다시 만들어지지 않는다. 별도 조치가 없으면 데이터베이스는 멈춘 상태로 남는다. Kubernetes의 out-of-service taint를 사용하는 복구는 노드가 실제로 꺼졌는지를 먼저 확인하는 순서를 전제로 하며, VM의 정지와 전원 상태를 확인할 수 있는 주체는 OpenStack이다. 본 작품은 Nova를 통한 fencing 요청과 실제 종료 확인을 구분한다. 종료가 확인된 뒤에만 Kubernetes의 Pod 정리와 volume 재연결 절차를 진행한다. 이 시나리오의 완료에는 새로운 데이터베이스의 접속 성공과 장애 전에 커밋된 데이터의 보존이 함께 포함된다.

시나리오 4는 worker 노드 VM 정지다. worker 노드 VM이 멈추면 Kubernetes는 남은 노드에서 Pod를 다시 실행하여 서비스를 회복시키지만, 클러스터에는 worker 노드가 한 대 줄어든 상태가 남아 다음 장애나 새 작업을 받아낼 여유가 줄어든다. 목표 용량을 되돌리려면 대체 VM을 만들고 Kubernetes 클러스터에 합류시켜야 한다. 본 작품은 Cluster API, Cluster API Provider OpenStack, MachineHealthCheck를 연결하여 이 과정을 관찰하고, 서비스가 남은 노드에서 회복되는 경로와 새 worker 노드가 준비되는 경로를 따로 기록한다.

이들 시나리오에 대응하려면 서비스 상태와 인프라 상태를 같은 자원 관계 위에서 읽어야 한다. 본 작품은 조치 대상의 식별자를 확인하고 안전 조건이 충족된 뒤 정해진 순서로 조치하도록 설계한다. 조치 이후에는 서비스 요청, 데이터, 노드 용량 가운데 해당 시나리오에 필요한 결과를 확인한다. 이러한 구조는 관측과 조치를 하나의 절차로 연결하면서도 각 단계의 성공 근거를 따로 남긴다. 예를 들어 VM 정지 요청의 접수는 fencing 완료 확인과 분리하여 기록하고, Pod의 준비 상태는 외부 요청의 회복과 함께 검토한다. 그 결과 어떤 단계에서 문제가 남았는지를 실행 기록으로 추적할 수 있다. 본 작품은 재시작, 재스케줄링, toleration, MachineHealthCheck와 같은 기존 기능을 비교 조건에 포함한다. 기존 기능만으로 서비스나 용량 문제가 남는지는 다음 절의 목표에 따라 실험으로 확인한다.

## 1.2 연구논문/작품의 목표

본 작품의 목표는 세 가지다. 첫째, OpenStack과 Kubernetes를 함께 사용하는 테스트베드를 코드로 구축한다. 클라우드 호스트의 선언에서 서비스 실행 환경까지 필요한 단계를 연결하고, 각 단계의 상태를 확인할 수 있게 한다. 둘째, 네 가지 장애에 대한 대응 모듈을 공통된 네 단계 구조로 구현한다. 자원 관계 확인, 조치 조건 판단, 대상 조치, 결과 확인을 같은 틀로 배치하되, 각 장애가 요구하는 조건과 제어 수단을 구체화한다. 셋째, 비교 조건을 둔 실험으로 조치의 효과를 확인한다. 대응 모듈이 남긴 성공 표시와 별도로 외부 요청 원자료를 평가하여 결과를 판단한다. 환경과 설정을 기록해야 같은 조건에서 조치를 비교할 수 있고, 독립적인 판정이 있어야 구현의 완료와 서비스의 회복을 각각 확인할 수 있다.

평가는 필요성, 계층 간 정보의 기여, 조치 기전, 복구 효과, 안전성의 다섯 연구 질문에 답하도록 설계하였다. 필요성은 기존 기능만으로 서비스나 용량 문제가 남는지를 묻는다. 계층 간 정보의 기여는 두 계층의 정보를 연결하는 과정이 판단과 대상 지정에서 어떤 역할을 하는지를 묻는다. 조치 기전은 구현된 절차 가운데 어떤 조치가 관측된 차이와 연결되는지를 검토한다. 복구 효과는 서비스의 응답뿐 아니라 데이터와 실행 용량까지 포함한다. 안전성은 조치 조건이 부족할 때의 보류와 실행 이후의 원상 복원을 다룬다. 이 질문들은 하나의 성공 여부로 합치기보다 서로 다른 근거로 평가할 필요가 있다. 서비스가 회복된 결과는 효과에 관한 근거이고, 실행 중인 VM에 대해 복구를 보류한 결과는 안전 순서에 관한 근거다. 본 작품은 각 질문에 대응하는 관측을 결과표와 분석에서 구분하여 제시한다.

본 작품은 사전에 정의한 네 가지 장애를 대상으로 하며, 임의의 장애를 자동으로 분류하는 기능은 범위에 포함하지 않는다. 표 1-1은 각 장애의 발생 조건, 서비스 영향, 대응 조치와 작품 내 역할을 정리한 것이다. 호스트 CPU 경합과 공유 송신 경로 혼잡은 서비스의 응답 품질 저하를 중심으로 구성한다. 노드 통신 단절은 단일 데이터베이스의 실행 종료와 같은 volume의 재사용 순서를 중심으로 구성한다. worker 노드 VM 정지는 기존 제어기가 수행하는 노드 교체를 통합하는 사례로 구성한다. 각 시나리오는 영향을 받는 자원과 조치의 완료 조건이 분명하다. 이 구분에 따라 직접 구현한 판단·순서 제어와 기반 플랫폼이 제공하는 기능의 역할을 정리한다.

| 1. 호스트 CPU 경합 | 같은 compute 호스트의 다른 VM이 CPU를 과다 사용 | API 응답 지연 | 다른 compute 호스트의 worker 노드로 API Pod 재배치 | 직접 구현 |
| 2. 공유 송신 경로 혼잡 | API와 업로드가 같은 송신 경로를 공유 | API 응답 지연 | 업로드를 다른 worker 노드로 분리하고 그 port에 Neutron QoS 적용 | 직접 구현 |
| 3. 노드 통신 단절과 데이터베이스 복구 | worker 노드의 제어 통신과 데이터베이스 접속 경로 단절 | 데이터베이스 접근 실패 | 기존 VM의 fencing 확인 → out-of-service taint → 같은 volume으로 데이터베이스 재기동 | 직접 구현 |
| 4. worker 노드 VM 정지 | worker 노드 VM 한 대 정지 | 일시적 요청 실패, 노드 용량 감소 | MachineHealthCheck 기반 Machine 교체와 용량 회복 확인 | 기존 기능 통합 |

## 1.3 전체 개관과 결과 미리보기

테스트베드는 Google Cloud의 controller 호스트 1대와 compute 호스트 2대 위에 OpenStack을 배포한 구조다. 그 위의 VM으로 Kubernetes control plane 노드와 worker 노드를 구성한다. controller 호스트는 OpenStack 제어 서비스와 클러스터를 관리하는 management 클러스터를 제공한다. compute 호스트는 workload 클러스터의 VM과 장애 재현에 필요한 경쟁 VM을 실행한다. 그림 1-1과 같이 대응 모듈과 평가 도구는 운영 클라이언트에서 두 관리 계층의 상태를 읽고 조치를 요청한다. 접근에는 IAP(Identity-Aware Proxy)를 사용한다. 하나의 서비스에서 출발하여 Pod, Node, VM과 그 하위 자원을 따라가도록 관계를 구성한다. 이 구조는 요청 품질의 변화와 인프라 조치의 대상을 같은 실행 기록으로 연결한다. 구체적인 사양과 식별자 연결 방식은 3장에서 설명한다.

> [그림 1-1 자리] 구성 요소: 아래층에 Google Cloud 호스트 3대, 가운데층에 OpenStack 서비스와 control plane 노드 VM 1대·worker 노드 VM 2대, 위층에 Kubernetes 서비스를 배치한다. 오른쪽의 대응 모듈·평가 도구에서 Kubernetes와 OpenStack 각각으로 상태 읽기와 조치 화살표를 연결한다.

[그림 1-1] 전체 구성 개요

실험 결과는 표 1-2와 같이 서비스 품질, 데이터 보존, 용량 복원으로 나누어 정리하였다. 서비스 품질은 SLO 위반율로 판정한다. SLO는 시나리오별 요청 지연 기준(100~2000 ms)이며, 외부 측정기가 보낸 요청 가운데 실패했거나 기준을 넘은 요청의 비율을 위반율로 센다. 시나리오별 기준값과 산정 근거는 4.2절에 정리하였다. 대응 모듈의 완료 기록이나 Pod의 준비 상태와 별도로, 정의한 서비스 접근 경로에서 측정한 요청의 성공 여부와 지연으로 회복을 판정하기 위해서다. 시나리오 1에서 다른 compute 호스트로 재배치한 조건의 조치 후 SLO 위반율은 0.08~0.14%였다. 무조치와 동일 노드 재시작 조건에는 더 높은 위반율이 남았다. 시나리오 2의 제안 방식은 4회 모두 조치 이후의 위반율이 0%였다. 시나리오 3에서는 fencing 확인을 앞세운 복구 뒤 1,000건의 커밋 데이터가 보존되었다. 시나리오 4에서는 두 조건 모두 서비스가 약 73~81초 중단된 뒤 회복되었고, MachineHealthCheck 사용 조건에서만 노드 용량까지 복원되었다. 시나리오 2에서는 작업 분리 단독으로 API 보호 효과가 나타나지 않았으며, Neutron QoS를 포함한 조치에는 업로드 처리량 감소라는 대가가 있었다.

[표 1-2] 시나리오별 핵심 결과

| 시나리오 | 제안 방식 | 비교 조건 | 핵심 차이 |
|---|---|---|---|
| 1 | 조치 후 SLO 위반율 0.08~0.14% | 무조치 2.44~2.63%, 동일 노드 재시작 2.24~3.54% | 재배치만 기준선 수준으로 회복 |
| 2 | 조치 후 위반율 0% (4/4) | 작업 분리 단독 2.63~3.02%, 무조치 1.72~2.34% | Neutron QoS가 필요. 업로드 처리량(관측 구간 평균) 약 66% 감소 |
| 3 | 3/3 회복, 1,000건 보존 | fencing 절차 없음 0/3 (관측 구간 동안 요청 전부 실패) | fencing 확인 후 같은 volume으로 재기동 |
| 4 | 용량 복원 3/3 (정지 요청 후 283~298초) | MachineHealthCheck 미사용: 용량 복원 0/3 | 서비스는 두 조건 모두 약 73~81초 중단 후 회복 |

※ 시나리오 3의 fencing 절차 없음 조건은 toleration 3600초와 강제 volume 분리·MachineHealthCheck 교체 차단을 적용한 대조 조건이며, Kubernetes 기본 설정의 복구 성능을 나타내지 않는다.

## 1.4 보고서 구성

본 보고서의 구성은 다음과 같다. 2장은 통합 관측, 계층 간 장애 정보 전달, 자원 경합과 네트워크 제어, 상태 저장 서비스 복구, 서비스 수준의 결과 검증이라는 다섯 관점에서 관련연구를 검토한다. 연구별 관측 대상과 조치 주체를 비교하여 본 작품의 위치를 정리한다. 3장은 기반 기술의 동작 원리와 테스트베드 구성을 제시한다. 이어 구축·운영 설계의 원칙과 공통 대응 구조를 설명하고, 각 시나리오의 판단 기준과 조치 순서를 구체화한다. 4장은 구현 결과, 측정 조건, 비교 실험의 결과를 제시한다. 결과표에 나타난 관측을 연구 질문과 연결하고, 판정 지표의 의미와 타당성 위협을 검토한다. 5장은 목표의 달성과 기여를 정리하고 후속 연구를 제시한다. 소감에는 작품을 진행하며 겪은 경험과 배운 점을 적는다. 부록에는 판단과 안전 순서를 구현한 핵심 원천코드를 수록하여 본문의 설명을 구현과 대조할 수 있게 한다.

# 2. 관련연구

본 장은 OpenStack 위에서 Kubernetes 서비스를 운영할 때 여러 계층의 정보를 연결해 장애에 대응하는 과정을 다섯 관점에서 검토한다. 검토 대상은 통합 관측, 계층 간 장애 정보 전달, 자원 경합과 네트워크 제어, 상태 저장 서비스의 복구, 서비스 수준의 결과 검증이다. 각 연구에서 관측하는 대상과 실제 변경하는 자원을 구분하고, 장애 탐지, 자원 수리, 사용자 서비스의 회복이 어떤 결과로 평가되는지 살펴본다. 이러한 비교는 본 작품의 자원 관계 확인과 조치 순서가 선행연구의 어느 부분과 연결되는지를 정리하는 기준이 된다.

## 2.1 통합 관측과 장애 증거 연결

김지용 등은 OpenStack 환경에서 서비스 메시 기반의 통합 모니터링 시스템을 제안하였다[1]. 이 시스템은 서비스 메시가 제공하는 마이크로서비스 관측 정보에 기반 인프라의 메트릭을 함께 수집하고 시각화하여, 운영자가 개별 서비스뿐 아니라 시스템 전반의 상태를 확인할 수 있게 하였다. 이 연구에서 중요한 관점은 서비스 계층의 정보와 하위 실행 환경의 정보를 함께 제공한다는 점이다. 서비스 요청의 이상과 인프라 상태를 같은 맥락에서 살펴보면 문제 발생 당시의 실행 환경을 더 넓게 파악할 수 있다. 해당 연구의 조치 단위는 자동 복구 명령보다 관측과 시각화에 놓여 있으며[1], 이 점에서 본 작품이 자원 관계를 따라 장애 근거를 모으는 과정과 관련된다.

박주원 등은 OpenStack의 시스템 및 응용 서비스 이벤트 로그를 메시지 기준으로 군집화하고 그룹 사이의 연관성을 분석하였다[2]. 시간적으로 어긋난 패턴의 비교에는 DTW(Dynamic Time Warping)를 사용하였다[2]. MicroRCA와 Sage도 관측 정보를 이용하여 성능 문제의 원인이 되는 서비스를 추정하였다[3][4]. 이들 연구는 흩어진 관측을 연결하여 문제의 위치를 파악한다는 공통점을 갖는다[2][3][4]. 관측 항목의 수집과 원인 추정은 장애 대응에서 조치를 선택하기 위한 근거를 제공한다. 본 작품은 providerID와 VM·port·volume 식별자를 이용하여 자원 관계를 명시적으로 연결하고, 장애 시점에 읽은 정보가 실제로 변경할 자원과 일치하는지를 확인하는 데 초점을 둔다.

## 2.2 계층 간 장애 정보 전달

Yang과 Kim은 컨테이너 서비스를 위한 클라우드 인프라에서 Fast Fault Detection Manager를 설계하였다[5]. OpenStack의 Ceilometer와 Aodh가 감지한 VM 장애를 Kubernetes로 전달하여 Node의 상태가 변경되도록 구성하였다[5]. 평가는 장애 발생 이후 Kubernetes의 관리 계층이 장애 정보를 받기까지의 탐지 시간을 중심으로 수행하였다[5]. VM 계층의 관측이 컨테이너 계층의 복구 흐름으로 이어진다는 점에서 본 작품과 가장 가까운 선행연구다. 장애 정보가 관리 계층 사이를 이동하도록 연결하면 상위 계층의 상태 인식에 하위 계층의 증거를 반영할 수 있다[5].

OpenStack Masakari는 VM과 compute 호스트의 장애에 대응하는 고가용성 기능을 제공한다[6]. 공식 문서는 VM 프로세스 장애 시 Nova의 정지·시작 기능으로 VM을 다시 시작하고, compute 호스트 장애 시 Nova evacuation을 사용한다고 설명한다[6]. 조치 단위는 VM이며 인프라 수준에서 실행 가능한 상태를 회복하는 흐름이다[6]. VM 수준의 복구는 그 위에서 실행되는 서비스가 다시 동작할 기반을 마련한다. Yang과 Kim의 연구와 Masakari는 각각 장애 정보의 전달과 VM 수준의 복구를 중심으로 한다[5][6]. 본 작품은 이 흐름 이후의 서비스 요청, 데이터 보존, 클러스터 용량을 외부 관측과 자원 상태로 확인하는 데까지 검토 범위를 넓힌다.

## 2.3 자원 경합과 서비스 목표를 고려한 제어

Delimitrou와 Kozyrakis의 Paragon은 서버의 이질성과 함께 배치된 작업 사이의 간섭을 고려하는 스케줄러다[7]. 이전 작업에 대한 정보를 활용하여 새로운 작업의 특성을 분류하고, 공유 자원에서의 간섭을 줄이는 방향으로 배치를 결정한다[7]. 이 접근은 작업이 어느 서버에서 실행되는지가 성능에 영향을 준다는 문제를 다루며[7], 서로 다른 실행 단위가 하위 자원을 공유하는 상황을 살피는 관점을 제공한다. 본 작품의 호스트 CPU 경합 시나리오도 VM 내부의 서비스와 같은 호스트의 다른 VM 사이에 존재하는 자원 공유 관계를 대상으로 한다.

Qiu 등의 FIRM은 마이크로서비스의 SLO 위반에 대응하는 자원 관리 프레임워크다[8]. 온라인 관측 정보와 기계학습으로 문제가 있는 마이크로서비스 및 경합 자원을 식별하고[8], 동적인 자원 재할당으로 서비스 목표 위반을 완화한다[8]. FIRM은 서비스의 응답 품질을 하위 자원 상태와 제어 조치에 연결한다는 점에서 관련된다[8]. Paragon과 FIRM은 배치 또는 자원 할당의 결정 방식을 제안한다[7][8]. 본 작품은 이미 호스트 경합이 발생한 상황에서 OpenStack의 compute 호스트 정보를 확인하고 Kubernetes의 배치를 변경하는 절차를 시나리오 1로 구현하였다. 구현한 절차의 효과는 재배치와 동일 노드 재시작의 관측 결과를 통해 검토한다.

## 2.4 네트워크 성능 제어와 작업 배치의 결합

변지섭 등은 엣지 컴퓨팅 환경에서 Kubernetes 기반 네트워크 성능 제어 방식의 실측 특성을 분석하였다[9]. 이 연구는 설정한 성능 수준에 도달하기까지 시간이 걸리거나 목표 성능을 충분히 달성하지 못하는 사례를 보고하였다[9]. 이러한 결과는 네트워크 제어의 설정값과 실제 트래픽의 동작을 구분하여 확인해야 함을 보여 준다[9]. 제어 규칙이 존재한다는 사실과 서비스가 목표 성능을 얻었다는 사실은 서로 다른 관측 대상이다. 해당 연구는 네트워크 제어를 평가할 때 설정의 확인에 더하여 서비스가 경험한 성능을 관찰하는 근거를 제공한다[9].

설정과 실측을 함께 검토하는 관점은 공유 송신 경로의 여러 작업을 다룰 때에도 적용된다. 하나의 제어 규칙이 어느 트래픽에 적용되는지에 따라 API와 업로드가 받는 영향이 달라지기 때문이다. 변지섭 등의 연구에서 나타난 목표 성능과 관측 성능의 차이는 제어 적용 이후의 결과 확인이 필요함을 뒷받침한다[9]. 본 작품의 시나리오 2는 Neutron QoS가 Open vSwitch 인터페이스에 설치되었는지 확인하고, 이와 함께 API 지연과 업로드 처리량을 관측한다. 정책 설치, API 응답 품질, 업로드 진행을 나누어 읽음으로써 제어 설정과 서비스 결과를 연결한다.

## 2.5 상태 저장 서비스의 가용성과 복구 순서

Vayghan 등은 상태 저장 마이크로서비스의 가용성을 관리하기 위한 HA(High Availability) State Controller를 제안하였다[10]. 이 구조는 애플리케이션의 상태 복제와 정상 인스턴스로의 전환을 결합한다[10]. 이 연구는 반응 시간, 수리 시간, 서비스 회복 시간, 전체 중단 시간을 구분하였다[10]. 관리 대상의 수리와 사용자에게 서비스를 다시 제공하는 사건을 따로 측정하는 점이 중요하다[10]. 이러한 구분은 상태 저장 서비스에서 새 Pod의 기동과 데이터 접근의 회복을 각각 확인하는 관점으로 이어진다.

Fence Agents Remediation은 fence agent를 사용하여 비정상 노드를 fencing하고 복구하는 Kubernetes operator다[11]. 공식 문서의 복구 과정에는 비정상 노드의 재부팅과 해당 노드 작업의 축출이 포함된다[11]. 이전 실행 주체의 동작을 끊는 절차는 상태 저장 작업을 다른 노드에서 시작하기 위한 안전 조건과 연결된다. Vayghan 등의 상태 복제와 정상 인스턴스 전환은 서비스 가용성을 유지하는 방식이고[10], fencing은 이전 실행 주체의 상태를 제어하는 방식이다[11]. 본 작품의 시나리오 3은 단일 PostgreSQL과 같은 Cinder volume을 사용한다. fencing을 확인한 뒤 그 volume을 다른 노드에서 다시 사용하도록 순서를 구성하고, 커밋 데이터의 보존과 새 요청의 수행을 확인한다.

## 2.6 probe와 사용자 관점의 회복 검증

Flora 등은 TeaStore와 SockShop에 부하와 결함을 주입하여 Kubernetes probe의 장애 감지 효과를 평가하였다[12]. 실험에서는 probe가 감지하지 못한 응용 실패가 관찰되었다[12]. 건강 검사 엔드포인트의 구현과 매개변수 설정이 감지 동작에 미치는 영향도 분석하였다[12]. 이 연구는 관리 계층에 표시되는 컨테이너 상태와 실제 응용 동작을 함께 확인해야 한다는 관점을 제공한다[12]. probe의 응답은 해당 검사 경로에 관한 관측이며, 사용자 요청의 성공과 지연은 서비스 사용 경로에 관한 관측이다. 두 종류의 관측을 함께 살피면 상태 표시가 정상인 동안에도 남아 있는 서비스 문제를 구분할 수 있다.

Basiri 등의 카오스 엔지니어링은 장애를 주입하여 분산 시스템의 실제 동작을 실험적으로 확인하는 접근이다[13]. 복잡한 시스템의 장애 대응을 가정에만 의존하지 않고 실행 결과로 검토한다는 데 의미가 있다[13]. 이 관점에서 장애 주입은 서비스가 어떤 영향을 받으며 대응 이후 어떤 상태에 도달하는지를 관찰하기 위한 수단이 된다[13]. Flora 등의 probe 평가도 결함을 주입하고 응용 실패를 함께 살폈다는 점에서 같은 실증적 관점과 연결된다[12]. 본 작품은 외부 측정기가 보낸 요청의 성공 여부와 지연으로 회복을 판정하여, Pod Ready와 사용자 관점의 응답 품질을 함께 읽는 평가 구조를 구성하였다.

# 3. 제안 작품 소개

## 3.1 이론적 배경

Nova는 VM의 생성과 실행 상태를 관리하며, 공유 CPU 정책에서는 여러 VM의 vCPU가 같은 호스트 CPU를 나누어 사용한다[14]. 이 정책에서 vCPU는 특정 호스트 CPU에 고정되지 않아 CPU overcommit이 가능하며, 시스템 전체의 효율을 얻는 대신 개별 VM의 성능과 지연이 영향을 받을 수 있다[14]. dedicated 정책은 vCPU를 호스트 CPU에 고정하여 다른 고정 VM과 CPU를 함께 쓰지 않게 한다[14]. 본 작품은 기본값인 공유 정책을 전제로 하며 dedicated 정책 환경은 범위에서 제외한다. Nova의 정지 요청은 비동기로 처리되므로 요청의 접수와 VM의 실제 정지는 따로 확인해야 한다[15]. Neutron은 VM의 네트워크 연결을 port 단위로 관리하며, Neutron QoS의 bandwidth-limit 규칙은 지정한 port의 트래픽을 제한한다[16]. bandwidth-limit 규칙은 평균 허용 속도(rate)와 한 번에 몰아 보낼 수 있는 양(burst)으로 정의된다. burst가 작으면 TCP가 전송 속도를 높이는 순간 허용량을 넘은 패킷이 버려지고 TCP가 속도를 줄이는 일이 반복되어, 실제 처리량이 설정한 rate보다 낮아진다. Neutron 문서는 TCP 트래픽의 burst를 rate의 80%로 설정하도록 권장한다[16]. Cinder는 VM에 연결하는 영구 block volume을 제공한다.

Kubernetes는 Node의 Ready 조건에 따라 not-ready 또는 unreachable taint를 붙이고, Pod는 toleration 시간(기본 300초)이 지나면 축출된다[17]. 노드가 정상 종료 절차 없이 멈춘 경우에는 노드가 실제로 꺼졌음을 확인한 뒤 out-of-service taint를 붙여야 Pod 정리와 volume 분리가 진행된다[18]. 조건에 따라 6분 뒤 volume을 강제로 분리하는 동작도 있으나[18], 본 작품은 시나리오 3에서 이를 비활성화하여 fencing을 앞세운 순서를 유지하였다.

Cluster API는 클러스터의 노드를 Machine 객체로 선언하여 관리한다. MachineHealthCheck는 Node 조건과 그 지속 시간을 검사하여 비정상 Machine의 교체를 시작하며, skip-remediation 또는 paused annotation으로 교체를 막을 수 있다[19]. Cluster API Provider OpenStack은 Machine을 Nova VM으로 생성한다[20]. Cluster Autoscaler는 배치되지 못한 Pod의 자원 요청을 보고 worker 노드 수를 조정한다.

MAPE-K는 Monitor, Analyze, Plan, Execute의 순환과 공유 Knowledge로 자율 관리를 설명하는 모델이며[21], 본 작품의 공통 대응 구조는 이 순환에 대응한다(3.3절). PSI(Pressure Stall Information)는 작업이 CPU·메모리·I/O를 기다리며 멈춘 시간의 비율로[22], CPU 사용률만으로는 구분하기 어려운 경합을 판단하는 근거로 사용한다. PostgreSQL은 데이터 파일을 바꾸기 전에 변경 내용을 WAL(Write-Ahead Logging)에 기록한다[23]. 따라서 fsync, synchronous_commit, full_page_writes가 켜진 상태에서 커밋이 끝난 데이터는 같은 volume으로 다시 기동할 때 보존된다.

## 3.2 시스템 구성

테스트베드는 Google Cloud의 사용자 정의 VPC(Virtual Private Cloud) 안에 있는 호스트 3대로 구성된다(표 3-1). controller 호스트에는 OpenStack 제어 서비스와 kind 기반 management 클러스터를 두고, compute 호스트 2대에서는 KVM 중첩 가상화로 workload 클러스터의 VM을 실행한다. 운영 클라이언트는 IAP(Identity-Aware Proxy)로만 호스트에 접근하며, workload 클러스터의 API는 공개하지 않고 터널로 접근한다. compute 호스트 1은 재배치 목적지로 쓰며, 4 vCPU로 구성한 예비 실험에서 재배치 후에도 p95 지연이 회복 기준을 간헐적으로 넘어 n2-standard-8로 구성하였다. 이로 인한 호스트 간 사양 차이는 4.6절에서 다룬다.

## 3.3 개념설계: 공통 대응 구조와 구축·운영 원칙

모든 대응 모듈은 자원 관계 확인, 조치 조건 판단, 대상 조치, 결과 확인의 네 단계로 동작한다(그림 3-2). 이는 MAPE-K의 Monitor, Analyze·Plan, Execute와 다음 순환의 Monitor·Knowledge 갱신에 대응한다. 판단 단계는 자원 사용률 하나로 장애를 선언하지 않고 서비스 영향과 자원 증거가 함께 지속될 때만 조치하며, 근거가 부족하거나 서로 맞지 않으면 보류 사유를 기록한다. 조치 단계는 변경 의도를 기록하고 조건부로 변경한 뒤 실제 적용을 다시 읽어 확인한다. 결과 확인은 한 번의 정상 응답이나 Pod Ready가 아니라 외부 요청이 연속 구간 동안 목표를 만족하는지로 판정하며, 시나리오에 따라 데이터와 노드 용량도 확인한다.

구축과 운영 코드에는 표 3-2의 원칙을 공통으로 적용하였다. 이 원칙들은 대응 조치가 잘못된 대상이나 다른 실행이 만든 자원에 영향을 주지 않게 하고, 실패한 실행을 증거와 함께 남기기 위한 것이다.

## 3.4 상세설계: 시나리오별 알고리즘

표 3-3은 네 시나리오의 판단 조건, 조치, 회복 판정과 활용한 기존 기능을 정리한 것이다.

표 3-3의 배율과 임계값은 연구자가 실험 전에 정한 공학적 기준이며, 측정으로 최적값을 찾은 값은 아니다. 경합 판정의 CPU 사용률 0.7과 PSI 0.02는 사전 측정에서 경쟁 부하가 없을 때의 값(CPU 약 12%, PSI 약 0.65%)보다 충분히 높고, 경쟁 부하를 걸었을 때의 값(약 99.7%, 24%)보다는 낮은 수준이다. 시나리오 2의 송신 16 Mbps는 20 Mbit 출구의 80%다. 시나리오 3의 접속 15회 연속 실패는 1초 간격으로 15초 동안 모든 접속이 실패한 경우를 뜻한다. 이 기준들은 결과를 본 뒤 바꾸지 않았다.

[표 3-3] 시나리오별 판단·조치·회복 기준

| 시나리오 | 판단 조건 | 조치(직접 구현) | 회복 판정 | 활용한 기존 기능 |
|---|---|---|---|---|

| 3. 노드 통신 단절과 데이터베이스 복구 | Node NotReady 뒤 데이터베이스 접속 15회 연속 실패. 기존 데이터베이스 컨테이너의 실행 여부 확인 | Nova 정지 요청 후 SHUTOFF, task_state 없음, power_state 4, libvirt shut off를 확인. 직전에 다시 확인한 뒤 out-of-service taint 적용. fencing 미확인 시 중단 | 같은 volume을 쓰는 새 Pod Ready, 1,000건 digest 일치, 새 COMMIT 후 SELECT 성공, 60초 연속 접속, volume의 단독 연결 | Nova 정지, out-of-service taint, StatefulSet, Cinder CSI, PostgreSQL WAL |

시나리오 1의 서비스는 요청마다 PBKDF2를 100,000회 계산하는 CPU 중심 HTTP 서버로, compute 호스트 2의 worker 노드에서 실행하고 같은 호스트의 4 vCPU 경쟁 VM으로 경합을 만든다. 호스트 vCPU 4개(n2-standard-4) 위에 worker 노드 VM 2 vCPU와 경쟁 VM 4 vCPU를 배치하므로 overcommit 비율은 1.5다. 경쟁 VM은 호스트 vCPU 수와 같은 4 vCPU로 두고 CPU 작업 4개를 실행하여 의도적으로 강한 경합을 만들었다. 서비스 영향과 호스트 경합이 함께 지속될 때만 조치하도록 두 조건의 동시 성립을 요구하며, 목적지는 다른 compute 호스트로 한정한다. 같은 노드에서 다시 시작해도 같은 호스트의 경합은 남기 때문이다. 그림 3-3은 진단 반복, 목적지 선택, 안정화 확인의 순서를 나타낸다.

[그림 3-3] 시나리오 1 순서도

시나리오 2는 요청마다 256 KiB를 응답하는 API와 1 MiB 조각을 보내는 업로드가 controller 호스트의 20 Mbit 송신 제한을 함께 지나는 구성이다. Neutron QoS는 port 단위로 적용되므로 두 작업이 같은 port를 쓰면 API까지 제한된다. 그래서 업로드를 별도 worker 노드로 옮겨 port를 나누고, 이동 전에 목적지 port에 제한을 먼저 걸어 이동 직후의 혼잡을 막는다(그림 3-4). 제한은 6 Mbps에서 시작하여 판정 창마다(실측 약 110초 간격) API 상태를 확인하고 10·14·18 Mbps로 올리며, burst는 사전 측정에서 정한 250 kbit로 고정한다. 10 Mbps 제한에서 burst를 1000 kbit로 두었을 때는 평균 송신량이 줄었음에도 API p95가 약 214 ms로 조정 목표(기준선의 1.3배)를 넘었고, 100 kbit와 250 kbit에서는 목표를 만족하여 업로드량이 더 많은 250 kbit를 택하였다. 이 값은 Neutron 문서가 TCP에 권장하는 값(제한값의 80%)보다 훨씬 작으며[16], 업로드 처리량을 희생하는 대신 API의 꼬리 지연을 보호하는 선택이다. 제한값 단계는 공유 출구 20 Mbit 아래에서 정한 설계값이며, 조정 규칙은 판정 창마다 API 상태를 확인해 제한값을 올리거나 내린다. 업로드 조각은 수신 측 기록과 SHA-256으로 검증하여 이동 뒤에도 중복이나 손상 없이 이어지는지 확인한다.

> [그림 3-4 자리] 구성 요소: 기존 그림 3-5(시나리오 2 조치 전후 배치도)를 그대로 사용한다. 높이는 약 7cm 이내로 줄인다.

[그림 3-4] 시나리오 2 조치 전후 배치도

시나리오 3은 단일 PostgreSQL StatefulSet이 1 GiB Cinder volume을 쓰는 구성에서, 대상 worker 노드의 Kubernetes API(6443)와 데이터베이스(5432) 경로를 iptables로 차단한다. 이때 Node는 NotReady가 되지만 기존 데이터베이스 프로세스는 계속 실행될 수 있으므로, 이전 VM이 실제로 멈췄음을 Nova와 libvirt 양쪽에서 확인한 뒤에만 out-of-service taint를 붙인다(그림 3-5). Cluster API 환경에서는 MachineHealthCheck가 VM을 삭제하여 복구할 수도 있으나, 본 시나리오는 VM을 삭제하지 않고 정지를 확인한 뒤 복구하는 순서를 검증한다. 따라서 실험 동안 toleration을 관측 구간(900초)보다 충분히 긴 3600초로 두고, 강제 volume 분리와 MachineHealthCheck의 교체를 비활성화하여, 관측된 복구가 본 모듈의 절차에 의한 것인지 확인할 수 있게 하였다. 본 모듈은 Pod 강제 삭제 명령, volume 강제 분리 API, finalizer 제거를 직접 수행하지 않는다. VM 정지를 확인한 뒤 out-of-service taint를 적용하고, Kubernetes 제어기가 Pod 정리와 volume 분리를 수행하도록 한다.

> [그림 3-5 자리] 구성 요소: 기존 그림 3-6(시나리오 3 순서도)을 그대로 사용한다. 높이는 약 8cm 이내로 줄인다.

[그림 3-5] 시나리오 3 순서도

시나리오 4의 서비스는 영구 volume이 없는 HTTP Deployment(replica 1, toleration 30초)이며, Kubernetes API의 서비스 프록시 경로로 초당 1회 요청한다. 실행기는 정확히 한 VM에 정지를 요청하고 서비스 회복과 노드 용량 회복을 따로 판정한다. 노드 교체 자체는 MachineHealthCheck, Cluster API, Cluster API Provider OpenStack이 수행하며, MachineHealthCheck 미사용 조건은 paused annotation으로 만든다. 정지 요청에서 SHUTOFF 확인까지는 약 73~81초가 걸렸다. 이 값은 4.3.4절의 서비스 중단 구간(73~81초)과 범위가 우연히 겹칠 뿐 별개의 측정값이다. 관측 구간과 용량 복원 시간은 SHUTOFF 확인 시각을 기준으로 잰다. 외부 요청은 정지 요청 전부터 계속 기록하므로 관측 구간 이전의 실패도 원자료에 남는다.

## 3.5 평가 도구 설계

평가 도구는 장애 주입기, 대응 정책, 외부 측정기, 독립 판정기를 분리한다(그림 3-6). 판정기는 외부 측정기의 요청 원자료와 사건 기록, 상태 스냅샷만 읽으며, 정책이 남긴 성공 표시는 사용하지 않는다. 판정은 측정 조건 충족, 안전성(대상·순서·식별자), 관측 구간 안의 서비스 회복을 따로 기록한다.

# 4. 구현 및 결과분석

## 4.1 구현 결과

구현 코드는 Python 약 2.5만 줄과 셸·Makefile 약 6천 줄이며, 구축·운영(scripts), 시나리오 실행기(experiments), 평가 도구(evaluation)로 나뉜다. 본 보고서의 결과는 최종 평가 33회다. 이에 앞서 구현 동작을 확인하고 설정값을 정하기 위한 예비 실험을 수행하였으며(예: 시나리오 2의 burst, 3.4절), 그 결과는 분석에 포함하지 않았다. 구축은 클라우드 선언부터 Cluster Autoscaler까지 하위 계층부터 순서대로 검증했으며, worker 노드의 1→2→3→2→1 자동 증감과 삭제된 노드의 Machine·VM·port 정리도 확인하였다. 장애 비교 실험은 worker 노드 수를 2대로 고정한 조건에서 수행하였다.

## 4.2 실험 방법

외부 측정기는 대응 모듈과 분리된 요청 생성기로, 예정된 시각마다 요청을 보내고 예정 시각, 성공 여부, 지연을 모두 기록하며, 서비스 요청은 재시도하지 않는다. 표 4-1은 시나리오별 측정 조건과 비교 조건이다. 각 시나리오는 같은 장애·부하·설정에서 제안 조치만 뺀 무조치를 기본 비교로 두었다. 시나리오 1에는 재시작의 효과를 구분하는 동일 노드 재시작과, 호스트 경합만 있고 서비스 영향은 없을 때 조치하지 않는지 확인하는 경합만 있는 대조 조건을 더했다. 시나리오 2의 작업 분리 단독 조건은 Neutron QoS의 필요성을 확인하려고 다른 결과를 본 뒤 추가하였다. 실험은 11개 조건, 총 33회다. 요청 발생 위치는 시나리오마다 다르다(표 4-1). 대응 모듈과 판정기는 운영 클라이언트(노트북)에서 실행하지만, 시나리오 1~3의 요청은 테스트베드 안에서 발생하고 시나리오 4만 운영 클라이언트에서 Kubernetes API를 거쳐 보낸다.

[표 4-1] 측정 조건과 비교 조건

| 시나리오 | 관측 구간 | 요청률 | SLO | 요청 발생 위치 | 장애 강도 | 비교 조건(횟수) |
|---|---:|---:|---:|---|---|---|

※ 시나리오 1의 경합만 있는 대조 조건은 SLO 100 ms를 사용하였다. 이 조건은 요청당 PBKDF2 계산을 10,000회로 줄여(다른 시나리오 1 조건은 100,000회) 정상 지연이 낮으므로, 200 ms를 쓰면 기준이 지나치게 느슨해져 서비스 영향이 없다는 판정이 의미를 잃기 때문이다. 경쟁 VM과 CPU 작업 4개는 다른 시나리오 1 조건과 같다.

SLO는 외부 SLA가 아니라 연구자가 지정한 합성 workload의 실험 목표다. 장애의 탐지는 대응 모듈의 상대 기준(기준선 대비 배율)이 맡고, SLO는 결과에 따라 달라지지 않는 고정 목표로 정상 지연보다 넉넉하게 두어 서비스가 목표를 벗어났는지를 판정한다. 시나리오 1은 정상 상태 300초 측정 3회의 20초 구간 45개에서 가장 큰 p95(113.9 ms)에 1.2를 곱해 10 ms 단위로 올리고, 하한 200 ms를 적용하여 200 ms를 얻었다. 하한은 짧은 정상 측정의 변동 때문에 목표가 낮아지는 것을 막기 위해 두었다. 이후 정상 상태 검증 2회도 이 기준을 충족하였다. 시나리오 2는 정상 상태 p95(약 105~111 ms)보다 넉넉한 500 ms로 정하였다. 시나리오 3·4의 장애는 지연 증가가 아니라 요청 실패나 시간 초과로 나타나므로, 정상 지연보다 충분히 큰 2000 ms를 두어 위반이 주로 요청 실패로 집계되게 하였다(요청 제한 시간 5초). SLO는 비교 조건의 결과에 맞추어 조정하지 않았다.

20초 판정 구간마다 예정 요청이 모두 기록되고, SLO 위반 비율이 5% 이하이며, 성공 요청의 p95 지연이 SLO 이하이면 정상 구간이다. 엄격 회복 판정은 관측 구간 끝까지 정상 구간이 120초 이상 이어지는 경우이며, 회복하지 못한 실험의 시간은 —로 표시한다. 시나리오 1·2는 조치 적용 확인 시각부터 관측 구간 끝까지의 SLO 위반율(조치 후 위반율)을 주지표로 쓰고, 조치 기록이 없는 무조치에는 진단 완료 시각을 집계 시작으로 사용한다. 이 지표를 택한 이유는 4.5절에서 설명한다.

대응 모듈의 조치 조건과 독립 판정기의 서비스 평가 기준은 목적이 다르다. 전자는 기준선 대비 성능 저하와 자원 경합을 확인하고, 후자는 사전에 정한 요청 지연 임계값과 구간별 위반 비율로 서비스 상태를 평가한다. 따라서 모듈이 조치하더라도 독립 판정상 비정상 구간이 발생하지 않을 수 있다. 조치 후 위반율은 결과 확인 뒤 정한 지표이며(4.5절), 집계는 첫 조치의 적용 확인 시각부터 시작한다. 시나리오 1에서는 Deployment patch 응답을 받고 변경된 Deployment를 다시 읽은 시각(Pod 이동 완료 전)이고, 시나리오 2에서는 목적지 port의 QoS 제한이 Open vSwitch에 설치되고 업로드 Pod가 목적지 노드에서 준비된 시각이다. 작업 분리 단독 조건은 QoS 없이 업로드 Pod의 이동 완료 시각을 쓴다.

요청 실패는 두 조건 모두 정지 요청 약 10초 뒤 시작되어 73~81초 이어졌고, 대부분 VM이 SHUTOFF로 확인되기 전에 발생하였다(표 4-5, 그림 4-3). Nova는 게스트의 정상 종료를 기본 60초까지 기다린 뒤 강제로 종료하므로, 그동안 게스트 안에서 서비스가 먼저 멈춘 것으로 해석된다. nova-compute 로그를 수집하지 않아 정상 종료와 강제 종료 중 어느 쪽이었는지는 확인하지 않았다. 서비스는 두 조건 모두 남은 worker 노드에서 회복했지만, 노드 용량은 MachineHealthCheck 사용 조건에서만 정지 요청 후 283~298초에 복원되었다. 서비스는 Kubernetes가 회복시키지만 노드 용량은 인프라 계층의 교체 없이는 돌아오지 않는다는 1.1절의 문제가 실측으로 확인된 것이다. 용량 복원은 기존 기능이 수행하였으며, 본 작품의 기여는 이를 통합하여 서비스와 용량을 분리해 판정하는 부분이다. 실행이 중단된 뒤 정지 요청을 다시 보내지 않고 재개·정리하는 절차도 구현했으나, 이는 단위 테스트로만 확인했고 본 실험에서 중단이 발생하지는 않았다.

필요성과 복구 효과는 지지되었다(표 4-6). 기존 기능만 쓴 조건에서는 서비스 품질이나 노드 용량 문제가 남았다. 시나리오 3 fencing 절차 없음(다른 자동 복구 차단)는 기존 자동 복구를 막은 대조이므로 필요성 근거에서 제외하였다. 시나리오 1·2에서는 조치 후 위반율이 감소하였다. 시나리오 3에서는 데이터베이스 접근이 회복되고 기준 데이터가 보존되었으며, 시나리오 4에서는 서비스 회복과 노드 용량 복원이 각각 관측되었다. 조건 간 차이를 보면 시나리오 1·2의 조치 후 위반율은 비교 조건과 완전히 분리되었고(양측 확률값 각각 0.10, 0.057), 시나리오 3·4는 3/3 대 0/3이었다(0.10). 시나리오 1·2는 조치 후 위반율에 대한 정확 순열 검정으로, 제안 방식을 각 비교 조건과 따로 비교하였다(시나리오 1은 3회 대 3회, 시나리오 2는 4회 대 3회). 시나리오 3·4는 엄격 회복과 용량 복원 여부에 대한 Fisher 정확 검정이다. 모두 양측 검정이고 표본 단위는 실행 회차이며, 두 집합이 완전히 분리되어 동률은 없었다. 표본이 작아 이 확률값은 설명용으로만 제시한다.

계층 간 정보의 기여는 부분 지지로 판정하였다. 시나리오 3에서는 Node가 NotReady였으나 VM과 데이터베이스는 실행 중이어서, Kubernetes 정보만으로는 이전 writer의 종료를 판단할 수 없음을 관측하였다. 시나리오 2에서는 업로드 Pod가 연결된 VM과 Neutron port를 알아야 QoS 대상을 정할 수 있었으며, 이는 구성상의 근거다. 다만 단일 계층 정보만 쓰는 판단 규칙과 결과를 비교하지 않았고, 시나리오 1은 worker 노드 2대가 서로 다른 호스트에 있어 "다른 노드로 옮긴다"는 단일 계층 규칙도 같은 목적지를 고르므로 정보의 효과를 따로 식별할 수 없다. 조치 기전은 부분 지지다. 시나리오 1의 재배치 효과와 시나리오 2의 Neutron QoS 필요성은 확인했지만, 작업 분리가 꼭 필요한지와 시나리오 3의 개별 조치 기여는 나누어 시험하지 않았다. 안전성도 부분 지지다. 경합만 있는 대조 조건의 보류와 33회 전체의 정리 검증을 관측하였다. 또한 최종 비교 실험 33회와 별도로, 환경 식별자가 일치하지 않는 실행 시도 4회가 장애 주입 전에 거부되었다. fencing이 확인되지 않은 상태에서 후속 복구 조치를 거부하는 동작은 단위 테스트와 예비 실험에서 확인하였으며, 최종 실험에서는 발생하지 않았다.

## 4.5 판정 지표에 대한 고찰

엄격 회복 판정은 관측 구간 끝의 120초가 모두 정상 구간이면 회복으로 본다. 그런데 위반율이 낮은 수준으로 일정하게 유지되는 조건에서는 각 구간이 대부분 5% 기준을 통과하므로, 서비스가 개선되지 않아도 회복으로 판정될 수 있다. 예를 들어 위반율이 약 2.6%(시나리오 1 무조치의 중앙값)이면 요청 100개인 구간 하나가 기준을 넘을 확률은 약 4.7%이고, 마지막 6개 구간이 모두 정상일 확률은 약 75%다(요청 간 독립과 일정한 위반 확률을 가정한 단순화된 예시). 실제로 위반율이 줄지 않은 조건들(시나리오 1 무조치 2/3, 동일 노드 재시작 3/3, 시나리오 2 무조치 3/3, 작업 분리 단독 2/3)도 회복으로 판정되었고, 그 시점은 100~1040초로 흩어져 있었다. 따라서 엄격 회복은 개선 여부를 구분하는 지표로 적합하지 않아, 시나리오 1·2는 조치 후 SLO 위반율을 주지표로 삼고 엄격 회복 판정은 함께 공개하였다. 이 지표는 실험 후에 정한 것이다.

조치 시점에 따른 집계 구간 선택의 영향을 확인하기 위해 관측 구간 전체의 SLO 위반율도 비교하였다(표 4-2, 표 4-3). 시나리오 1에서는 제안 방식이 0.57~0.68%, 무조치와 동일 노드 재시작이 2.38~3.48%였다(경합만 있는 대조 조건은 제외). 시나리오 2에서는 제안 방식이 0.21~0.50%, 무조치와 작업 분리 단독이 1.67~2.83%였다. 따라서 관측된 조건 간 분리는 조치 후 구간만을 선택했을 때에 한정되지 않았다. 다만 이는 동일한 실행 자료에 대한 보완 분석이며, 사후 지표 선택과 작은 반복 수의 한계는 남는다.

## 4.6 타당성 위협과 한계

본 평가는 조건당 2~4회의 소규모 비교 실험이며, worker 노드 2대와 호스트 3대의 고정된 테스트베드에서 수행하였다. 재배치 목적지 호스트(8 vCPU)가 원래 호스트(4 vCPU)보다 커서, 시나리오 1의 개선에서 호스트 변경과 사양 차이의 효과를 분리하지 못하였다. 다만 재배치 후 지연은 장애 주입 전 기준선보다 낮아지지 않았다. 또한 시나리오 1의 요청 발생 위치가 재배치 목적지 호스트에 있다(표 4-1). 시나리오 1의 경쟁 VM은 CPU를 계속 사용하여 간헐적 경합보다 강한 조건이다. 시나리오 2의 burst는 10 Mbps 한 조건에서 정한 값을 모든 단계에 사용했고, 본 실험에서는 바꾸어 시험하지 않았다. 제한값을 단계적으로 올리지 않고 처음부터 한 값으로 유지하는 조건과 비교하지 않아 단계적 상향의 추가 효과는 평가하지 못하였고, 실효 처리량이 설정 상한보다 낮아 API 보호에 작은 burst와 단계적 상향 규칙이 각각 얼마나 기여했는지도 분리하지 못하였다. 조치 후 위반율과 작업 분리 단독 조건은 사후에 정하였다. 시나리오 3은 커밋된 기준 레코드의 보존만 확인했고, fencing 절차 없음 조건의 미회복은 900초 관측 범위의 결과다. 또한 시나리오 3은 MachineHealthCheck의 VM 교체에 의한 복구와 비교하지 않았다. 시나리오 4의 관측 구간은 SHUTOFF 확인 시각에서 시작하므로 실제 중단은 정지 요청 기준으로 함께 제시하였다.

# 5. 결론 및 소감

## 5.1 결론

본 작품은 OpenStack과 Kubernetes의 자원 관계를 식별자로 연결하여 대표 장애 네 가지에 대응하는 모듈을 구현하고, 11개 조건, 총 33회의 비교 실험으로 검증하였다. 통합 테스트베드를 코드로 구축하고, 네 단계의 공통 구조로 대응 모듈을 구현했으며, 외부 요청 원자료로 결과를 독립 판정하였다. 실험에서 호스트 경합 시 다른 호스트로의 재배치는 위반율을 기준선 수준으로 되돌렸고, Neutron QoS는 업로드 처리량을 대가로 API를 보호했으며, fencing을 앞세운 복구는 커밋 데이터를 보존하였다. worker 노드 VM 정지에서는 서비스 회복과 노드 용량 회복이 서로 다른 조건으로 이루어짐을 확인하였다. 본 구현에서는 Pod·Node와 VM·port의 식별자 연결을 이용하여 QoS 조치 대상을 특정하고 fencing 상태를 확인하였다. 계층 간 정보의 독립적인 효과는 현재 실험 구성에서 분리 평가하지 못하였다. 후속 연구로는 작업 분리 없이 Neutron QoS만 적용하는 조건, 단일 계층 정보만 쓰는 판단 규칙과의 비교, fencing과 out-of-service taint의 개별 효과 분리, 같은 호스트에 대체 노드가 있는 3대 이상의 worker 구성에서의 검증, Neutron QoS의 burst 설정에 따른 실효 처리량 비교가 필요하다.

## 5.2 소감

처음 이 주제를 골랐을 때 나는 OpenStack 위에 Kubernetes를 올리고 장애가 나면 자동으로 고치는 프로그램을 만드는 일을 구현의 문제로만 생각했다. 구축 초기에는 로컬 환경에 테스트베드를 꾸렸지만, 실행 환경과 CPU 구조가 다른 여러 구성을 함께 유지하는 부담이 커서 Google Cloud 한 곳으로 옮겼다. 중첩 가상화 위에 OpenStack과 Cluster API를 올리고 worker 노드가 자동으로 늘고 줄어드는 것을 처음 확인했을 때, 이제 시작할 수 있겠다는 안도감이 들었다.

가장 오래 붙잡고 있었던 것은 내가 만든 기능이 아니라 그 아래의 환경이었다. security group의 주소 목록이 비어 DNS가 실패하기도 했고, 접속 터널이 끊겨 실행이 중간에 멈추기도 했다. 원인을 하나 찾을 때마다 장애 대응을 연구한다면서 정작 내 실험 환경의 장애에 가장 많이 대응하고 있다는 생각이 들었다.

결과를 정리하면서 가장 크게 배운 것은 조치가 끝났다는 기록과 서비스가 회복되었다는 관측이 서로 다르다는 점이다. 시나리오 3에서 Node는 NotReady였지만 VM과 데이터베이스는 계속 실행 중이었고, 시나리오 4에서는 서비스가 회복된 뒤에도 노드 용량이 돌아오지 않은 조건이 있었다. 시나리오 2에서는 API를 보호한 대가로 업로드 처리량이 줄었다. 하나의 성공 여부로 합쳤다면 보이지 않았을 차이들이다. 그래서 판정기가 대응 모듈의 성공 표시를 쓰지 않고 외부 요청 원자료만 읽도록 분리한 것이 이 작품에서 가장 잘한 결정이었다고 생각한다. 판정 지표도 마찬가지였다. 엄격 회복 판정만 보면 위반율이 줄지 않은 조건도 회복으로 기록되었고, 숫자는 그것을 잰 방법과 함께 읽어야 한다는 것을 배웠다.

진행하면서 스스로 지키려고 한 원칙도 있다. 재배치 목적지의 성능이 회복 기준을 넘었을 때 기준을 낮추지 않고 목적지 사양을 늘렸으며, 그 사실과 한계를 기록했다. 복구되지 않은 결과도 다시 돌려 좋은 결과로 바꾸지 않았다. 그리고 이 작품의 가치가 복구 속도보다, 이전 VM이 멈췄는지 확인한 뒤에야 볼륨을 넘기는 안전한 순서에 있다는 것을 분명히 알게 되었다. 제한된 클라우드 비용 안에서 호스트 가동 시간을 관리한 경험도 비용을 생각하며 일하는 연습이 되었다.

아쉬움도 남는다. 같은 호스트에 대체 노드를 두는 구성이나 작업 분리 없이 QoS만 거는 조건은 자원과 비용 제약으로 시험하지 못했다. 다시 한다면 실험 환경의 안정성과 측정 방법부터 먼저 검증한 뒤 기능을 만들겠다. 이번 작품을 통해 동작하는 시스템을 만드는 것과 그것이 제대로 동작한다고 말할 수 있는 근거를 만드는 것은 다른 일이며, 후자가 훨씬 어렵고 중요하다는 것을 배웠다.

def diagnose(baseline, sample, metrics, cpu_before, cpu_after, baseline_pressure, rate):
    reasons = []
    if sample['requests'] < rate * POLICY['window_seconds'] * .9 or sample['duplicate_indexes'] or\
            sample['max_sample_gap_seconds'] is None or sample['max_sample_gap_seconds'] > max(2.5, 3 / rate):
        reasons.append('request_evidence_incomplete')
    if not baseline['latency_ms']['p95']:
        reasons.append('latency_unavailable')
    elif sample['failures'] <= baseline['failures']:
        if not sample['latency_ms']['p95']:
            reasons.append('latency_unavailable')
        elif sample['latency_ms']['p95'] <= baseline['latency_ms']['p95'] * POLICY['impact_ratio']:
            reasons.append('service_impact_not_confirmed')
    if metrics['cpu_utilization'] < POLICY['cpu_min'] or\
            metrics['cpu_pressure_some'] < max(POLICY['psi_min'], baseline_pressure * POLICY['psi_baseline_ratio']):
        reasons.append('host_contention_not_confirmed')
    delta, errors = pod_cpu_delta(cpu_before, cpu_after)
    if errors or delta.get('nr_throttled', 0) or delta.get('throttled_usec', 0):

    if metrics['memory_pressure_some'] >= .02 or metrics['io_pressure_some'] >= .02 or\
            metrics['memory_available'] < POLICY['min_host_memory_bytes']:
        reasons.append('other_host_pressure')

        self.write('fence-intent', fence_requested_at=utc_now())

    def mark_out_of_service(self):
        source = self.record['source']
        # Re-read fencing immediately before the first destructive recovery action.
        server = self.admin_json('server', 'show', source['nova_id'])
        if server.get('OS-EXT-SRV-ATTR:host') != source['host']:
            raise RuntimeError('source VM hypervisor mapping changed')
        hypervisor = self.operational_remote('s3-hypervisor-state','sudo docker exec nova_libvirt virsh domstate ' + shlex.quote(source['instance_name']), host=source['host'])
        require_fenced(server, source['nova_id'], hypervisor)
        node = self.obj('node', source['node'], False)
        if node['metadata']['uid'] != source['node_uid']:
            raise RuntimeError('source Node identity changed')
        taints = node['spec'].get('taints', [])
        if any(t['key'] == OUT for t in taints):
            raise RuntimeError('out-of-service taint is owned by another actor')

                 {'op': 'add', 'path': '/spec/taints', 'value': taints + [{'key': OUT, 'value': self.record['run_id'], 'effect': 'NoExecute'}]}]
